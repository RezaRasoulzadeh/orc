# M05-002 — Make persisted Plan provenance Controller-compatible

**Status:** Planned
**Milestone:** M05 — Planning and Lead unification

## Objective

Remove the durable Plan schema's false assumption that every Plan must originate from both a Lead decision and a Planner run, while preserving truthful provenance for all existing legacy Plans.

This is the prerequisite discovered while attempting supervised Controller proposal persistence. M05-001 can produce a valid Controller plan proposal, but the current canonical `plans` schema cannot represent its origin without fabricating legacy lineage.

M05-002 changes only durable Plan provenance semantics and the deterministic persistence/read/validation code that depends on them. It does not yet persist a Controller plan proposal through authorization.

## Confirmed repository constraint

Current canonical Plan persistence requires:

- `source_lead_decision_id INTEGER NOT NULL`;
- `source_planner_run_id INTEGER NOT NULL`;
- a real project `PLAN_REQUIRED` Lead decision;
- a real `execution_class = 'plan'` Planner run.

`store_plan_and_consume_decision` also consumes the Lead decision, while `store_plan_revision` requires an actionable `REVISE_PLAN` decision plus Planner run. Existing plan-review validation assumes consumed Lead provenance and a completed Planner run.

These are legacy workflow assumptions, not intrinsic Plan invariants. A Controller-origin Plan cannot satisfy them truthfully.

## Target invariant

A persisted Plan must always have truthful, explicit origin/provenance, but legacy Lead/Planner references are required only when the Plan actually originated through the legacy Lead→Planner path.

The durable model must distinguish at least:

- legacy Planner-origin Plans, retaining their real Lead decision and Planner run references;
- Controller-origin Plans, which have no fabricated Lead decision or Planner run references.

Use the smallest repository-compatible representation that makes this invariant explicit. Prefer an explicit typed Plan origin/provenance discriminator plus origin-appropriate optional references over implicit inference from nulls alone.

## Scope

- Inspect the exact `plans` schema, `PersistedPlan`, Plan row decoding, `store_plan`, `store_plan_and_consume_decision`, `store_plan_revision`, plan-history/read-model code, plan-review validation, approved-plan application, and all storage tests before editing.
- Introduce a typed, model-independent persisted Plan origin/provenance representation.
- Migrate the `plans` schema so legacy source references are no longer universally `NOT NULL`, while retaining foreign-key integrity whenever those references are present.
- Ensure legacy Planner-origin creation still requires and validates the exact real Lead decision and Planner run it requires today.
- Ensure legacy revision persistence still preserves its existing actionable `REVISE_PLAN` and Planner-run lineage rules.
- Add a canonical storage/application seam capable of representing Controller-origin Plan provenance without requiring/fabricating Lead or Planner IDs. This seam may remain unused by production Controller persistence until the next task.
- Update Plan reads/serialization/read models so callers can distinguish origin truthfully.
- Update plan-review preconditions so provenance-specific checks apply to the appropriate origin instead of universally requiring legacy Lead/Planner lineage. Do not migrate plan-review judgment itself.
- Preserve existing Plan status/version/parent/supersession semantics.
- Add migration/reopen tests proving existing legacy DB data remains readable and retains lineage.

## Preserve

- Canonical `PlanResponse` validation.
- Plan status/version/parent/supersession invariants.
- Existing legacy Lead→Planner proposal behavior.
- Existing legacy plan revision behavior.
- Existing plan review decisions and review persistence semantics except removing the invalid universal assumption that all Plans have legacy provenance.
- Existing approved-plan application/task creation semantics.
- Foreign-key integrity for real Lead/Planner references.
- `OrcApp`/Database as trusted deterministic mutation boundaries.

## Constraints

- Do not fabricate Lead decision IDs or Planner run IDs.
- Do not consume a Lead decision for Controller provenance.
- Do not create fake Planner runs.
- Do not infer Controller origin merely from arbitrary missing data if an explicit origin representation is practical.
- Do not weaken validation for legacy Planner-origin Plans.
- Do not persist a production Controller proposal yet; this task creates the truthful durable representation/seam only.
- Do not add Controller authorization/execution from the superseded M05-002 scope; that becomes the next task after this prerequisite passes review.
- Do not create/apply tasks.
- Do not approve Plans.
- Do not remove Lead/Planner roles, commands, workflow stages, or tables.
- Do not broadly rewrite the workflow engine.
- No Qwen-specific behavior.
- No Python.

## Non-goals

- Authorized Controller Plan persistence.
- Controller plan-review judgment.
- Controller Plan revision.
- Applying Controller Plans.
- Removing legacy Lead/Planner machinery.
- DIRECT_TASKS migration.
- User-decision routing migration.
- Memory, autonomy, TUI, or GUI work.

## Dependencies

- M05-001 complete.
- Repository discovery from the aborted original M05-002 attempt establishes the blocking legacy provenance constraint.

## Acceptance criteria

1. Persisted Plan provenance explicitly distinguishes legacy Planner origin from Controller origin without fabricated IDs.
2. Existing legacy Plans retain real Lead-decision and Planner-run lineage after schema migration/reopen.
3. Legacy Planner-origin Plan creation still rejects missing, wrong-project, wrong-kind, or invalid Planner/Lead provenance as before.
4. A canonical deterministic storage representation/API can represent a Controller-origin `Proposed` Plan with no Lead decision or Planner run references, without creating tasks or consuming Lead state.
5. Plan reads/read models expose truthful provenance and do not panic or misclassify Controller-origin records.
6. Plan-review eligibility/validation no longer universally requires legacy provenance; legacy provenance checks remain intact for legacy-origin Plans.
7. Plan status/version/parent/supersession and approved-plan application behavior remain unchanged.
8. Existing planning/Lead/workflow/storage tests pass, with new migration/provenance tests covering both origins.
