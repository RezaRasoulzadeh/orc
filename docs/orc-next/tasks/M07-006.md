# M07-006 — Establish explicit bounded Controller memory capture grants

**Status:** Done
**Milestone:** M07 — Supervised autonomy

## Objective

Establish the smallest explicit finite permission boundary required before M06-010 Controller memory-capture judgment can later be invoked automatically and allowed to persist project-bound durable memory without bypassing the existing M06-009 supervised mutation boundary.

This task adds permission only. It does **not** automatically generate capture candidates, invoke capture judgment, mutate memory on workflow events, scan memory, or integrate memory automation into the workflow loop.

## Repository-grounded context

M06-009 already owns the canonical memory mutation boundary:

- typed `ControllerMemoryMutationIntent::{Create, Correct, Supersede, Remove}`;
- deterministic current-project/scope/target legality;
- validated `ControllerMemoryMutationProposal`;
- opaque one-shot `ControllerMemoryMutationAuthorization` for one exact proposal;
- fresh canonical validation immediately before mutation;
- mutation only through the existing `MemoryService`.

M06-010 already owns bounded read-only capture judgment over one explicit trusted candidate. It can return only `Ignore` or one exact candidate-backed `Create` intent. It intentionally cannot authorize or execute that intent.

M07-001 through M07-005 established a finite grant model for routine task continuation, but that grant is deliberately specific to `ControllerActionIntent::{Dispatch, SemanticReview, Revise}` and must not be stretched into a universal permission object for unrelated memory capabilities.

The missing seam for future automatic capture is therefore a capability-specific, project-bound finite capture permission that can mint the **existing M06-009 exact one-shot authorization** for an eligible candidate-backed `Create` proposal. The grant must not create a second memory mutation or persistence path.

## Scope

Add one opaque in-process `ControllerMemoryCaptureGrant` and the smallest application seam required to inspect an existing M06-009 proposal against it.

Required behavior:

- grants are created only by trusted `OrcApp` code for the current positive project ID;
- grants are opaque and non-serializable;
- grants have a positive finite mutation budget with a hard kernel maximum;
- cloned handles share the same mutable budget/lifecycle state and cannot reset permission by cloning;
- lifecycle is Active / Exhausted / Revoked;
- grant scope is **capture Create only**; it cannot authorize Correct, Supersede, Remove, task actions, recovery, Plan mutation, or Accept;
- automatic-capable capture permission is restricted to project-bound `MemoryKind::Project` and `MemoryKind::Episodic` records for the grant's exact current project;
- `MemoryKind::User` and `MemoryKind::Experience` remain outside this automatic-capable grant;
- inspection accepts an already validated canonical `ControllerMemoryMutationProposal` and rejects any proposal that is not one eligible project-bound Create proposal;
- exact proposal project identity, kind, scope, and current project binding are checked deterministically before authorization;
- successful inspection mints the existing M06-009 `ControllerMemoryMutationAuthorization` for that exact proposal and consumes exactly one grant unit;
- rejected inspection consumes zero budget;
- exhausted, revoked, wrong-project, global-memory, non-Create, invalid, or otherwise ineligible proposals mint no authorization and consume zero budget;
- mutation execution remains exclusively `OrcApp::execute_authorized_controller_memory_mutation(...)`;
- a failure after a successful authorization mint receives no budget refund;
- grants are in-process only and are never stored in project/global persistence or reconstructed after restart.

## Why this is a separate grant

Do not broaden `ControllerContinuationGrant` into a universal Controller permission token. Routine task continuation and durable memory mutation are different capability domains with different legality and risk boundaries.

This capture grant reuses the same architectural pattern—finite explicit permission + exact existing one-shot authorization—without sharing action enums, intent types, lifecycle persistence, or execution code with task continuation.

## Invariants / requirements

- M06-009 remains the sole canonical memory mutation legality/authorization/execution path.
- M06-010 remains the sole capture judgment schema.
- The grant contains no model runtime, `MemoryService`, database handle, filesystem handle, workflow handle, or mutation callback.
- The model never sees, constructs, extends, revokes, or inspects grants.
- No authorization may be minted for `User` or `Experience` memory through this grant.
- No authorization may be minted for Correct/Supersede/Remove through this grant.
- Project/Episodic Create must match the grant's exact project in both proposal binding and memory scope.
- One successful exact authorization mint consumes exactly one unit.
- Pre-mint rejection consumes zero.
- Post-mint execution/fresh-validation/storage failure is not refunded.
- Revocation is shared across handles/clones.
- Budget exhaustion is deterministic and observable.
- No provider token budget or model-specific behavior is introduced.
- No automatic workflow invocation, background scanning, transcript ingestion, semantic/vector retrieval, or Python.

## Non-goals

- Automatically invoking `judge_controller_memory_capture()`.
- Deriving capture candidates from tasks, reviews, Plans, transcripts, or workflow events.
- Automatically executing an M06-010 proposal.
- Global User/Experience automatic memory writes.
- Automatic Correct/Supersede/Remove maintenance.
- Extending the routine-action `ControllerContinuationGrant`.
- Persisting/reconstructing grants across restart.
- Replenishing grants automatically.
- Workflow-loop integration.
- CLI/TUI/GUI controls.
- Memory ranking, semantic search, embeddings, or consolidation.

## Acceptance criteria

1. Trusted application code can create one finite project-bound capture grant with observable remaining budget and lifecycle.
2. The grant can authorize only an already validated M06-009 project-bound Create proposal for `Project` or `Episodic` memory in its exact project.
3. Successful inspection returns/mints the existing M06-009 one-shot `ControllerMemoryMutationAuthorization` and consumes exactly one grant unit.
4. Rejected inspection—including global kinds, non-Create operations, wrong project, revoked/exhausted state, or invalid scope—mints nothing and consumes zero.
5. M06-009 execution remains unchanged and still performs fresh validation and canonical mutation.
6. Post-mint failure is not refunded.
7. Shared handles cannot reset budget or revocation state.
8. Grants are non-serializable/in-process only and existing memory/capture/task-continuation APIs remain unchanged.

## Required validation

- eligible Project/Episodic Create authorization and exact unit consumption;
- shared budget/exhaustion/revocation behavior;
- wrong-project/scope/global-kind/non-Create zero-consumption rejection;
- exact authorization reuse protection;
