# M06-002 — Add deterministic bounded memory retrieval to Controller context

**Status:** Planned
**Milestone:** M06 — Persistent memory

## Objective

Project active durable memory into the existing bounded, model-independent Controller context through a deterministic read-only retrieval path.

M06-001 established canonical typed memory records and storage. M06-002 makes selected memory visible to Controller reasoning without granting memory mutation authority, adding semantic retrieval, or weakening current task/project authority.

## Repository-grounded direction

M06-001 exposes durable memory through the canonical `MemoryService` / typed memory API. `ControllerStatePacket` is the existing bounded Controller context and already enforces an overall serialized packet limit.

M06-002 must connect those existing seams rather than introduce a parallel retrieval store, direct SQLite access, or a model-owned memory path.

The retrieval boundary must remain model-independent and deterministic. Memory is supporting context, not a replacement for canonical Orc state.

## Authority and precedence

Controller context must preserve the architecture precedence:

```text
current operator instruction
→ current project facts/decisions
→ current task/plan contract
→ durable user preferences
→ historical experience
→ base model tendencies
```

For the memory projection added here:

- current operator instruction is never replaced, rewritten, or inferred from durable memory;
- canonical current project/task/Plan facts remain authoritative over memory;
- Project memory is current-project scoped and may provide durable project facts/decisions;
- User memory is cross-project durable preference/context and must not override a conflicting current-project fact or task/Plan contract;
- Episodic memory is project-scoped historical context, not stronger authority than current project/task state;
- Experience memory is cross-project historical guidance and must never be presented as authoritative current-project fact.

The Controller-facing representation must retain enough source metadata to distinguish these authority levels explicitly rather than relying on prompt wording alone.

## Retrieval eligibility

Normal Controller context may include only active memory records.

- Removed records must not appear.
- Superseded records must not appear.
- Project and Episodic records must be bound to the exact current project identity.
- User and Experience records come from the existing shared global authority.
- Retrieval must use the canonical M06-001 application/storage API; Controller code must not query raw SQLite tables.
- Retrieval itself must not modify memory records, lifecycle state, timestamps, confidence, or history.

Historical inspection remains available through the M06-001 memory API but is not part of normal Controller context assembly.

## Controller memory projection

Add a model-independent typed projection to Controller state containing only bounded fields needed for reasoning and provenance inspection.

Each projected memory must retain at least:

- stable memory identity;
- memory kind;
- scope identity where applicable;
- bounded subject;
- bounded content;
- provenance kind and bounded source reference when present;
- optional confidence;
- enough lifecycle/source information to prove the record was eligible when projected.

Do not expose raw database rows or storage-specific identifiers beyond the canonical typed memory identity.

## Deterministic selection and bounds

Memory retrieval and projection must be explicitly bounded and deterministic.

Define and enforce:

- a per-memory content/text bound suitable for Controller context;
- a maximum count per memory kind;
- a maximum total memory count;
- a maximum serialized memory-projection size;
- continued enforcement of the existing overall `ControllerStatePacket` serialized-size limit;
- stable deterministic ordering before truncation;
- stable deterministic truncation when eligible records exceed bounds.

Selection must not depend on model inference, embeddings, vector similarity, fuzzy scoring, nondeterministic ranking, hash iteration order, wall-clock randomness, or external workers.

Prefer structured filters and stable repository-backed ordering using existing memory metadata. If a new deterministic ordering key is required, keep it explicit and testable.

## Context integration

Integrate the bounded memory projection into the existing Controller state construction path so all Controller capabilities that consume the canonical state packet can receive the same memory context without bespoke per-capability retrieval logic.

The integration must preserve compatibility when no relevant active memory exists: Controller state construction and existing recommendation/recovery/planning flows must continue to behave as before apart from the additional empty memory field/projection.

Do not duplicate memory retrieval independently across normal recommendation, recovery, planning, Plan review, Plan revision, or intake paths.

## Application boundary

Memory access for Controller context must remain read-only and go through Orc's canonical application/kernel memory seam.

The local inference runtime must receive only the bounded Controller projection. It must not gain a `Database`, `MemoryService`, registry connection, or any direct persistence capability.

No model may request or mutate additional memory as part of M06-002.

## Constraints

- Preserve M06-001 storage authority and migration behavior.
- Preserve exact cross-project isolation for Project/Episodic memory.
- Preserve cross-project visibility for User/Experience memory.
- Preserve existing Controller packet validation and overall serialized-size bound.
- Preserve deterministic task/Plan/workflow/lifecycle authority.
- No memory writes from Controller inference.
- No autonomous memory capture.
- No memory consolidation.
- No semantic/vector retrieval.
- No embeddings.
- No inference-based ranking or deduplication.
- No direct SQLite access from Controller/runtime code.
- No model/runtime-specific memory domain types.
- No Qwen/GGUF/llama.cpp-specific retrieval behavior.
- No Python.

## Non-goals

- Creating or correcting memories from Controller output.
- Automatic memory capture from task/Plan/review events.
- Memory consolidation or deduplication.
- Semantic search, embeddings, or vector databases.
- Learned relevance ranking.
- Interactive CLI/TUI/GUI memory management.
- Training/fine-tuning or experience dataset generation.
- Expanding the overall Controller architecture beyond the smallest read-only retrieval seam.

## Acceptance criteria

1. The canonical Controller state packet contains a typed, bounded, model-independent memory projection built through the M06-001 memory API.
2. Only active eligible memories are projected; removed and superseded records are excluded from normal Controller context.
3. Project/Episodic retrieval is strictly bound to the current project, while User/Experience retrieval uses the shared global authority without cross-project leakage.
4. Projected records retain stable memory identity, kind, scope, provenance, optional confidence, and bounded subject/content sufficient for the Controller to distinguish source and authority.
5. Selection order and truncation are deterministic and covered by explicit per-item, per-kind, total-count, memory-payload-size, and existing overall packet-size bounds.
6. Current project/task/Plan facts remain authoritative; durable User memory and historical Episodic/Experience memory cannot overwrite or masquerade as stronger current-state authority in the typed Controller projection.
7. Retrieval is read-only and causes no memory lifecycle, timestamp, history, or persistence mutation.
8. Existing Controller flows remain compatible when no relevant memory exists, and all canonical Controller capabilities reuse the same memory projection rather than implementing separate retrieval paths.

## Required validation

- Focused Controller memory-projection tests.
- Exact project isolation test with multiple projects sharing one global authority.
- Global User/Experience visibility test across projects.
- Removed/superseded exclusion tests.
- Deterministic ordering and truncation tests with more eligible records than every configured count bound.
- Per-item and serialized memory-projection bound tests.
- Existing overall `ControllerStatePacket` bound/validation tests including memory payload.
- Provenance/identity/confidence preservation tests.
- Precedence/authority representation tests proving historical/global memory cannot be represented as current canonical project/task truth.
- No-memory compatibility regression tests for existing Controller state/recommendation flows.
- Read-only retrieval test proving no durable memory fields/history change after repeated projection.
- `cargo test --lib`.
- `cargo test --features llama-cpp --lib`.
- relevant integration suite(s) for Controller/application/memory behavior.
- `cargo fmt --check`.
- normal and feature `cargo clippy --all-targets -- -D warnings`.
- `git diff --check`.

A real Qwen evaluation is required only if this task changes prompt/schema semantics in a way that can affect structured Controller decisions. If implementation can add the typed memory projection without changing evaluated inference semantics, report why deterministic validation is sufficient rather than adding an unrelated model benchmark.
