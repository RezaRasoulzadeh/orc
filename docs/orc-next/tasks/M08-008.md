# M08-008 — Add explicit typed curation for Controller memory capture judgment

**Status:** Planned
**Milestone:** M08 — Experience dataset

## Objective

Add one capability-local curation adapter for an already-produced Controller memory-capture judgment, projecting the existing typed `ControllerMemoryCaptureInput` and canonical `ControllerMemoryCaptureResult` into one M08-001 experience example under explicit trusted verification metadata.

This task continues the narrow M08 adapter pattern at the next clean typed reasoning boundary. It must curate the Controller's capture judgment itself, not the later supervised mutation proposal/grant/execution outcome.

## Repository-grounded context

`src/controller_memory_capture.rs` already provides a bounded read-only reasoning boundary:

- `ControllerMemoryCaptureInput` contains one exact explicit `ControllerMemoryCaptureRequest` plus bounded advisory `ControllerMemoryContext` and exposes public `validate()`;
- the request contains one explicit `ControllerMemoryCaptureCandidate`, whose canonical `MemoryDraft` and bounded `source_facts` are caller-supplied authority;
- `ControllerMemoryCaptureResult` has exactly two outcomes: `Ignore` or `ProposeMutation { intent }`;
- production `ControllerMemoryCaptureResult::validate(candidate)` validates the mutation intent and requires any proposed create intent to preserve the supplied candidate draft exactly;
- capture inference is read-only; mutation proposal legality, grants, durable memory mutation, and composed-step execution happen later through separate deterministic/supervised boundaries.

M08-001 remains the sole durable experience-record format. M08-002 through M08-007 established capability-local adapters over existing typed production inference contracts.

## Scope

Add one memory-capture-specific typed curation request and the smallest `OrcApp` API needed to persist one explicitly verified memory-capture judgment example.

The request must accept:

- one existing `ControllerMemoryCaptureInput`;
- one observed `ControllerMemoryCaptureResult`;
- one explicit accepted/expected `ControllerMemoryCaptureResult`;
- explicit `ControllerExperienceVerificationBasis`;
- explicit M08 outcome and quality metadata;
- M08 provenance through the existing M08-001 type;
- correction metadata only when observed and accepted canonical outputs differ.

Do not accept a caller-controlled capability identifier.

## Canonical capability

Use fixed code-owned capability identifier:

`controller.memory_capture`

The caller must not be able to override it.

## Canonical input projection

The exact supplied `ControllerMemoryCaptureInput` is the dataset input authority.

Before projection:

- call existing production `ControllerMemoryCaptureInput::validate()`;
- serialize the exact typed input deterministically;
- preserve the exact candidate draft, source facts, request packet, and bounded memory context;
- do not rebuild, summarize, reorder, enrich, truncate, or reinterpret the candidate or memory context;
- do not read current memory storage to replace the supplied input with newer records;
- do not derive a candidate from workflow/task/log state.

No memory-capture inference call is permitted in the curation adapter.

## Canonical output projection

The existing `ControllerMemoryCaptureResult` is the dataset output authority.

Observed and accepted values must both pass existing production validation against the exact supplied candidate:

`ControllerMemoryCaptureResult::validate(&input.current_request.candidate)`

Persist the exact accepted result JSON as M08 `accepted_output`.

For `Ignore`, preserve exactly the canonical ignore result.

For `ProposeMutation`, preserve the complete canonical `ControllerMemoryMutationIntent`. Production validation must remain authoritative that the only valid capture proposal is a create intent whose `MemoryDraft` exactly equals the supplied candidate draft.

Do not replace the result with:

- a later mutation proposal validation result;
- a capture grant decision;
- a `ControllerMemoryCaptureStepResult`;
- a durable `MemoryRecord` created later;
- a mutation execution result;
- free-form explanation.

## Mutation boundary

The Controller capture result is advisory judgment only.

M08-008 must not:

- execute or authorize a memory mutation;
- call the capture grant path;
- call the composed capture-step path;
- read a later durable memory record to redefine the accepted output;
- treat successful mutation as proof that the original capture judgment was correct;
- treat rejection/failure downstream as proof that the original judgment was wrong.

M08-001 provenance remains explicit metadata and must not be synthesized from later mutation state.

## Correction semantics

Compare exact canonical serialized observed and accepted `ControllerMemoryCaptureResult` values after validating both against the same exact supplied candidate.

If observed == accepted:

- correction metadata must be absent;
- outcome must satisfy valid non-correction M08-001 semantics;
- no correction evidence is manufactured.

If observed != accepted:

- outcome must be `Corrected`;
- explicit valid correction metadata is required;
- `correction.original_output` must exactly equal the canonical observed `ControllerMemoryCaptureResult` JSON;
- M08 `accepted_output` must exactly equal the canonical accepted result JSON.

A correction may change `Ignore` to `ProposeMutation` or vice versa only through the explicit accepted typed result. A corrected proposed mutation must still pass the same production candidate-backed validation.

Do not infer a correction because mutation proposal validation, grant authorization, execution, later maintenance, or downstream task/workflow outcomes differed.

## Verification boundary

Verification remains explicit and caller-owned.

Do not automatically treat any of these as sufficient verification or correction evidence:

- successful mutation-proposal validation;
- capture grant issuance;
- successful durable memory creation;
- later retrieval of the memory;
- later maintenance/supersession/removal;
- workflow/task success;
- absence of downstream errors.

These are downstream facts, not automatic labels for the reasoning example.

## Production order

1. validate exact `ControllerMemoryCaptureInput`;
2. validate observed `ControllerMemoryCaptureResult` against the exact supplied candidate;
3. validate accepted `ControllerMemoryCaptureResult` against the exact supplied candidate;
4. deterministically project exact input/observed/accepted JSON;
5. enforce correction semantics;
6. construct exactly one `ControllerExperienceExampleDraft` with fixed capability;
7. delegate verification/outcome/quality/provenance/bounds validation to M08-001;
8. persist only through existing `OrcApp::create_controller_experience_example(...)`.

At most one row may be written per call. Any validation/projection failure must write zero rows.

## Acceptance criteria

1. One explicit application API persists one verified Controller memory-capture interaction as one M08-001 example.
2. Capability is fixed as `controller.memory_capture` and not caller-controlled.
3. Dataset input is the exact validated `ControllerMemoryCaptureInput` projection.
4. Dataset accepted output is the exact validated `ControllerMemoryCaptureResult` projection.
5. Observed and accepted results reuse production candidate-backed validation.
6. `ProposeMutation` can only curate the exact candidate-backed create intent already allowed by production validation.
7. Equal/differing output correction semantics are exact.
8. Invalid/mismatched/unbounded data writes zero rows.
9. Success writes exactly one row through M08-001 only.
10. No capture inference/mutation/grant/execution/runtime-memory behavior changes.
