# M05-006 — Add read-only Controller Plan revision generation

**Status:** Planned
**Milestone:** M05 — Planning and Lead unification

## Objective

Generate a revised Plan through the local Controller from a current Controller-origin Plan whose latest actionable Controller-origin Plan review requires revision, while keeping generation strictly read-only.

This task migrates semantic Plan revision generation away from the legacy Planner. It does not persist, supersede, approve, apply, or otherwise mutate the Plan graph.

## Required path

```text
current Controller-origin Plan
        +
latest actionable Controller REVISE review
        ↓
bounded Controller revision request
        ↓
LocalInferenceRuntime
        ↓
validated revised PlanResponse
        ↓
no mutation
```

## Scope

- Inspect legacy `run_pending_plan_revision_with_backend`, M05-001 Controller planning, M05-004 review inference, M05-005 review provenance/persistence, Plan version/supersession rules, `store_plan_revision`, and relevant workflow/storage tests before editing.
- Define a bounded, model-independent Controller Plan revision request/state containing only the canonical current Plan, the latest actionable Controller-origin `RevisePlan` review feedback, and bounded project/planning context needed to revise it.
- Add deterministic pre-inference eligibility checks: Plan exists, belongs to the current project, is current, has Controller origin, and has a latest unsuperseded Controller-origin review whose decision is `RevisePlan` and whose state is still actionable for that Plan.
- Reject approve/user-decision reviews, stale/superseded reviews, legacy Lead-origin review lineage, stale/non-current Plans, and inconsistent state before inference.
- Reuse the canonical `PlanResponse` validation rules for the revised proposal. Do not weaken planning validation for revision output.
- Add a dedicated read-only Controller revision builder/service over `LocalInferenceRuntime`, following existing structured-output boundaries.
- Add an `OrcApp` read-only entry point that constructs the trusted bounded state and invokes Controller revision generation.
- Return a typed bounded revision result carrying the validated revised `PlanResponse` plus only the canonical parent/review identity needed by a later persistence task.
- Add deterministic fake-runtime tests for successful revision generation, invalid output, wrong review decision, legacy review rejection, stale/superseded review rejection, stale/non-current Plan rejection, bounded input construction, and proof of no mutation.
- Add an ignored real-model evaluation covering representative revision scenarios because this task introduces production Controller revision-generation inference semantics.

## Preserve

- Canonical `PlanResponse` validation.
- Existing Controller planning/review prompt boundaries except where a dedicated revision prompt/schema is required.
- M05-002 Plan provenance semantics.
- M05-005 Plan-review provenance and status semantics.
- Existing legacy Planner revision path and workflow compatibility.
- Existing Plan revision persistence/version/supersession semantics; they are not invoked by this task.
- Existing approved-plan application/task creation behavior.

## Constraints

- Strictly read-only: do not call `store_plan_revision`, `store_controller_plan`, review persistence, approval/application, or task creation.
- Do not supersede the parent Plan or consume/supersede its review.
- Do not fabricate Lead decisions, Lead runs, or Planner runs.
- Do not invoke the legacy Planner backend from the Controller revision path.
- Revision feedback must come from canonical persisted Controller review state, not arbitrary model-supplied lineage/provenance.
- Model output cannot choose parent Plan ID, review ID, provenance, authorization, or persistence metadata.
- The revised `PlanResponse` must pass canonical deterministic validation before being returned as a valid result.
- Do not automatically persist or continue the workflow after generation.
- Do not remove legacy Lead/Planner machinery.
- No autonomous planning/revision loop.
- No Qwen-specific core/domain behavior.
- No Python.

## Non-goals

- Persisting Controller Plan revisions.
- Superseding Plan versions/reviews.
- Plan approval/application.
- Task creation.
- Removing legacy Planner revision support.
- General Lead/Planner removal.
- DIRECT_TASKS migration.
- General user-decision routing migration.
- Memory/autonomy/UI work.

## Acceptance criteria

1. A current Controller-origin Plan with a latest actionable Controller-origin `RevisePlan` review can produce a bounded Controller revision request without mutation.
2. Eligibility is rejected deterministically before inference for missing/stale/non-current Plans, legacy-origin Plans/reviews, non-revise decisions, stale/superseded reviews, or inconsistent state.
3. The model receives canonical Plan content and bounded persisted revision feedback but cannot supply or alter trusted parent/review/provenance identity.
4. Successful inference returns a revised `PlanResponse` that passes canonical deterministic validation.
5. Invalid/unrecognized model output fails closed without mutation.
6. Successful generation does not persist/supersede a Plan or review, create Lead/Planner lineage, create tasks, approve/apply anything, or continue workflow execution.
7. Existing legacy Planner revision behavior remains unchanged.
8. Fake-runtime tests cover eligibility, success/failure, bounded state, and no mutation; real-model revision evaluation satisfies the structured contract and expected semantic revision behavior.
