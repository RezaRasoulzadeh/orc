# M04-004 — Route validation-repair exhaustion into supervised Controller recovery

**Status:** Planned
**Milestone:** M04 — Recovery intelligence

## Objective

Replace one concrete rigid recovery dead-end with the supervised M04 Controller recovery boundary: when implementation/revision validation repair is exhausted, preserve deterministic validation truth and existing run/revision evidence, then expose the resulting abnormal state to Controller recovery instead of forcing a blind policy continuation or destroying actionability.

This is the first migration of an existing judgment-heavy recovery policy onto M04-001/002/003. Keep the change narrow: validation-repair exhaustion only.

## Why this task

The repository currently owns deterministic validation correctly, but bounded validation-repair orchestration also embeds judgment about whether another repair/escalation is worthwhile. The Orc Next architecture assigns that judgment to the Controller while the kernel continues to own validation facts, lifecycle legality, lineage, authorization, and mutation.

The migration must prove this architecture on one real failure path before expanding to broader economy/retry policy.

## Required path

```text
implementation or revision
        ↓
deterministic validation fails
        ↓
existing bounded repair attempts
        ↓
repair exhausted
        ↓
persist exact validation/run/revision facts
        ↓
RecoveryInspection
        ↓
RecoveryRecommendation
        ↓
supervised authorization
        ↓
fresh legality + canonical recovery mutation
```

M04-004 does not add an autonomous continuation loop. The operator/application still explicitly invokes and authorizes recovery through the M04-003 boundary.

## Scope

- Inspect the current implementation and revision validation-repair paths and identify the exact point where repair exhaustion is converted into lifecycle/execution/economy state.
- Preserve deterministic validation execution and the existing bounded repair mechanism for the repair attempts themselves in this task; change only what happens after exhaustion.
- Ensure repair exhaustion persists enough canonical facts for M04-001 to classify the abnormal state without relying on free-form logs.
- For revision repair exhaustion, preserve the actionable semantic REVISE lineage/revision contract so `ResumeRevision` can remain legal when canonical rules permit it.
- Ensure generic `Requeue` cannot erase actionable revision lineage.
- For implementation repair exhaustion without revision lineage, preserve the canonical failure state and expose only repository-supported legal recovery operations; do not invent a repair operation.
- Remove/avoid any post-exhaustion automatic policy step that conflicts with supervised Controller recovery, but do not broadly rewrite scheduler/economy policy.
- Keep infrastructure validation failure distinct from semantic validation-repair exhaustion; infrastructure failure must not be mislabeled as repair non-convergence.
- Add deterministic integration tests that drive the real implementation/revision repair-exhaustion paths into M04 recovery observation/legality.

## Required scenarios

1. Revision validation repair exhausts while a current actionable REVISE lineage exists:
   - lineage remains persisted/current;
   - recovery observation identifies the abnormal revision state;
   - `ResumeRevision` is legal when canonical revision rules permit it;
   - generic `Requeue` is rejected because it would discard lineage.
2. Implementation validation repair exhausts with no semantic revision lineage:
   - exact failure/validation evidence remains available;
   - recovery inspection exposes only canonically legal operations;
   - no synthetic semantic revision is created.
3. Infrastructure validation failure:
   - remains classified as infrastructure failure;
   - does not enter semantic repair-non-convergence behavior;
   - Controller recovery cannot manufacture an unsupported repair operation.
4. Economy/quota constraint encountered around repair exhaustion:
   - remains a fact/constraint;
   - M04-004 does not automatically escalate tiers or manufacture an agent;
   - no `economy_escalation_exhausted` policy dead-end may destroy otherwise valid revision actionability.

## Kernel/Controller boundary

Kernel remains authoritative for:
- validation pass/fail/infrastructure truth;
- validation freshness/evidence;
- run state and persisted usage;
- revision/review lineage;
- dependency state;
- agent eligibility/quota facts;
- legal recovery operations;
- authorization and mutation.

Controller owns judgment about what recovery to choose after exhaustion. M04-004 must not encode a new heuristic such as "always resume revision", "always requeue", or "always escalate".

## Constraints

- Reuse M04-001 `RecoveryInspection`, M04-002 recommendation, and M04-003 supervised execution boundaries.
- Do not add new `RecoveryOperation` variants unless repository inspection proves the current three operations cannot represent this migration; if a new operation appears necessary, stop and report instead of adding it.
- Do not change deterministic validation success/failure criteria.
- Do not remove bounded repair attempts themselves in this task unless repository inspection proves they cannot be separated from the post-exhaustion policy; report before broadening scope.
- Do not let the Controller directly execute validation, mutate SQLite, manipulate Git/worktrees, select arbitrary commands, or bypass lifecycle rules.
- Do not add inference→action→inference loops or unattended recovery.
- Do not weaken revision lineage/current-review checks.
- Do not broadly refactor scheduler/economy escalation.
- Do not change M03 normal-action semantics.
- Do not change recovery prompt/schema/parser unless the bounded M04-001 representation is genuinely insufficient; stop and report before such a change.

1. Real implementation/revision validation-repair exhaustion flows terminate in canonical abnormal state that M04-001 can inspect without loss of validation/run evidence.
2. Revision repair exhaustion preserves actionable REVISE lineage and does not make generic requeue the default recovery.

8. Existing successful implementation/revision validation behavior remains unchanged.
