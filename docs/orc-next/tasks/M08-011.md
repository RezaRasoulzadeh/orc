# M08-011 — Add deterministic Controller experience dataset inventory

**Status:** Planned
**Milestone:** M08 — Experience dataset

## Objective

Add one deterministic, read-only inventory view over the persisted M08 Controller experience dataset so Orc can inspect actual curation coverage before any export, splitting, balancing, or M09 specialization work.

The inventory is metadata inspection only. It must not reinterpret examples, infer training readiness, mutate lifecycle, export trainer records, or run Controller inference.

## Repository-grounded context

M08-001 established the canonical persisted `ControllerExperienceExample` substrate in the global registry with typed schema version, capability, verification basis, provenance, correction/outcome/quality metadata, created timestamp, and Active/Retired lifecycle. Existing application APIs already create, get, list, and retire examples.

M08-002 through M08-010 now cover every current inference-backed Controller judgment module with capability-local curation adapters:

- `controller.task_recommendation`;
- `controller.recovery_recommendation`;
- `controller.plan_generation`;
- `controller.workflow_intake`;
- `controller.plan_review`;
- `controller.plan_revision`;
- `controller.memory_capture`;
- `controller.memory_maintenance`;
- `controller.memory_selection`.

The next smallest evidence-backed M08 step is therefore deterministic dataset inspection rather than another reasoning adapter. D-006 requires a curated dataset and evaluation suite; D-007 keeps training/export a separate concern and forbids a Python runtime dependency.

## Scope

Add a typed read-only dataset inventory and the smallest `OrcApp` API required to obtain it from the canonical global-registry experience table.

The inventory must report the complete persisted dataset, not a caller-selected page, and must expose only deterministic metadata counts.

## Canonical inventory shape

Add versioned typed inventory structures equivalent to:

- inventory schema version;
- total example count;
- total Active count;
- total Retired count;
- deterministic per-capability summaries sorted lexicographically by exact capability string.

Each per-capability summary must contain exact integer counts for:

- total;
- Active;
- Retired;
- `Accepted`;
- `Corrected`;
- `Rejected`;
- `OperatorAttestation`;
- `ExplicitCorrection`;
- `ExternalEvaluation`.

Do not add percentages, floating-point ratios, scores, recommendations, rankings, readiness labels, or inferred quality classes in this task.

## Data authority

The persisted canonical M08-001 rows are the sole authority.

Inventory construction must:

1. read the complete experience-example metadata set from the global registry through a deterministic storage/application read path;
2. reject malformed/unrecognized persisted enum/schema/capability metadata rather than silently skipping or coercing it;
3. count each persisted row exactly once;
4. sort capability summaries lexicographically by exact capability identifier;
5. verify aggregate invariants before returning the inventory.

The inventory must not use runtime `MemoryKind::Experience`, project-local databases, task/run/review tables, workflow state, logs, filesystem state, or model output.

## Required aggregate invariants

For the whole inventory:

- `total == active + retired`;
- sum of every capability `total` equals global `total`;
- sum of capability Active counts equals global Active count;
- sum of capability Retired counts equals global Retired count.

For every capability:

- `total == active + retired`;
- `total == accepted + corrected + rejected`;
- `total == operator_attestation + explicit_correction + external_evaluation`.

Empty dataset is valid and returns zero totals plus an empty capability list.

## Read boundary

This task is inspection only.

Do not:

- create, retire, update, delete, or relabel examples;
- alter M08-001 validation;
- deserialize or reinterpret capability-specific input/output payloads for counting;
- infer whether an example is good/bad beyond its persisted metadata;
- infer whether a capability has enough data;
- infer dataset balance or training readiness;
- automatically harvest examples;
- call any Controller inference path;
- read runtime memory;
- write files.

## Storage boundary

Prefer a narrow deterministic read-side storage API that reads only metadata needed for inventory. Do not load potentially large input/accepted-output/correction payloads merely to count metadata if the existing storage layer can expose a smaller typed projection.

Any new raw storage projection must remain private to the deterministic storage/application boundary and must map persisted strings/integers into existing typed M08 enums with explicit failure on unknown values.

Do not create a second persistence format or duplicate the canonical experience table.

## API boundary

Expose one explicit read-only `OrcApp` API for the complete inventory.

The caller must not provide arbitrary SQL, grouping expressions, capability aliases, lifecycle rewrites, or trainer/export settings.

No pagination parameter is required for the aggregate inventory.

## Invariants / requirements

- Deterministic read-only metadata inspection only.
- Canonical global-registry M08-001 rows are authoritative.
- Exact persisted capability identifiers are preserved.
- Capability ordering is deterministic and lexicographic.
- Counts are integer and exact.
- Unknown/corrupt persisted schema or enum metadata fails closed.
- Empty dataset is valid.
- No input/output payload reinterpretation.
- No mutation or lifecycle changes.
- No runtime `MemoryKind::Experience` integration.
- No Controller inference.
- No export/trainer format.
- No dataset split/balance/sample/dedup/ranking policy.
- No quality threshold/readiness policy.
- No model-specific behavior.
- No provider fallback or provider token hard cap.
- No embeddings.
- No Python.

## Non-goals

- JSONL/CSV/trainer export.
- Train/validation/test splitting.
- Deduplication.
- Sampling or balancing.
- Capability weighting.
- Quality-score policy.
- Automatic retirement.
- Dataset readiness/pass-fail judgment.
- Fine-tuning.
- Evaluation runner changes.
- Runtime memory changes.
- CLI/TUI/GUI presentation unless strictly required by an existing test boundary.

## Acceptance criteria

1. One explicit `OrcApp` read API returns a typed versioned inventory of the complete canonical Controller experience dataset.
2. Empty dataset returns valid zero totals and no capability summaries.
3. Every persisted row is counted exactly once.
4. Global Active/Retired counts are exact.
5. Per-capability lifecycle counts are exact.
6. Per-capability outcome counts are exact.
7. Per-capability verification-basis counts are exact.
8. Capability summaries are sorted lexicographically by exact capability identifier.
9. All aggregate invariants are checked before return.
10. Malformed/unrecognized persisted metadata fails closed rather than being skipped/coerced.
11. Inspection reads no capability-specific payload semantics and performs no mutation/inference/export/training work.

- empty dataset;
- one Active example;
- one Retired example;
- multiple capabilities in non-sorted insertion order produce lexicographically sorted summaries;
- mixed Active/Retired lifecycle counts;
- mixed Accepted/Corrected/Rejected outcome counts;
- mixed OperatorAttestation/ExplicitCorrection/ExternalEvaluation counts;
- global totals equal capability sums;
- each capability lifecycle sum equals total;
- each capability outcome sum equals total;
- each capability verification sum equals total;
- exact capability strings are preserved;
- examples from all current fixed M08 capability identifiers can be represented without aliasing;
- malformed persisted schema version fails closed where constructible through test-only/raw fixture setup;
- malformed persisted lifecycle value fails closed where constructible;
- malformed persisted outcome value fails closed where constructible;
- malformed persisted verification value fails closed where constructible;
- malformed/empty persisted capability fails closed where constructible;
- inspection performs zero writes;
- repeated inventory reads are identical when storage is unchanged;
- retiring one example changes only the expected lifecycle counts and not total/outcome/verification counts;
- M08-001 through M08-010 regressions;
- relevant global-registry reopen/persistence regressions;
- runtime `MemoryKind::Experience` regressions;
- `cargo test --lib`;

- `git diff --check`.

No real-Qwen evaluation is required because this task must not change any inference prompt, schema, parser, runtime request, or decision semantics.
