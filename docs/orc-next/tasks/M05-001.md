# M05-001 — Add read-only Controller planning capability

**Status:** Planned
**Milestone:** M05 — Planning and Lead unification

## Objective

Move the first concrete Planner judgment path into the local Controller by adding a bounded, read-only Controller planning capability that turns an existing canonical planning request into a typed plan recommendation, without applying tasks, consuming Lead decisions, mutating plan state, or deleting the current Planner/Lead machinery.

This task establishes the Controller-side planning seam before any legacy Planner or Lead removal.

## Repository-grounded context

Current planning is split across durable domain/application data and separate intelligent-role machinery:

- `PlanningRequest` / `PlanResponse` are existing protocol-level planning artifacts.
- `OrcApp::automated_plan_with_backend` invokes the current automated Planner path.
- persisted plans retain `source_lead_decision_id` and `source_planner_run_id` lineage.
- `LeadDecisionKind::PlanRequired` and `WorkflowStage::Planner` currently route Lead judgment into Planner execution.
- existing CLI/application APIs expose planning and Lead as separate operator flows.

M05 target architecture keeps useful Plan/approval data but moves intelligent planning/Lead judgment into Controller capabilities.

## Required path

```text
canonical PlanningRequest / bounded planning facts
                ↓
      Controller planning request
                ↓
        LocalInferenceRuntime
                ↓
    typed Controller plan result
                ↓
      no mutation in M05-001
```

## Scope

- Inspect `PlanningRequest`, `PlanResponse`, planner packet construction, `automated_plan_with_backend`, plan persistence, and Lead→Planner routing before editing.
- Add a small Controller-owned planning request/result boundary using the existing `LocalInferenceRuntime` abstraction.
- Reuse existing canonical planning facts where safe; do not duplicate the whole project report or Planner packet merely to preserve old role boundaries.
- Keep the planning input bounded and model-independent. Qwen, GGUF, llama.cpp, tokenizer, prompt-template, and native backend details must not enter domain/application types.
- Produce a typed structured result representing a proposed plan and bounded rationale/uncertainty as needed for operator review.
- Validate model output deterministically before returning it. Invalid structure, protocol violations, or unsupported content must return typed failure rather than partial application.
- Add fake-runtime deterministic tests for successful planning, malformed output, and bounded-input behavior.
- Add one ignored feature-gated real-model evaluation only if production planning prompt/schema semantics are introduced by this task.

## Preserve

- Existing `PlanResponse`/task-proposal validation rules unless repository inspection proves a Controller-specific wrapper is required.
- Existing persisted Plan records and lineage fields.
- Existing explicit plan application/approval semantics.
- Existing Lead decisions and Planner path during this task; they remain compatibility machinery until a later M05 task migrates their routing.
- `OrcApp` as the canonical mutation boundary.

## Constraints

- Read-only: M05-001 must not persist a plan, create/apply tasks, consume a Lead decision, dispatch work, or mutate workflow state.
- Do not remove `LeadDecisionKind`, `WorkflowStage::Planner`, Planner agent actions, planner CLI commands, or plan persistence yet.
- Do not add a second planning domain model if existing `PlanningRequest` / `PlanResponse` can safely serve as canonical artifacts.
- Do not couple core logic to Qwen or llama.cpp.
- Do not expose SQLite, Git/worktree mutation, shell execution, arbitrary files, credentials, or worker invocation to the Controller.
- Do not add autonomous planning→application loops.
- Do not refactor general workflow/Lead machinery beyond the minimum seam needed for this read-only capability.
- No Python.

## Non-goals

- Replacing/removing Lead.
- Replacing/removing the legacy Planner path.
- Automatic plan persistence or application.
- Applying `DIRECT_TASKS` through Controller.
- Plan revision migration.
- User-decision routing migration.
- Workflow-engine rewrite.
- Memory.
- Autonomous mode.
- CLI/TUI/GUI redesign.
- Model replacement or GPU optimization.

## Dependencies

- M01 native runtime complete.
- M02 reliable structured Controller output complete.
- M03/M04 Controller/kernel authorization and legality boundaries remain intact.

## Acceptance criteria

1. Orc exposes a read-only Controller planning API that accepts bounded canonical planning input and returns a typed proposed plan result through `LocalInferenceRuntime`.
2. Controller/domain/application planning types contain no Qwen/GGUF/llama.cpp/backend-specific details.
3. Invalid or schema-incompatible model output is rejected deterministically and cannot mutate Orc state.
4. Successful Controller planning performs no DB, task, workflow, Lead-decision, Git, or worker mutation.
5. Existing plan persistence/application semantics and current Lead→Planner workflow remain behaviorally unchanged.
6. Deterministic fake-runtime tests cover success, invalid structured output, and bounded-input behavior.
7. Existing planning/Lead/storage/workflow tests continue to pass.
8. If production planning prompt/schema semantics are new, an opt-in real local-model evaluation is run and reported separately from normal tests.

## Required validation

- Focused Controller planning tests with fake runtime.
- Existing planner/app API tests.
- Existing Lead tests.
- Existing workflow-engine tests.
- Existing storage/plan persistence tests.
- `cargo test --lib`.
