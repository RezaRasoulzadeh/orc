# M05-003 — Persist Controller Plan proposals through explicit authorization

**Status:** Planned
**Milestone:** M05 — Planning and Lead unification

## Objective

Connect a validated M05-001 Controller plan result to the M05-002 canonical Controller-origin Plan storage seam through explicit trusted one-shot authorization.

This task migrates Controller proposal persistence only. Plan review judgment, revision judgment, approval, and application remain existing explicit mechanisms.

## Required path

```text
validated ControllerPlanResult
            ↓
 typed persistence proposal
            ↓
 trusted one-shot authorization
            ↓
 fresh deterministic validation
            ↓
 Database::store_controller_plan
            ↓
 canonical Controller-origin Proposed Plan
```

## Scope

- Inspect M05-001 Controller planning types/API, M05-002 `PlanOrigin`/`PlanProvenance` and `Database::store_controller_plan`, and M03/M04 authorization patterns before editing.
- Add a narrow typed Controller Plan persistence intent/proposal containing only the canonical data needed to persist the validated proposed plan.
- Add an opaque trusted one-shot authorization token. It must not be serializable, cloneable, constructible from model output, rationale, confidence, or arbitrary caller-supplied provenance.
- Add an `OrcApp` authorization entry point and an authorized execution entry point following existing trusted Controller mutation patterns.
- Bind authorization to the exact proposal/plan identity or deterministic content identity needed to prevent substitution between authorization and execution.
- Immediately before mutation, verify authorization matches the proposal and freshly run canonical deterministic `PlanResponse` validation.
- Persist exclusively through `Database::store_controller_plan` or the smallest canonical `OrcApp` wrapper around it; do not duplicate Plan SQL/provenance logic.
- Return a bounded typed execution result with the persisted Plan ID, status, and Controller provenance/origin.
- Ensure successful execution persists exactly one Controller-origin `Proposed` Plan and performs no other lifecycle action.
- Add deterministic tests for proposal creation, authorization matching, one-shot consumption, substitution/mismatch rejection, invalid/stale plan rejection, successful persistence, and absence of side effects.

## Preserve

- M05-001 inference prompt/schema/parser semantics.
- M05-002 Plan origin/provenance and migration semantics.
- Canonical `PlanResponse` validation.
- Existing plan-review behavior.
- Existing legacy Lead/Planner proposal/revision behavior.
- Existing approved-plan application/task creation behavior.
- `OrcApp`/Database as trusted deterministic mutation boundaries.

## Constraints

- Controller output/recommendation is never authorization.
- Authorization must be opaque, trusted, one-shot, and consumed by execution.
- Do not accept model-supplied provenance or authorization fields.
- Do not fabricate or consume Lead decisions.
- Do not fabricate or invoke Planner runs.
- Do not create tasks.
- Do not approve or apply the Plan.
- Do not automatically invoke plan review.
- Do not migrate plan-review judgment or plan revision in this task.
- Do not remove Lead/Planner roles, commands, workflow stages, or tables.
- Do not broaden `Database::store_controller_plan` semantics unless a concrete invariant defect is found; stop and report before doing so.
- No autonomous planning loop.
- No Qwen-specific behavior.
- No Python.

## Non-goals

- Controller plan review.
- Controller plan revision.
- Controller approval/application.
- Removing legacy Planner/Lead machinery.
- DIRECT_TASKS migration.
- User-decision routing migration.
- Workflow-engine rewrite.
- Memory/autonomy/UI work.

## Dependencies

- M05-001 complete: read-only validated Controller planning.
- M05-002 complete: truthful Controller-compatible Plan provenance and `Database::store_controller_plan`.
- M03/M04 authorization patterns available as precedent.

## Acceptance criteria

1. A validated `ControllerPlanResult` can produce a typed persistence proposal without mutation.
2. Persistence requires an explicit trusted opaque one-shot authorization that cannot originate from model output.
3. Authorization is bound tightly enough to reject proposal substitution/mismatch before mutation.
4. Execution freshly validates the canonical `PlanResponse` immediately before persistence.
5. Successful execution persists exactly one Controller-origin `Proposed` Plan through the canonical M05-002 storage seam.
6. Successful execution consumes/fabricates no Lead decision, invokes/fabricates no Planner run, creates no task, performs no review, and does not approve/apply the Plan.
7. Invalid proposal, invalid plan, authorization mismatch, or reused authorization fails without Plan/task/workflow/Lead/worker mutation.
8. Existing legacy planning, plan review, workflow, storage, and approved-plan application behavior remains unchanged.
