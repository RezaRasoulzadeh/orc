# M06-008 — Integrate bounded memory into Controller Plan revision

**Status:** Planned
**Milestone:** M06 — Persistent memory

## Objective

Feed reusable M06-002 `ControllerMemoryContext` into the existing read-only Controller Plan-revision generation capability without changing canonical revision eligibility, persisted review feedback authority, Plan schema, lineage attachment, revision persistence, authorization, or workflow semantics.

## Repository-grounded context

`src/controller_plan_revision.rs` already defines the next distinct read-only Controller seam:

- `ControllerPlanRevisionRequest` contains the current Plan content, persisted actionable revision feedback, and bounded `ControllerPlanningRequest` context;
- `OrcApp::revise_controller_plan` deterministically verifies active project, Controller Plan origin/current revision state, latest actionable Controller review, and persisted revision feedback before inference;
- parent Plan ID/version and review ID are intentionally excluded from model input and attached from canonical state after inference;
- `ControllerPlanRevisionBuilder::revise` returns only canonical `PlanResponse`;
- revision persistence, lineage, authorization, workflow transitions, application, and task mutation remain downstream kernel-owned boundaries;
- the existing revision request is bounded to 64 KiB.

Use this seam directly. Do not redesign planning, Plan review, intake, recovery, normal recommendation, persistence, authorization, or workflow routing.

## Scope

Integrate memory into Plan-revision generation only.

Required behavior:

- introduce a capability-local revision inference input containing the existing `ControllerPlanRevisionRequest` plus typed `ControllerMemoryContext`, preserving the request as current revision authority;
- `OrcApp::revise_controller_plan` retrieves memory only through `controller_memory_context()` after existing deterministic eligibility/review checks;
- preserve direct builder/evaluation compatibility through explicit empty memory;
- preserve typed memory identity/kind/scope/authority/provenance metadata;
- preserve independent existing revision-request validation and M06-002 memory validation;
- add an explicit deterministic 64 KiB combined revision inference-input bound and reject oversized input before inference;
- empty memory remains valid;
- retrieval/inference remains read-only.

## Authority and precedence

```text
current persisted Plan content and actionable persisted revision feedback
→ current bounded planning/project facts
→ durable Project memory
→ durable User memory
→ Episodic project history
→ cross-project Experience memory
→ base model tendencies
```

The current Plan and persisted revision feedback are authoritative. Current planning/project facts outrank contradictory memory. Memory may help produce a better compliant revision but cannot rewrite the revision request, remove applicable persisted feedback, choose lineage, persist/approve/apply a Plan, authorize actions, or mutate workflow state.

## Invariants / requirements

- Reuse `ControllerMemoryContext`; no revision-specific persistence model.
- Keep `ControllerPlanRevisionRequest` distinct and authoritative; do not create a universal Controller request.
- Existing deterministic eligibility, origin/current-Plan, latest-review, and actionable-feedback checks remain before inference.
- Model output remains exactly canonical `PlanResponse`; parent Plan ID/version and review ID remain attached from trusted canonical state after inference.
- Existing request validation and independent memory validation remain enforced; combined input is bounded to 64 KiB before inference.
- Revision persistence, lineage, authorization, workflow transitions, approval/application, task mutation, and worker execution remain unchanged.
- No memory writes/capture/correction/removal/consolidation.
- No semantic/vector retrieval, embeddings, learned ranking, or model-based memory selection.
- No model-specific domain behavior.
- No Python.

## Non-goals

- Changing revision eligibility or persisted review semantics.
- Changing Plan review/generation/intake/recovery/normal recommendation integrations.
- Changing PlanResponse schema or durable revision lineage.
- Automatically recording revisions as memories.
- Consolidation/deduplication or semantic retrieval.

## Acceptance criteria

1. `OrcApp::revise_controller_plan` supplies canonical bounded memory only after existing deterministic revision eligibility checks.
2. Revision inference preserves typed memory metadata while `ControllerPlanRevisionRequest` remains authoritative.
3. Current Plan, persisted revision feedback, and current planning/project facts outrank contradictory memory.
4. Model output remains canonical `PlanResponse`; trusted lineage IDs remain outside model authority and are attached after inference.
5. Existing request validation and independent memory validation remain enforced; combined input is bounded to 64 KiB before inference.
6. Empty-memory direct/evaluation behavior remains compatible.
7. Revision persistence, authorization, workflow, approval/application, and task/worker semantics remain unchanged.
8. Retrieval/inference causes no durable memory mutation and no unrelated Controller capability is redesigned.

- typed authority/provenance serialization;
- prompt capture proving current Plan + persisted revision feedback + current planning facts outrank memory;
- regression proving contradictory memory cannot suppress applicable persisted feedback or alter lineage authority;
- regression proving output remains canonical `PlanResponse` and trusted lineage attachment remains unchanged;
