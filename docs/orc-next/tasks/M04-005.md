# M04-005 — Route semantic revision non-convergence into supervised Controller recovery

**Status:** Planned
**Milestone:** M04 — Recovery intelligence

## Objective

Migrate the next concrete judgment-heavy recovery policy: when a semantic blocker survives a completed revision, preserve the canonical review/revision/run/economy facts and expose the abnormal state to the supervised M04 Controller recovery boundary instead of automatically invoking semantic-revision economy escalation.

Keep the change narrow to semantic revision non-convergence and its immediate post-review policy.

## Why this task

The current repository can detect the factual condition that a semantic blocker survived a completed revision, but the subsequent choice to escalate provider/model tier is judgment. Orc Next assigns that choice to the Controller while the deterministic kernel retains review truth, revision lineage, lifecycle legality, economy/quota facts, authorization, and mutation.

M04-004 proved this separation for validation-repair exhaustion. M04-005 applies the same principle to semantic revision non-convergence.

## Scope

- Inspect the exact review/revision path that detects `SemanticRevisionNonConvergence` and the call to the current escalation policy.
- Preserve the factual detection of repeated/surviving semantic blockers and all current review/revision lineage needed to understand the condition.
- Preserve current review verdict, revision contract/currentness, run evidence, validation evidence, and bounded economy/quota/eligibility facts.
- Remove or bypass only the automatic post-detection economy escalation decision where it conflicts with supervised Controller recovery.
- Persist a canonical abnormal state that M04-001 can inspect without relying on free-form logs or a pending escalation request.
- Ensure the resulting recovery legality does not silently requeue away valid semantic revision evidence.
- Keep exact non-convergence acknowledgement semantics distinct from ordinary semantic revision non-convergence; do not repurpose `AcknowledgeNonConvergence` unless the canonical execution condition is exactly the state that operation already represents.
- Add integration tests through the real semantic review/revision path.

## Required scenarios

1. A semantic REVISE blocker survives a completed revision:
   - repeated/non-convergent semantic evidence remains persisted and current;
   - task enters a bounded canonical abnormal state inspectable by M04-001;
   - no automatic economy escalation request is required to represent the condition;
   - M04-001 exposes only canonically legal recovery operations.
2. Valid actionable revision lineage exists after the non-convergent review:
   - generic `Requeue` cannot discard it;
   - `ResumeRevision` is legal only if existing canonical revision rules permit it.
3. Economy/quota/eligible-agent facts around semantic non-convergence:
   - remain observable facts;
   - no automatic stronger-tier/model escalation occurs;
   - absence/exhaustion of an escalation target does not replace or erase the semantic evidence.
4. Ordinary first-time REVISE review:
   - remains normal `RevisionRequired` behavior;
   - is not incorrectly classified as semantic non-convergence.
5. PASS review and acceptance-ready behavior remain unchanged.
6. Exact `NonConvergenceReplanRequired` behavior remains unchanged unless repository inspection proves this path is the same canonical state; if so, stop and report before changing semantics.

## Kernel/Controller boundary

Kernel remains authoritative for:
- review verdict/currentness;
- criterion/findings evidence;
- revision contracts and lineage;
- validation evidence/freshness;
- lifecycle/queue state;
- repeated-blocker/non-convergence factual detection;
- agent eligibility, quota and economy observations;
- legal recovery operations;
- authorization and canonical mutation.

Controller owns judgment about whether another revision, operator decision, or other already-legal recovery is worthwhile. Do not replace automatic escalation with another automatic choice.

## Constraints

- Reuse M04-001 recovery observation/legality, M04-002 recommendation, and M04-003 supervised execution.
- Do not add a new `RecoveryOperation` unless repository inspection proves the existing set cannot safely represent the canonical state; stop and report before adding one.
- Do not weaken semantic review evidence/currentness or revision-contract consumption rules.
- Do not fabricate revision lineage.
- Do not broaden into general scheduler/economy redesign.
- Do not remove economy/quota/eligibility observations; remove only automatic judgment where appropriate.
- Do not change validation-repair behavior from M04-004.
- Do not add autonomous recovery or inference→action→inference loops.
- Do not change M03 normal-action semantics.
- Do not change recovery prompt/schema/parser unless M04-001 lacks a necessary bounded factual distinction; stop and report before such a change.

## Non-goals

- General economy-policy removal.
- Worker/model/tier selection by Controller.
- Automatic retry or escalation.
- Validation repair changes.
- Dependency/infrastructure repair.
- Planning/Lead migration.
- Memory.
- Autonomous mode.
- CLI/TUI/desktop UX.
- Model replacement, GPU work, or Python.

6. M04-001 remains the sole deterministic recovery-legality source and M04-002/M04-003 remain the only Controller recommendation/supervised execution path.
7. No new recovery-choice heuristic, automatic continuation loop, or broad scheduler/economy refactor is introduced.
