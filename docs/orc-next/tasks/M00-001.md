# M00-001 — Map current Orc into kernel, policy and interface surfaces

**Status:** Done  
**Milestone:** M00 — Architecture and repository mapping

## Objective

Inspect the current repository and produce a repository-grounded map showing which existing modules/APIs belong to the deterministic kernel, which encode engineering judgment/policy that should eventually move to the local Controller, which are interface adapters, and which old Lead/Planner/recovery concepts may become migration/removal candidates.

## Why

Orc already contains substantial shared infrastructure. The new architecture must evolve it rather than duplicate or rewrite it. We need concrete seams before introducing the Controller.

## Scope

Inspect at minimum:
- `src/main.rs` and CLI orchestration;
- `src/app.rs` / application operations;
- task/lifecycle/scheduler/workflow modules;
- automated review/revision flow;
- validation and validation-repair orchestration;
- economy/model-resolution logic;
- Lead and planning modules/persistence;
- storage/transactions;
- agent registry/permissions/quota;
- TUI/desktop adapters where they reveal shared API boundaries;
- relevant deterministic tests that document intended behavior.

Produce a map that identifies:
1. deterministic kernel surfaces to preserve;
2. engineering judgment/policy surfaces to migrate;
3. reusable application APIs suitable for future Controller tools;
4. Lead/Planner persisted data worth preserving;
5. Lead/Planner role/handoff machinery likely to become obsolete;
6. lifecycle invariants versus recovery policy;
7. economy hard constraints versus escalation judgment;
8. validation facts versus repair/retry judgment;
9. likely read-only Controller state packet sources;
10. smallest safe integration seam for M01/M02.

## Non-goals

- Do not implement local inference.
- Do not add Controller mutations.
- Do not delete or rewrite Lead/Planner.
- Do not redesign the database speculatively.
- Do not change task lifecycle behavior.
- Do not add TUI/GUI features.
- Do not create a broad shared-core extraction merely because interfaces are separate.

## Dependencies

None.

## Acceptance criteria

1. Every major orchestration subsystem is classified as kernel, judgment/policy, interface, or migration candidate.
2. Existing reusable `OrcApp` / `ProjectOperations` seams are named concretely.
3. Lead/Planner durable data is separated from old intelligent-role/handoff machinery.
4. Lifecycle invariants are separated from abnormal recovery policy.
5. Validation execution/evidence is separated from retry/repair judgment.
6. Economy hard constraints are separated from model-escalation judgment.
7. A concrete bounded read-only Controller state packet is proposed using existing data sources.
8. A minimal integration seam for the next milestone is proposed without requiring a rewrite.

## Required evidence

This is primarily a repository-reading/design task. Evidence must cite concrete files, types/functions and relevant tests. No implementation validation suite is required unless code is changed unexpectedly.

## Result

Completed in `docs/orc-next/M00-REPOSITORY-MAP.md`.

Key result: Orc already has suitable seams for an incremental Controller integration. `ProjectOperations` is the provider-independent observation boundary and `OrcApp` is the canonical application/mutation boundary. M01/M02 can therefore introduce a native model runtime and read-only Controller state/recommendation path without rewriting lifecycle/storage or exposing the database directly to the model.

The map also identifies Lead/Planner role machinery, abnormal recovery choice, validation-repair retry choice and economy escalation choice as judgment-heavy migration targets while preserving their durable facts, evidence and hard constraints.
