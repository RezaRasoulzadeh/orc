# M06-001 — Establish typed persistent memory records and deterministic storage

**Status:** Planned
**Milestone:** M06 — Persistent memory

## Objective

Establish Orc's canonical durable memory data model and deterministic persistence/read surface before any Controller retrieval, autonomous memory writing, semantic search, embeddings, or training behavior.

This task creates inspectable, correctable, removable memory as explicit Orc data. It does not yet put memory into Controller prompts.

## Repository-grounded direction

`ARCHITECTURE.md` defines memory as separate from model weights and distinguishes user, project, episodic, experience, and bounded working memory. Orc already has two durable persistence scopes: the per-project SQLite database used by `OrcApp`/`Database`, and the authoritative global registry used for cross-project reusable state. M06-001 must reuse those canonical persistence seams rather than introduce a third database or model-owned store.

Working memory is bounded current context and is not a durable record type in this task.

## Required storage semantics

- **User memory** is durable and cross-project. Store it in the existing global persistence authority.
- **Experience memory** is durable and cross-project. Store it in the existing global persistence authority.
- **Project memory** is durable and project-scoped. Store it in the project's canonical database and bind it to the exact project identity.
- **Episodic memory** records significant project events/observations and is project-scoped in this milestone. Store it in the project's canonical database and bind it to the exact project identity.
- **Working memory** remains transient/bounded context and must not be persisted through this API.

If the current global registry abstraction cannot safely host non-agent global records without corrupting its authority boundary, stop and report the exact repository constraint before creating a parallel database.

## Typed memory model

Add model-independent typed records with at least:

- stable memory ID;
- memory kind: `User`, `Project`, `Episodic`, `Experience`;
- scope identity that is structurally consistent with the kind;
- bounded structured subject/key or category;
- bounded content/value;
- provenance/source describing where the memory came from;
- created timestamp;
- updated timestamp;
- optional confidence as an Orc fact/annotation, not model authority;
- lifecycle state sufficient to support correction/removal without silently rewriting history;
- optional supersession linkage when a correction replaces a prior memory.

The exact Rust names may differ, but invalid kind/scope combinations must be unrepresentable or rejected deterministically.

## Provenance

Provenance must be explicit and inspectable. Support at least the categories needed to distinguish:

- explicit operator-provided memory;
- deterministic Orc/project fact promoted to memory;
- Controller-proposed memory accepted through a future trusted boundary;
- historical/imported memory where original source is known only as imported data.

Do not add Controller mutation authority in this task. A provenance variant for future Controller-approved memory may exist, but no model may persist memory directly.

Where a source entity exists, provenance should permit bounded source identity/reference such as project/task/plan/workflow/event identifiers without embedding whole transcripts or arbitrary repository dumps.

## Deterministic write/read surface

Add a canonical storage/application surface supporting:

- create one valid memory record;
- get by stable ID;
- list/query by memory kind and effective scope;
- correct/supersede an existing record while retaining historical provenance;
- remove/deactivate a record so it no longer appears in active-memory reads;
- explicitly inspect historical/superseded/removed records when requested by the storage API.

Writes must be transactional and deterministic. Correction/supersession must not leave two simultaneously-active conflicting versions of the same record due to a partial transaction.

Do not implement semantic similarity, ranking, prompt assembly, or fuzzy deduplication here. Queries in M06-001 are structured deterministic filters only.

## Scope and precedence groundwork

Represent enough metadata for later M06 retrieval to enforce the architecture precedence:

```text
current operator instruction
→ current project facts/decisions
→ current task/plan contract
→ durable user preferences
→ historical experience
→ base model tendencies
```

M06-001 does **not** implement this full retrieval precedence. It must simply avoid a schema that would make precedence/scope impossible to enforce later.

Project memory and episodic memory must never leak across project identity through a global query. User and experience memory must remain accessible across projects through the global authority.

## Application boundary

Expose memory through a small canonical Rust API owned by Orc's application/kernel layer, not by the local model runtime and not by CLI/TUI-specific code.

Prefer a narrow `OrcApp`/storage-facing memory service or equivalent canonical seam. Do not let callers manipulate raw SQLite rows as the public memory API.

The API must be usable later by:

- Controller state/retrieval construction;
- CLI inspection/edit/removal;
- TUI/GUI adapters;
- future explicitly authorized Controller memory proposals.

Do not add those consumers in this task.

## Migration and compatibility

- Existing project databases must migrate/reopen successfully.
- Existing global registry databases must migrate/reopen successfully.
- A project database reset must not destroy user/experience memory stored in the global authority.
- Opening another project against the same global authority must expose the same active user/experience memories but not another project's project/episodic memories.
- Existing agent-registry authority and migration behavior must remain unchanged.

## Constraints

- Memory is explicit Orc data, not model weights.
- No model inference is required for CRUD/storage behavior.
- No direct model access to SQLite.
- No autonomous memory writes.
- No semantic/vector database.
- No embeddings.
- No transcript-as-memory dumping.
- No whole-repository snapshots stored as memory content.
- Do not introduce a third persistent database solely for memory.
- Preserve authoritative global-agent registry behavior.
- Preserve all existing project lifecycle/task/plan/workflow semantics.
- Model/runtime details including Qwen/GGUF/llama.cpp must not appear in memory domain types.
- No Python.

## Non-goals

- Feeding memory into Controller prompts.
- Retrieval ranking or precedence resolution.
- Vector/semantic retrieval.
- Automatic consolidation.
- Controller-proposed memory authorization/execution.
- Learning/training dataset generation.
- CLI/TUI/GUI memory UX.
- Importing existing chats/transcripts as memory.

## Acceptance criteria

1. Orc has typed durable `User`, `Project`, `Episodic`, and `Experience` memory records with explicit scope, provenance, timestamps, lifecycle state, and bounded content.
2. User/Experience memory is stored in the existing global authority; Project/Episodic memory is stored in the canonical project database with exact project binding; no third database is introduced.
3. Invalid kind/scope/provenance data is rejected deterministically before or during canonical persistence.
4. Canonical APIs support create, get, structured list/query, correction/supersession, removal/deactivation, and explicit historical inspection.
5. Correction/supersession/removal mutations are transactional and cannot leave partial or simultaneously-active superseded state.
6. Cross-project tests prove global user/experience visibility and strict isolation of project/episodic memory.
7. Existing project DB and global registry migrations/reopen behavior remain compatible, including project DB reset not deleting global memories.
8. Memory domain/storage code contains no inference/model-specific behavior, and no Controller or external worker can write memory directly.

## Required validation

- Focused memory-domain validation tests.
- Project-memory CRUD/correction/removal/history tests.
- Global user/experience-memory CRUD/correction/removal/history tests.
- Cross-project visibility/isolation tests using two projects and one shared global authority.
- Existing project database migration/reopen tests.
- Existing global registry/adoption/reset tests.
- Existing agent registry tests.
- `cargo test --lib`.
- `cargo test --features llama-cpp --lib`.
- relevant integration suite(s) for storage/adoption/app API.
- `cargo fmt --check`.
- normal and feature `cargo clippy --all-targets -- -D warnings`.
- `git diff --check`.

No real Qwen evaluation is required because this task adds no inference prompt/schema/parser semantics.

Report the concrete Rust memory types; exact project/global storage placement; schema/migration changes; canonical application/storage APIs; transaction semantics for correction/removal; cross-project isolation/visibility proof; project-reset/global-persistence proof; existing registry compatibility; deterministic validation results; and the smallest next M06 seam for read-only Controller memory retrieval.
