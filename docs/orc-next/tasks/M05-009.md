# M05-009 — Replace Lead intake judgment with supervised Controller routing

**Status:** Planned
**Milestone:** M05 — Planning and Lead unification

## Objective

Complete M05 by moving the remaining normal-workflow Lead intake judgment into the local Controller while keeping intake persistence, workflow transitions, user gates, DIRECT_TASKS application, Plan routing, and all mutation authority deterministic and kernel-owned.

After this task, the normal supervised Controller workflow must no longer require a legacy Lead or Planner semantic backend for intake, Plan generation, Plan review, or Plan revision. Legacy Lead/Planner APIs and durable historical records may remain as compatibility surfaces; removing them is not required to close M05.

## Repository-grounded seam

M05-008 routes persisted Plan generation/review/revision through Controller capabilities, but `WorkflowStage::Lead` still obtains a legacy `LeadOutcome` and branches on `LeadDecisionKind::{DirectTasks, PlanRequired, UserDecisionRequired}`. The remaining semantic seam is therefore intake classification/routing before either `ApplyDirect` or Controller Plan generation.

## Required path

```text
persisted workflow after discovery
            ↓
bounded Controller intake request
            ↓
typed intake judgment
  ├─ DirectTasks
  ├─ PlanRequired
  └─ UserDecisionRequired
            ↓
trusted deterministic workflow routing
            ↓
ApplyDirect / Controller Plan path / user gate
```

## Scope

- Inspect legacy Lead intake request/response/persistence, `WorkflowStage::Lead`, `LeadOutcome`, discovery snapshot/fingerprint handling, DIRECT_TASKS application, user-decision resolution, M05-008 `WorkflowPlanPath`, and existing Controller inference conventions before editing.
- Add a bounded model-independent Controller intake request containing only the canonical objective/discovery/project facts needed to decide among `DirectTasks`, `PlanRequired`, and `UserDecisionRequired`.
- Add a strict typed Controller intake result with exactly those three semantic outcomes and bounded rationale/details. Reuse `LocalInferenceRuntime` and grammar/schema-constrained structured output conventions.
- Keep task definitions/proposals for `DirectTasks` truthful. If DirectTasks requires structured task content currently produced by Lead, the Controller intake result may carry the minimum canonically validated direct-task proposal required by the existing deterministic application boundary. Do not fabricate a Lead decision merely to transport it.
- Add a supervised Controller intake adapter to the persisted workflow. Controller output may select only the semantic intake outcome/content; the workflow kernel maps it to legal stages/statuses.
- `PlanRequired` must enter the M05-008 Controller Plan path without invoking legacy Lead/Planner semantic backends.
- `DirectTasks` must reuse the canonical existing task-application transaction/invariants. Do not create a second task-creation implementation.
- `UserDecisionRequired` must persist enough exact workflow-owned state to survive restart and resume through the existing operator gate without replaying completed inference or adopting unrelated state.
- Controller intake inference must not create fake Lead decisions, Lead runs, Planner runs, provider runs, or legacy lineage.
- Normal Controller workflow continuation must recover a completed persisted intake boundary without a runtime; runtime is required only when fresh intake inference is actually necessary.
- Preserve legacy workflow/Lead entry points for compatibility. Existing legacy workflows must continue to decode and continue correctly.
- Add deterministic fake-runtime tests for all three intake outcomes, DIRECT_TASKS application, PlanRequired routing into Controller Plan generation, user-decision wait/resume, restart after persisted intake, runtime-free recovery, no duplicate inference/mutation, and legacy compatibility.
- Add a small real-model Controller intake evaluation covering the three outcomes because this task introduces a new inference prompt/schema/parser.

## Preserve

- `WorkflowEngine` as the single persisted workflow/state machine.
- Discovery facts and fingerprint semantics.
- Existing canonical DIRECT_TASKS validation/application semantics.
- M05-001 through M05-008 Controller Plan behavior and authorization boundaries.
- Existing user decision/approval/cancellation gates.
- Existing Plan application and task execution lifecycle.
- Deterministic lifecycle legality, persistence, authorization, and mutation authority.
- Legacy Lead/Planner compatibility APIs and historical data readability.

## Constraints

- Controller/model output is judgment/content, never authorization or mutation authority.
- Model cannot choose workflow ID/stage/status, project ID, persistence IDs, provenance metadata, or lifecycle metadata.
- Do not fabricate Lead/Planner/provider lineage.
- Do not duplicate DIRECT_TASKS task-creation logic.
- Do not introduce another workflow/state machine.
- Do not delete legacy Lead/Planner tables, types, CLI commands, or compatibility paths merely for cleanup.
- Do not change Dispatch/Review/Revise/Accept semantics.
- Do not expand into memory, autonomy, TUI, or GUI.
- No Qwen-specific core/domain behavior.
- No Python.

## Non-goals

- Physically deleting every Lead/Planner symbol or historical table.
- Rewriting discovery.
- Redesigning task contracts or Plan application.
- Autonomous multi-step execution beyond the existing persisted workflow.
- M06 memory work.

## Dependencies

## Acceptance criteria

1. A bounded strict Controller intake capability can return exactly DirectTasks, PlanRequired, or UserDecisionRequired using `LocalInferenceRuntime` without mutation.
2. Normal supervised Controller workflow intake uses that capability and does not invoke the legacy Lead semantic backend.
3. PlanRequired enters the existing M05-008 Controller Plan path with no fabricated legacy lineage.
4. DirectTasks reuses canonical deterministic task validation/application and creates no parallel task-creation path.
5. UserDecisionRequired persists/restarts/resumes correctly without replaying completed inference or requiring a runtime solely to recover persisted state.
6. Controller intake output cannot control workflow/lifecycle/persistence identity or bypass user gates.
7. Legacy Lead/Planner compatibility entry points and existing historical workflow decoding remain valid.
8. With this change, normal supervised Controller workflow semantic ownership is unified: Controller owns intake + Plan generation/review/revision judgment; kernel owns persistence, workflow, approval/application, validation, and lifecycle invariants.
