# M05-008 — Route supervised Plan workflow through Controller capabilities

**Status:** Planned
**Milestone:** M05 — Planning and Lead unification

## Objective

Integrate the completed Controller Plan generation, review, revision, and authorized persistence boundaries into Orc's persisted Plan workflow so normal supervised Plan progression no longer depends on legacy Planner/Lead semantic calls, while preserving deterministic workflow transitions, approval/application gates, restart safety, and legacy compatibility.

This task is routing/integration. It must not collapse the workflow engine or remove legacy Lead/Planner machinery yet.

## Repository-grounded seam

The current `WorkflowEngine` still routes `WorkflowStage::Planner`, `PlannerRevision`, and `PlanReview` through `WorkflowActions::plan`, `revise_plan`, and `review_plan`, and the existing concrete actions use legacy Planner/Lead semantics. M05-001 through M05-007 now provide Controller-owned semantic Plan generation/review/revision plus explicit trusted persistence boundaries.

## Required path

```text
persisted workflow Plan stage
        ↓
Controller semantic capability
        ↓
trusted explicit persistence authorization
        ↓
canonical Plan/review/revision mutation
        ↓
existing deterministic workflow transition
        ↓
existing user approval / ApplyPlan gates
```

## Scope

- Inspect `WorkflowEngine`, its concrete `WorkflowActions` implementation, recovery/restart hooks, current Lead/Planner workflow tests, and M05-001 through M05-007 APIs before editing.
- Identify the smallest integration seam that lets workflow Plan generation, Plan review, and Plan revision use the Controller capabilities and their trusted persistence APIs without duplicating semantic or mutation logic.
- Preserve `WorkflowEngine` as deterministic persisted orchestration. The Controller supplies judgment/content; the kernel/workflow owns legal stage/status transitions.
- Route the normal Plan generation stage through M05-001 + M05-003 semantics: Controller generation, explicit trusted persistence, then existing `PlanReview` transition.
- Route Plan review through M05-004 + M05-005 semantics: Controller review judgment, explicit trusted persistence, then existing deterministic branching to ApplyPlan, PlannerRevision-equivalent revision stage, or user gate.
- Route Plan revision through M05-006 + M05-007 semantics: Controller revision generation, explicit trusted persistence/supersession, then existing Plan review stage.
- Preserve restart/recovery behavior: a persisted Controller-origin Plan/review/revision created before a crash must be recoverable without replaying already-completed inference or persistence.
- Preserve user Plan approval policy and `ApplyPlan` behavior exactly; Controller routing must not bypass configured user approval.
- Keep existing legacy Lead/Planner paths callable for compatibility outside the new Controller-routed workflow path unless a tiny adapter change is required.
- Add bounded typed workflow outcome/adapters as needed. Do not fake provider run IDs for Controller inference. If existing workflow outcome types require provider-run identity, change them truthfully and minimally rather than fabricating legacy run records.
- Add deterministic tests for Controller Plan generation → review → approve routing, review → revise → new review routing, user-decision review routing, configured user approval gate, restart/recovery after each persisted semantic boundary, and absence of legacy Planner/Lead provider invocation on the Controller Plan path.

## Preserve

- Persisted `WorkflowEngine` transition legality and restart safety.
- Existing Plan status/version/provenance/review semantics from M05-002 through M05-007.
- Explicit trusted authorization before Controller-derived mutations.
- Existing `ApplyPlan` task creation/application semantics.
- Existing user approval/cancellation gates.
- Existing task execution lifecycle after Plan application.
- Legacy Lead/Planner APIs for compatibility until a later cleanup task.

## Constraints

- Do not let Controller/model output choose workflow stage/status, persistence IDs, provenance, authorization, version, or supersession metadata.
- Do not bypass M05-003/M05-005/M05-007 trusted persistence boundaries.
- Do not fabricate Lead decisions, Lead runs, Planner runs, or provider run IDs merely to satisfy legacy workflow fields.
- Do not automatically approve a Plan when policy requires user approval.
- Do not create tasks before canonical `ApplyPlan`.
- Do not introduce a second Plan workflow/state machine alongside `WorkflowEngine`.
- Do not remove `WorkflowEngine`, legacy Lead/Planner APIs, or compatibility tests in this task.
- Do not expand into DIRECT_TASKS intake migration unless a strictly necessary narrow adapter is required; report a larger dependency instead.
- No autonomous planning loop beyond the existing bounded workflow revision policy.
- No Qwen-specific core/domain behavior.
- No Python.

## Acceptance criteria

1. Normal supervised workflow Plan generation uses Controller generation + authorized Controller Plan persistence, not the legacy Planner semantic backend.
2. Normal workflow Plan review uses Controller review judgment + authorized Controller review persistence, not legacy Lead semantic review.
3. Normal workflow Plan revision uses Controller revision generation + authorized Controller revision persistence, not the legacy Planner semantic revision backend.
4. Existing deterministic workflow transitions and revision-count/non-convergence policy remain kernel-owned and correct.
5. Controller-derived persistence still passes through exact trusted one-shot authorization and fresh deterministic checks.
6. Restart/recovery can observe already-persisted Controller Plan/review/revision boundaries and continue without replaying completed semantic calls or duplicating mutations.
7. User Plan approval policy and canonical `ApplyPlan` gate remain unchanged and cannot be bypassed by Controller output.
8. No fabricated legacy Lead/Planner/provider lineage is introduced; legacy compatibility paths remain available outside the Controller-routed path.
