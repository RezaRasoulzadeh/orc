# M06-002 — Build deterministic bounded Controller memory context

**Status:** Done
**Milestone:** M06 — Persistent memory

## Objective

Build Orc's first reusable, read-only, model-independent Controller memory context from the canonical M06-001 memory API.

M06-001 established typed durable memory records and deterministic persistence. M06-002 adds the bounded deterministic retrieval/projection seam that later Controller capabilities can embed in their own request/state types without forcing unrelated capabilities into one universal Controller packet.

This task does not yet require every Controller capability to consume memory and does not add autonomous memory writes, semantic retrieval, or model-specific behavior.

## Repository-grounded context

M06-001 exposes memory through the canonical `MemoryService` / typed memory API owned by Orc's application/kernel layer.

The existing Controller architecture does **not** use one universal request shape. For example:

- normal task recommendation uses `ControllerStatePacket`;
- planning uses its own bounded `ControllerPlanningRequest` / `ControllerPlanningState`;
- other Controller capabilities likewise own capability-specific request/state types where appropriate.

Therefore M06-002 must introduce memory reuse at the smallest correct abstraction: a reusable bounded typed memory context that capability-specific Controller inputs may embed later. Do not redesign existing Controller capabilities around `ControllerStatePacket` merely to reuse memory.

Memory retrieval remains Controller-owned judgment/context preparation over kernel-owned canonical facts. The kernel/storage layer remains authoritative for record identity, scope, lifecycle, provenance, and persistence.

## Scope

Add a canonical read-only retrieval/projection seam that:

- reads active durable memories through the M06-001 canonical API;
- resolves the current project's project/episodic scope exactly;
- reads user/experience memory from the shared global authority;
- projects eligible records into a reusable bounded model-independent `ControllerMemoryContext` or equivalent typed structure;
- preserves explicit source/authority metadata needed by future capability-specific Controller requests;
- applies deterministic selection, ordering, and truncation;
- performs no persistence mutation;
- can be called from `OrcApp` or an equivalent canonical application seam without exposing raw SQLite or registry handles.

The exact Rust names may differ, but the abstraction must be reusable by later Controller capability-specific request builders without requiring those capabilities to share one state/request type.

## Authority and precedence

The context must preserve enough typed information for later Controller capabilities to enforce the architecture precedence:

```text
current operator instruction
→ current project facts/decisions
→ current task/plan contract
→ durable user preferences
→ historical experience
→ base model tendencies
```

M06-002 must not collapse all memories into undifferentiated text.

At minimum:

- Project memory must remain distinguishable as current-project durable context/fact/decision.
- User memory must remain distinguishable as durable cross-project preference/context.
- Episodic memory must remain distinguishable as project-scoped historical context.
- Experience memory must remain distinguishable as cross-project historical guidance.
- Provenance and scope must remain visible in the typed projection.
- Historical memory must not be represented as canonical current task/project truth.

This task establishes the retrieval representation needed for precedence. It does not require natural-language conflict resolution or model judgment about contradictory memories.

## Retrieval eligibility

Normal Controller memory context may contain only active eligible records.

- Removed records must not appear.
- Superseded records must not appear.
- Project and Episodic records must be bound to the exact current project identity.
- User and Experience records must come from the existing shared global authority.
- Retrieval must use the canonical M06-001 application/storage memory seam; no Controller/runtime raw SQL.
- Historical inspection remains available through M06-001 but is not part of normal Controller memory context.

Retrieval must not modify lifecycle state, timestamps, confidence, provenance, supersession history, or any other durable field.

## Reusable Controller memory projection

Add a bounded typed context containing projected memory items.

Each projected item must retain at least:

- stable canonical memory identity;
- memory kind;
- scope identity where applicable;
- bounded subject;
- bounded content;
- provenance kind;
- bounded provenance source reference when present;
- optional confidence;
- explicit authority/category information if needed to prevent callers from treating historical/global memory as current canonical truth.

Do not expose raw database rows or storage implementation details.

The projection may omit fields that are purely persistence-internal and irrelevant to Controller reasoning, but eligibility must be provable from canonical active-memory reads.

## Deterministic selection and bounds

Retrieval and projection must be explicitly bounded and deterministic.

Define and enforce:

- per-item subject/content/source-reference bounds suitable for inference context;
- a maximum item count per memory kind;
- a maximum total memory item count;
- a maximum serialized `ControllerMemoryContext` size;
- stable deterministic ordering before truncation;
- stable deterministic truncation when eligible records exceed bounds.

Selection must not depend on:

- model inference;
- embeddings or vector similarity;
- fuzzy/learned ranking;
- nondeterministic hash iteration;
- randomness;
- external workers.

Use existing structured metadata and stable ordering. If a new deterministic ordering key is required, it must be explicit, repository-grounded, and testable.

Do not silently truncate individual UTF-8 content in a way that changes meaning or creates malformed data. Either project through a defined safe bound or reject/omit according to an explicit deterministic rule.

## Application boundary

Expose construction of the reusable memory context through Orc's canonical application/kernel-facing API, preferably through `OrcApp` and the existing M06-001 memory service rather than a parallel abstraction.

The local inference runtime must not receive a `Database`, `MemoryService`, registry connection, filesystem path, or persistence handle.

M06-002 should make it straightforward for later capability-specific Controller request builders to accept/embed the bounded memory context, but it must not redesign those request types in this task unless a tiny adapter is necessary to prove the seam.

## Compatibility

- Existing M06-001 memory CRUD/history/migration behavior must remain unchanged.
- Existing Controller request/state types must remain valid.
- Existing Controller inference behavior must remain unchanged unless a minimal non-semantic plumbing change is strictly necessary to compile/prove the new seam.
- No capability is required to change its prompt or structured-output schema in this task.
- No-memory context construction must succeed deterministically and return an empty bounded context rather than requiring special-case inference behavior.

## Invariants / requirements

- Memory remains explicit Orc data, separate from model weights.
- `MemoryService` or its canonical M06-001 equivalent remains the only memory persistence access seam used here.
- Project/Episodic memory never crosses project identity.
- User/Experience memory remains cross-project through the global authority.
- Current canonical project/task/Plan state remains outside memory authority and is not rewritten from memory.
- Retrieval is read-only.
- Controller/runtime code gets typed bounded context, not persistence access.
- Reuse happens at the memory-context abstraction, not by forcing unrelated Controller capabilities into one request/state type.
- No model-specific domain behavior.
- No Qwen/GGUF/llama.cpp-specific retrieval logic.
- No Python.

## Non-goals

- Feeding memory into every existing Controller capability.
- Redesigning all Controller request/state types.
- Adding memory directly to `ControllerStatePacket` solely as a universal reuse mechanism.
- Controller memory writes.
- Autonomous memory capture.
- Memory consolidation/deduplication.
- Semantic/vector retrieval.
- Embeddings.
- Learned relevance ranking.
- Natural-language contradiction resolution.
- CLI/TUI/GUI memory management.
- Training/fine-tuning or experience dataset generation.

## Acceptance criteria

1. Orc has a reusable typed, model-independent, bounded Controller memory context constructed through the canonical M06-001 memory API rather than raw persistence access.
2. Only active eligible records are projected; removed and superseded records are excluded from normal memory context.
3. Project/Episodic retrieval is strictly bound to the exact current project, while User/Experience retrieval uses the shared global authority without cross-project leakage.
4. Projected items retain canonical memory identity, kind, scope, provenance, optional confidence, and bounded subject/content/source data sufficient for future capability-specific code to distinguish authority and history.
5. Per-item, per-kind, total-count, and serialized-context bounds are explicit and enforced, with stable deterministic ordering and truncation.
6. Retrieval is read-only and repeated context construction causes no durable memory lifecycle, timestamp, confidence, provenance, supersession, or history mutation.
7. The abstraction is reusable by capability-specific Controller request builders without requiring those capabilities to share `ControllerStatePacket` or another universal request type.
8. Existing Controller capabilities and M06-001 persistence behavior remain compatible, including deterministic empty context when no active memory exists.
