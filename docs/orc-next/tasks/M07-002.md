# M07-002 — Compose one supervised Controller continuation step

**Status:** Planned
**Milestone:** M07 — Supervised autonomy

## Objective

Compose the existing Controller recommendation, M07-001 continuation-grant inspection, and M03 exact one-shot execution boundaries into the smallest application-level API that can perform at most one routine supervised continuation action for one explicit task.

This task proves the end-to-end supervised continuation seam. It does **not** add a loop, automatic task enumeration, background execution, or automatic acceptance.

## Repository-grounded context

`OrcApp::propose_controller_action(task_id, runtime)` already produces a bounded typed `ControllerActionProposal` from current canonical task state plus bounded Controller memory. The proposal can represent the existing task actions but does not authorize or execute them.

M07-001 adds an opaque project-bound finite `ControllerContinuationGrant` that may authorize only `Dispatch`, `SemanticReview`, or `Revise`. Grant inspection checks current canonical legality, consumes exactly one grant unit only on successful authorization mint, and reuses the existing M03 exact-intent `ControllerActionAuthorization`.

M03 already owns execution through `OrcApp::execute_authorized_controller_action`, including exact-intent authorization matching, trusted execution context, fresh legality immediately before canonical mutation, and reuse of the existing dispatch/review/revision implementations.

`WorkflowEngine` remains the only restart-safe multi-step orchestration path and already owns deterministic workflow transition/revision limits. M07-002 must not duplicate that engine.

## Scope

Add one capability-local application seam for a single supervised continuation step.

Required behavior:

- accept one explicit task identity, one trusted M07-001 continuation grant, one local Controller runtime, and trusted application-owned execution dependencies/context needed by the selected existing action;
- call the existing `OrcApp::propose_controller_action` seam rather than introducing a new recommendation prompt/schema;
- only continue when the proposal contains one canonical `ControllerActionIntent` that the grant can authorize;
- route the exact proposed intent through M07-001 grant inspection to mint the existing M03 one-shot authorization;
- after successful grant authorization, execute exactly that same intent through `OrcApp::execute_authorized_controller_action`;
- perform at most one Controller inference, at most one successful grant-budget consumption, and at most one action execution per call;
- expose a bounded typed result that distinguishes at least: no actionable/unsupported recommendation, grant rejection, execution success, and execution rejection/failure;
- preserve the exact existing M03 execution result/evidence where practical rather than inventing parallel lifecycle truth;
- do not automatically retry when recommendation, grant inspection, fresh legality, or canonical execution fails;
- do not refund grant budget when execution fails after successful authorization mint, preserving M07-001 semantics.

## Supervised-step semantics

The application may invoke this seam because a trusted operator has already supplied a finite grant. That grant is permission to perform eligible routine actions, not permission for the model to widen scope or select another project/task.

The exact order must remain:

1. trusted caller supplies explicit task + grant + runtime + execution dependencies;
2. Controller produces one existing bounded action proposal from current canonical state;
3. deterministic proposal validation/adaptation yields one exact existing `ControllerActionIntent` or a non-actionable result;
4. M07-001 checks grant project/action/budget plus current canonical legality and mints one exact M03 authorization while consuming one unit;
5. M03 execution checks exact authorization match and fresh canonical legality again;
6. existing canonical mutation path performs the action.

No step may infer or mutate grant scope, budget, project binding, task identity, execution context, or acceptance policy.

## Invariants / requirements

- Reuse `OrcApp::propose_controller_action`; no new recommendation prompt, schema, or model-specific policy.
- Reuse `ControllerActionProposal` and `ControllerActionIntent`; no second action schema.
- Reuse M07-001 `ControllerContinuationGrant`; no second supervision/budget model.
- Reuse M03 `ControllerActionAuthorization` and `execute_authorized_controller_action`; no second mutation path.
- Only routine `Dispatch`, `SemanticReview`, and `Revise` may execute through this seam because those are the only M07-001 grantable actions.
- `Accept` must never execute through a continuation grant even if the Controller recommends it.
- Task identity must remain exact: a proposal for another task must not be authorized or executed.
- Trusted `ControllerActionExecutionContext` remains application-owned and must match the proposed action; model output cannot supply agent/provider/runtime/validation/backend handles or overrides.
- Current canonical legality is checked once during grant inspection and again immediately before execution through M03.
- Scheduler/agent permissions, availability, quota/economy facts, lifecycle, validation/review evidence, revision feedback, and workflow limits remain authoritative.
- One call performs at most one routine action. Do not call the recommendation seam again after execution.
- No automatic retry or recovery loop.
- No automatic workflow continuation after the action finishes.
- No automatic task selection or enumeration.
- No automatic `Accept`, Plan approval, user-decision resolution, memory capture, or memory maintenance.
- No persistence of model runtime/execution handles.
- No provider token hard cap, model-specific behavior, or Python.

## Non-goals

- Repeated continuation while grant budget remains.
- A new autonomous `run` loop.
- Persisting/recovering continuation grants across process restart.
- Integrating the grant into the full `WorkflowEngine` continuation loop.
- Automatically resolving `WaitingUser`, `AcceptanceReady`, blocked, non-convergent, or other operator/recovery gates.
- Automatically invoking memory capture/maintenance.
- UI/CLI design beyond the smallest API required for deterministic tests.
- Changing recommendation semantics or real-Qwen prompt/schema behavior.

## Acceptance criteria

1. One application call can compose current `propose_controller_action` → M07-001 grant inspection → existing M03 execution for exactly one explicit task.
2. The call executes at most one grantable routine action and cannot execute `Accept`.
3. Unsupported/non-actionable Controller proposals cause no authorization, no budget consumption, and no mutation.
4. Grant rejection causes no execution and preserves failed-inspection budget semantics.
5. Successful grant authorization consumes exactly one unit and the exact same intent is passed to M03 execution.
6. M03 fresh legality remains authoritative if state changes between grant inspection and execution; no stale grant observation bypasses kernel legality.
7. Execution context remains trusted/application-owned and action-matched; model output cannot inject execution dependencies or overrides.
8. Result/evidence is bounded and inspectable, with no autonomous retry, loop, task enumeration, acceptance, or second workflow/action system.

## Required validation

- successful one-step Dispatch composition;
- successful one-step SemanticReview composition;
- successful one-step Revise composition;
- Controller `Accept` recommendation cannot execute through a continuation grant and consumes no grant budget;
- unsupported/no-action recommendation consumes no budget and performs no mutation;
- wrong-project/revoked/exhausted/unsupported-action grant rejection performs no execution;
- illegal current action rejected during grant inspection performs no execution and consumes no budget;
- state-change-after-mint regression proving M03 fresh legality rejects stale authorization at execution;
- exact task/intent identity mismatch cannot execute;
- execution-context mismatch cannot mutate and does not trigger another recommendation/authorization;
- execution failure after successful authorization does not refund the consumed grant unit;
- exactly one Controller inference per call;
- no automatic second action after successful execution;
- existing M03 Controller action regressions;
- M06 recommendation/memory regressions;
- M07-001 continuation-grant regressions;
- existing workflow policy/limit regressions;
- `cargo test --lib`;
- `cargo test --features llama-cpp --lib`;
- `cargo fmt --check`;
- normal and feature `cargo clippy --all-targets -- -D warnings`;
- `git diff --check`.

No new real-Qwen evaluation is required if the implementation reuses the existing `propose_controller_action` inference contract without changing its prompt, schema, bounds, or semantics. If that contract changes, rerun its strict and semantic evaluation.
