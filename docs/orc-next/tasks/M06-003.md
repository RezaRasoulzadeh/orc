# M06-003 — Integrate bounded memory into Controller planning

**Status:** Planned
**Milestone:** M06 — Persistent memory

## Objective

Feed the reusable M06-002 `ControllerMemoryContext` into the existing read-only Controller planning capability without widening persistence authority or forcing other Controller capabilities onto the planning request shape.

This is the first capability-level memory integration. It should prove that a capability-specific Controller request can embed the shared bounded memory context while preserving current-request authority, deterministic bounds, and the model-independent runtime boundary.

## Repository-grounded context

M06-002 established standalone `ControllerMemoryContext` / `ControllerMemoryItem` and canonical read-only construction through `OrcApp::controller_memory_context()`. It intentionally changed no Controller prompts or capability request/state types.

Planning already has its own bounded `ControllerPlanningRequest` / `ControllerPlanningState` in `src/controller_planning.rs`, with a 64 KiB serialized request bound and structured `PlanResponse` output. `OrcApp::propose_controller_plan` is the application entrypoint used by persisted Controller workflow code.

Use these seams directly:

- build memory through `OrcApp::controller_memory_context()`;
- embed the typed context in the planning capability's own bounded request;
- keep `controller_planning` free of database, registry, `MemoryService`, filesystem, and model-specific persistence access;
- keep `LocalInferenceRuntime` model-independent and unaware of memory storage.

Do not redesign normal recommendation, recovery, intake, Plan review, or Plan revision in this task.

## Scope

Integrate M06-002 memory into Controller Plan generation only.

Required behavior:

- `ControllerPlanningRequest` carries a typed bounded `ControllerMemoryContext` (or a capability-local wrapper that contains it without duplicating its data model);
- application-level Plan proposal construction obtains the current memory context from the canonical `OrcApp` seam;
- the memory context is serialized as part of the bounded planning inference request;
- existing planning request fields remain canonical current input and are not rewritten from memory;
- planning output schema and persistence/authorization flow remain unchanged;
- empty memory is valid and preserves existing behavior apart from the explicit empty context;
- all request-size validation includes the serialized memory context.

## Authority and precedence

The planning prompt/request representation must make precedence explicit:

```text
current operator objective/instruction
→ current canonical project/planning state and explicit constraints
→ durable Project memory
→ durable User memory
→ Episodic project history
→ cross-project Experience memory
→ base model tendencies
```

For this capability:

- current `PlanningRequest` objective, constraints, non-goals, deliverables, definition-of-done, approval requirements, and canonical current state are authoritative;
- Project memory may supply durable project decisions/context but cannot contradict or rewrite the current request;
- User memory is preference/context only and cannot override project/request constraints;
- Episodic memory is historical evidence/context only;
- Experience memory is reusable guidance only and must not be presented as a current-project fact;
- memory provenance/authority metadata must remain visible to the model rather than flattening all memory to unlabeled prose.

No deterministic natural-language conflict resolver is required. The kernel/request structure must preserve authority; the Controller may reason over conflicts within that structure.

## Invariants / requirements

- Reuse `ControllerMemoryContext`; do not create a second planning-specific memory storage/retrieval model.
- Memory retrieval remains read-only and occurs through the canonical application seam.
- `controller_planning` receives bounded typed memory, not persistence handles.
- The existing planning request remains capability-specific; do not merge it with `ControllerStatePacket` or another universal Controller request.
- The existing 64 KiB planning request limit remains enforced after memory is added.
- The planning result/output JSON schema must not change solely because memory was added.
- Plan persistence, review, revision, workflow routing, approvals, and task application remain deterministic and unchanged.
- No memory writes, correction, removal, or lifecycle mutation from planning output.
- No autonomous capture or consolidation.
- No semantic/vector retrieval, embeddings, learned ranking, or model-based memory selection.
- No direct SQLite/registry access from Controller planning or runtime code.
- No Qwen/GGUF/llama.cpp-specific domain behavior.
- No Python.

## Non-goals

- Adding memory to normal task recommendation.
- Adding memory to recovery.
- Adding memory to intake.
- Adding memory to Plan review or Plan revision.
- Automatically creating memories from generated Plans.
- Memory consolidation/deduplication.
- Semantic search or embeddings.
- Changing Plan persistence lineage or workflow semantics.
- Creating a universal Controller request/state type.
- CLI/TUI/GUI memory management.

## Acceptance criteria

1. Controller Plan generation receives the current bounded M06-002 memory context through its existing capability-specific request/application path.
2. Planning code does not gain direct `Database`, `MemoryService`, global-registry, filesystem, or other persistence access.
3. The planning request preserves typed memory identity/kind/scope/authority/provenance metadata rather than flattening memory into unlabeled text.
4. Current operator objective, explicit planning constraints, and canonical current planning state remain structurally and prompt-level authoritative over durable/historical memory.
5. Existing 64 KiB planning request validation includes memory and deterministically rejects an over-limit combined request rather than silently bypassing either bound.
6. Empty memory remains valid and existing planning behavior/output contract remains compatible.
7. Planning structured-output schema, Plan validation, persistence, workflow, and approval/application semantics remain unchanged.
8. Retrieval/inference causes no durable memory mutation.
9. No other Controller capability is redesigned or required to consume memory in this task.

## Required validation

- Focused planning-request serialization/validation tests with non-empty `ControllerMemoryContext`.
- Application-level test proving `OrcApp::propose_controller_plan` includes memory obtained through the canonical M06-002 seam.
- Empty-memory compatibility regression test.
- Combined planning-request size-limit test proving the existing 64 KiB bound includes memory.
- Authority/provenance serialization tests preserving typed memory metadata.
- Prompt-capture/fake-runtime test proving explicit precedence instructions accompany the memory-bearing request.
- Regression tests proving planning output schema and `PlanResponse` validation are unchanged.
- Read-only test proving Plan inference does not mutate memory records/history.
- Existing planning tests and relevant workflow integration tests.
- `cargo test --lib`.
- `cargo test --features llama-cpp --lib`.
- `cargo fmt --check`.
- normal and feature `cargo clippy --all-targets -- -D warnings`.
- `git diff --check`.

Because this task changes the real planning prompt/input semantics, run a small real Qwen planning evaluation after deterministic validation. It must include at least:

- a conflict where explicit current planning constraints override incompatible User/Experience memory;
- a case where Project memory supplies relevant context without replacing the current objective;
- a case where historical Episodic/Experience memory remains guidance rather than current-project truth.

Report strict structured-output success and semantic precedence behavior separately.
