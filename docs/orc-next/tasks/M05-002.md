# M05-002 — Make persisted Plan provenance Controller-compatible

**Status:** Done
**Milestone:** M05 — Planning and Lead unification

## Objective

Remove the durable Plan schema's false assumption that every Plan must originate from both a Lead decision and a Planner run, while preserving truthful provenance for existing legacy Plans.

## Result

Implemented typed `PlanOrigin` and `PlanProvenance` distinguishing legacy Planner-origin and Controller-origin Plans.

Updated `PersistedPlan`, plan history/read paths, row decoding, schema, and plan-review validation to use origin-appropriate provenance. Legacy Lead/Planner references are nullable only where the explicit origin permits it, retain foreign-key integrity when present, and are protected by consistency checks.

Added legacy-schema rebuild migration preserving existing lineage, versions, parent/supersession relationships, dependencies, and reopen behavior.

Added canonical `Database::store_controller_plan`, which represents a Controller-origin `Proposed` Plan without fabricated Lead/Planner IDs, Lead-decision consumption, task creation, approval, or application. Production Controller authorization/persistence is intentionally deferred to the next M05 task.

Strict legacy creation/revision provenance validation and existing approved-plan application semantics remain intact.
