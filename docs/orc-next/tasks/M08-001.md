# M08-001 — Establish typed verified Controller experience examples

**Status:** Planned
**Milestone:** M08 — Experience dataset

## Objective

Establish the first canonical persistent dataset record and trusted application/storage API for explicitly curated, verified Controller experience examples.

M08 begins by defining what one training/evaluation example is and how Orc stores it. This task does **not** automatically harvest Controller traffic, infer labels from workflow state, train a model, export a training file, or conflate durable memory with training data.

## Repository-grounded context

D-006 requires collecting verified Controller decisions, operator corrections, and outcomes for periodic curated evaluation/training rather than blindly training after every interaction. D-005 separately states that user/project facts and experience memory remain explicit Orc memory; model fine-tuning is for reasoning behavior, not factual storage.

The repository already has project-local persistence plus an existing global registry database through `Database::init_with_registry(...)`. M06 also established `MemoryKind::Experience`, but M08 dataset examples serve a different purpose from runtime memory retrieval and must remain a distinct typed dataset surface rather than being stored as memory records.

## Scope

Add the smallest typed persistent experience-example model plus deterministic create/get/list APIs needed for later curation/export.

One example must represent an explicitly trusted, already-verified Controller interaction or correction, not raw unverified model traffic.

Required fields must include, using repository conventions and exact naming chosen during implementation:

- stable example identity;
- schema/version field;
- Controller capability/category identifying the reasoning surface represented by the example;
- bounded canonical input payload;
- bounded canonical expected/accepted output payload;
- verification basis/source identifying why this example is trusted;
- optional project provenance/reference without making the example project-owned;
- optional source run/task/Plan/review/memory references as opaque provenance only;
- optional operator correction metadata when the accepted output differs from the original Controller output;
- outcome/quality metadata sufficient to distinguish accepted success from corrected/rejected evidence;
- created timestamp;
- lifecycle suitable for later curation/removal without destroying provenance.

The record must be declarative and serializable. It must not contain runtime/model/storage handles, authorizations, grants, or mutable workflow objects.

## Persistence authority

Use the existing global registry database as the canonical persistence authority for M08 dataset examples so examples can be curated across projects.

Do not create a third database.

Project identity, task IDs, run IDs, Plan IDs, review IDs, memory IDs, or other source identities are provenance references only. An M08 example remains a global dataset record and must not become mutable project state.

If the actual registry abstraction requires a small reusable storage seam, add only the minimum necessary surface. Do not redesign database ownership.

## Trusted creation boundary

Creation is explicit and trusted application/kernel work only.

No local Controller inference is involved in this task.

The creation API must accept one fully specified example draft from trusted application code and deterministically validate it before persistence.

Do not automatically decide that a Controller decision is verified merely because:

- it executed successfully;
- a workflow advanced;
- validation passed;
- review passed;
- an operator accepted something;
- a memory mutation succeeded.

Those signals may become explicit verification evidence in later tasks, but M08-001 must not hardcode them into automatic dataset policy.

## Bounds and validation

Define explicit hard bounds for every variable-size field and the complete serialized example.

At minimum validate:

- supported schema version;
- non-empty bounded capability/category;
- non-empty bounded input payload;
- non-empty bounded accepted/expected output payload;
- supported verification basis;
- provenance references are bounded and structurally valid;
- project provenance, when present, uses a positive canonical project identity;
- correction metadata is internally consistent;
- outcome/quality metadata is internally consistent;
- lifecycle is valid;
- complete serialized record remains below one explicit maximum size.

Prefer structured `serde_json::Value` or another existing typed/declarative representation for bounded payloads; do not store arbitrary executable code, opaque binary blobs, or unbounded transcripts.

Do not silently truncate payloads or provenance.

## APIs

Provide the smallest application/storage API needed for:

- create one verified example;
- get one example by stable ID;
- list examples deterministically with bounded filtering/pagination suitable for later curation/export;
- retire/remove an example from the active curated set without erasing provenance/history.

Exact naming may follow existing repository conventions.

Do not add automatic dataset capture hooks yet.

## Invariants / requirements

- Dataset examples are distinct from `MemoryKind::Experience` runtime memory.
- One canonical persistent record format.
- Global registry database is the persistence authority.
- Explicit trusted creation only.
- No Controller inference.
- No automatic verification/label derivation.
- No workflow/task/review/validation/recovery hooks.
- No training or fine-tuning.
- No dataset export yet.
- No embeddings/vector DB.
- No Python runtime dependency.
- No provider/model-specific behavior.
- No provider token hard cap.
- Deterministic stable ordering for list operations.
- Historical/retired examples remain inspectable for provenance.

## Non-goals

- Automatically collecting every Controller request/response.
- Automatically converting successful actions into positive examples.
- Automatically converting failed/revised actions into negative/correction examples.
- Automatic operator-correction capture.
- Deduplication by embeddings or semantic similarity.
- Dataset balancing/sampling/ranking.
- Train/validation/test splitting.
- JSONL/GGUF/LoRA/trainer export.
- Fine-tuning Qwen or any other model.
- Evaluation runner changes.
- Runtime memory retrieval changes.
- `MemoryKind::Experience` mutation/retrieval changes.
- CLI/TUI/GUI integration.

## Acceptance criteria

1. Orc has one canonical typed, versioned persistent Controller experience-example record distinct from runtime memory.
2. Examples persist in the existing global registry database; no new database is introduced.
3. Trusted code can create exactly one fully specified verified example after deterministic validation.
4. Stable get/list APIs expose examples deterministically with bounded query behavior.
5. A lifecycle operation can retire/remove an example from the active curated set while preserving provenance/history.
6. Invalid/unbounded/internally inconsistent examples are rejected before persistence.
7. Project/run/task/Plan/review/memory identities are provenance only and do not grant mutation authority.
8. No Controller inference, automatic capture, automatic verification policy, workflow hook, training, export, embedding, or model-specific behavior is introduced.
9. Existing M06 memory behavior and M07 supervised-autonomy behavior remain unchanged.
