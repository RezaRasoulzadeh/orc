# M09-002 — Establish full-surface Controller specialization evaluation suite

**Status:** Planned
**Milestone:** M09 — Controller specialization

## Objective

Establish one deterministic, model-independent specialization evaluation suite covering every current inference-backed Controller judgment capability so M09 has a stable pre-training baseline and future candidate-model comparison gate before any model can be promoted.

This task defines evaluation semantics and deterministic fixtures only. It does not fine-tune a model, choose a trainer, transform the M09-001 snapshot into trainer-specific records, or change production Controller inference.

## Repository-grounded context

M09-001 now provides a deterministic trainer-neutral snapshot of the complete Active canonical Controller experience dataset.

The repository already contains the older M02 read-only Controller evaluation harness for normal task recommendations. M02-002 demonstrated the required pattern: bounded typed scenarios, semantic comparison rather than prose matching, deterministic fake-runtime tests, and an opt-in real-Qwen smoke path. That corpus predates the later Controller capabilities added for recovery, planning, workflow intake, Plan review/revision, memory capture, memory maintenance, and memory-maintenance target selection.

D-006 requires fine-tuning against a curated dataset and an evaluation suite. A candidate specialization therefore must not be trained or promoted against recommendation-only evidence.

The current fixed inference-backed capability surface is:

- `controller.task_recommendation`;
- `controller.recovery_recommendation`;
- `controller.plan_generation`;
- `controller.workflow_intake`;
- `controller.plan_review`;
- `controller.plan_revision`;
- `controller.memory_capture`;
- `controller.memory_maintenance`;
- `controller.memory_selection`.

## Scope

Add a versioned typed specialization-evaluation suite and deterministic evaluator over bounded canonical scenarios for all current fixed Controller capabilities.

The suite must reuse each capability's production typed input/result validation and model-independent inference boundary wherever practical. Expected answers are deterministic test/evaluation authority and must not be inferred from the model being evaluated.

The core evaluator must be runnable with fake runtimes and require no model file, network access, filesystem mutation, or provider access.

## Canonical evaluation shape

Add versioned typed structures sufficient to represent:

- suite schema version;
- scenario identifier;
- exact capability identifier;
- bounded typed/canonical input fixture;
- expected typed semantic result or explicitly enumerated acceptable equivalents where the production contract genuinely permits more than one answer;
- observed result or structured runtime/parse/validation failure;
- pass/fail result;
- aggregate exact counts globally and per capability.

Do not evaluate exact rationale wording, prose style, token usage, or confidence unless a production contract makes one of those fields semantically authoritative.

## Scenario coverage

Cover every current fixed capability with at least one positive representative scenario and enough negative/edge scenarios to exercise the capability's important semantic contract.

At minimum, the suite must prove that capability-local production semantics remain distinguishable. Examples include:

- normal recommendation: dispatch/accept/revise/operator-decision classes already represented by the M02 corpus;
- recovery: choose only legal recovery operations from supplied deterministic failure/recovery facts;
- planning: produce a plan result satisfying production typed validation without inventing unavailable authority;
- workflow intake: preserve production routing semantics;
- Plan review: preserve PASS/REVISE or equivalent production review semantics and blocker/lineage constraints;
- Plan revision: preserve production revision schema and validation;
- memory capture: preserve explicit-candidate capture/no-capture semantics;
- memory maintenance: preserve explicit-target maintenance/no-change semantics;
- memory selection: select only from supplied candidates or return no target.

Do not duplicate large production business logic inside the evaluator merely to manufacture expected results. Scenario expectations should be explicit fixtures tied to existing typed contracts.

## Determinism and authority

- Scenario IDs are stable and unique.
- Scenario order is code-owned and deterministic.
- Capability identifiers are exact fixed production capability strings.
- Expected semantic results are explicit fixture authority, never generated by the evaluated model.
- Fake-runtime evaluation over a fixed suite must serialize identically across repeated runs.
- Aggregate counts must exactly equal scenario results and per-capability sums.
- Unknown capability identifiers, duplicate scenario IDs, malformed expected values, and malformed observed typed values fail closed.

## Production-boundary constraints

The deterministic evaluation path must not:

- mutate task, Plan, memory, experience, workflow, registry, or project state;
- execute Controller intents;
- dispatch/review/revise work;
- create or retire M08 examples;
- consume M09-001 snapshot entries as automatic expected answers;
- change production prompts, parsers, schemas, runtime requests, temperatures, token limits, or decision semantics;
- add provider/model-specific branching to the core evaluator.

Prefer direct reuse of existing capability-local request/result types and validation functions rather than parallel evaluation-only schemas that can drift.

## Real-model boundary

A feature-gated ignored real-model smoke path may be added or extended using the existing `ORC_QWEN3_GGUF` convention, but deterministic acceptance of this task must not require a model file.

If the real-model path is included, it must:

- use the same model-independent evaluation suite;
- run read-only;
- report per-scenario and aggregate exact pass/fail counts;
- preserve structured runtime/parse/validation failure evidence;
- never relax expectations to fit current Qwen output.

This task establishes the baseline mechanism; it does not set a candidate-model promotion threshold yet.

## Invariants / requirements

- All nine current inference-backed Controller capabilities are represented.
- Typed semantic evaluation, not exact prose matching.
- Deterministic stable scenario identities and order.
- Explicit expected results independent of observed model output.
- Production input/result validation reused where practical.
- Exact global and per-capability aggregate accounting.
- Fail closed on malformed suite/scenario/capability/result metadata.
- Fake-runtime tests require no model or network.
- Read-only evaluation only.
- No production inference behavior changes.
- No training backend or trainer-specific dataset transform.
- No train/validation/test split, sampling, balancing, ranking, weighting, or readiness policy.
- No model promotion/default change.
- No runtime `MemoryKind::Experience` mutation.
- No embeddings.
- No Python runtime dependency.
- No provider fallback or provider token hard cap.

## Non-goals

- Fine-tuning or adapter training.
- Choosing llama.cpp training support, LoRA tooling, external frameworks, or trainer format.
- Building training records from M09-001 snapshot.
- Dataset splitting/balancing/deduplication.
- Quality thresholds.
- Automatic model promotion.
- Benchmarking latency, throughput, memory consumption, or token economy.
- Changing Controller prompts/parsers/runtime settings.
- CLI/TUI/GUI presentation unless strictly required by an existing test boundary.

## Acceptance criteria

1. A versioned typed specialization-evaluation suite represents every current fixed inference-backed Controller capability.
2. Stable unique scenario IDs and deterministic scenario ordering are validated.
3. Every scenario has explicit deterministic expected semantic authority independent of observed model output.
4. Evaluation reuses production capability types/validation where practical and compares typed semantics rather than prose.
5. Fake runtimes can produce passing, incorrect, malformed, and runtime-failure outcomes without mutating Orc state.
6. Global and per-capability exact pass/fail/error accounting is validated against scenario results.
7. Unknown capabilities, duplicate IDs, malformed expected data, and invalid observed results fail closed.
8. Repeated deterministic fake-runtime evaluations serialize identically.
9. No production inference, persistence, workflow, memory, experience, training, or model-default behavior changes.

## Required validation

Add focused deterministic tests for at least:

- suite validation with all nine exact fixed capability identifiers;
- duplicate scenario IDs rejected;
- unknown capability rejected;
- deterministic scenario ordering;
- at least one passing representative scenario per capability;
- incorrect typed result produces failure without aborting remaining scenarios;
- runtime failure is recorded deterministically;
- malformed/invalid typed output is recorded deterministically where the capability parser/runtime boundary permits it;
- semantically acceptable alternatives pass only where explicitly configured;
- exact rationale/prose differences do not affect semantic result unless production semantics require them;
- global aggregate counts equal scenario count;
- per-capability counts sum to global counts;
- repeated fake-runtime reports serialize identically;
- zero canonical state writes during evaluation;
- existing M02 evaluation regressions;
- M05/M06/M07 capability-local inference/validation regressions relevant to the covered modules;
- M08-002 through M08-010 curation regressions proving capability identifiers/types remain aligned;
- M09-001 snapshot regressions;
- `cargo test --lib`;
- `cargo test --features llama-cpp --lib`;
- normal and feature `cargo clippy --all-targets -- -D warnings`;
- `cargo fmt --check`;
- `git diff --check`.

Real-Qwen execution is optional for this task unless implementation changes a production inference path. If inference is unchanged, no real-Qwen run is required for acceptance.
