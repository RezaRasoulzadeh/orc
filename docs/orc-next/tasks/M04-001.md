# M04-001 — Expose bounded recovery facts and legal recovery operations

**Status:** Done
**Milestone:** M04 — Recovery intelligence

## Objective

Add the deterministic recovery observation boundary that later Controller reasoning will use. Orc should expose bounded abnormal-state facts plus the legal recovery operations available for a task, without executing recovery or asking the model to infer lifecycle legality.

## Why

M03 completed the supervised normal-action path. Recovery is currently spread across requeue, non-convergence, validation, revision, workflow, and economy handling. M04 needs the same split used elsewhere: the kernel owns facts and legal operations; the Controller will later decide which legal operation is appropriate.

A key case is a blocked revision that still has valid REVISE lineage. Generic requeue must not erase or hide that distinction. Infrastructure failure, dependency blocking, and agent/economy exhaustion must also remain separate factual conditions.

## Scope

- Inventory the existing canonical recovery/requeue/unblock/revision/validation/economy seams.
- Add a bounded serializable recovery observation derived from canonical `ProjectOperations` / selected `OrcApp` reads.
- Include only recovery-relevant facts: lifecycle/queue phase, execution condition, blocker classification, validation state, current review verdict/currentness, actionable revision lineage, latest relevant execution facts, dependencies, and relevant agent/economy constraints.
- Add a small typed repository-grounded recovery-operation set.
- Add deterministic legality inspection for those operations.
- Preserve revision lineage explicitly so blocked revision work cannot be confused with fresh backlog work.
- Keep inspection side-effect free.

Do not dump full transcripts, repository contents, unbounded validation logs, or raw history into Controller-facing recovery types.

## Required scenarios

Tests must distinguish at least:

1. Blocked revision with valid REVISE/revision-contract lineage.
2. Infrastructure validation/execution failure, distinct from semantic revision failure.
3. Dependency-blocked task, with no recovery operation that bypasses dependencies.
4. No-eligible-agent or economy-exhaustion condition, separate from semantic review/revision state.
5. Ambiguous/unsupported abnormal state where no safe automatic recovery operation is exposed and later Controller/operator judgment is required.

## Recovery operation rules

The operation set must be based on current repository behavior, not speculative design. Inspect existing recovery APIs first and include only operations with a clear deterministic meaning or a narrow canonical legality seam.

The legality layer answers **what is allowed**, not **what is wise**. It must not rank options, select workers/models, decide retry value, or choose an operation.

If current Orc supports them cleanly, relevant concepts may include preserving/returning valid revision-required lineage, retrying an existing execution/revision path, canonical requeue/restart, retaining an infrastructure-blocked condition, or requiring an operator decision. These names are illustrative; do not manufacture operations to match them.

## Constraints

- Reuse canonical lifecycle/queue, validation, review/revision, execution-condition, dependency, and economy facts.
- Do not expose `Database`, SQLite, arbitrary commands, filesystem paths, provider payloads, worker handles, or native runtime types.
- Do not duplicate lifecycle legality in Controller code.
- Do not execute recovery in this task.
- Do not create automatic retry/continuation loops.
- Do not let failing validation become success.
- Preserve acceptance/cancellation/operator gates.
- Keep M03 behavior unchanged.

## Non-goals

- Controller recovery choice or execution.
- Automatic retry/recovery loops.
- Broad removal of existing recovery policy.
- Agent/model/economy selection judgment.
- Planning/Lead migration.
- Memory.
- Scheduler redesign.
- CLI/TUI/desktop recovery UX.
- Model/prompt/Qwen changes.
- GPU or Python work.

## Implementation notes

`RecoveryObservation` is the bounded, serializable, model-independent read
type. It contains `RecoveryObservationState`, `RecoveryCondition`, lifecycle
and queue phase, typed execution-condition and validation facts, bounded review
verdict/currentness, `RecoveryRevisionLineage` identity, one bounded latest
execution fact, bounded incomplete dependencies, blocker state/actionability,
and bounded agent/economy constraint categories. Provider output, rationale,
commands, paths, SQL, credentials, handles, and runtime objects are not
represented.

`RecoveryInspection` pairs that observation with one deterministic legality
result for each `RecoveryOperation`: `Requeue`, `ResumeRevision`, and
`AcknowledgeNonConvergence`. Each result is `Allowed` or a bounded typed
`Rejected` reason. The list is a stable operation inventory, not a ranking or
selection.

Canonical fact sources are `ProjectOperations::task_detail` (lifecycle,
queue, validation, review, blocker, execution, dependency, and scheduler
facts), its `RevisionLineageSummary` projection from the existing actionable
REVISE/revision-contract queries, `ProjectOperations::inspect_action` for
revision legality, and the narrow read-only
`ProjectOperations::inspect_requeue` seam mirroring the preconditions of
`Database::requeue_task`. Non-convergence legality is restricted to the exact
existing `non_convergence_replan_required` condition; the existing
`OrcApp::unblock_non_convergence`/database acknowledgement remains the
canonical mutation API but is not executed here.

Included operations have clear current repository semantics. Generic requeue
is included only as an inspected canonical operator operation and is rejected
for blocked tasks with actionable revision lineage so that lineage cannot be
discarded. Resume revision delegates legality to the existing Revise action
inspection. Non-convergence acknowledgement exposes only the existing exact
gate. Generic retry/restart, dependency satisfaction, infrastructure repair or
acknowledgement, agent/model/economy escalation, blocker resolution, and
operator choice are excluded because this repository has no single
deterministic recovery operation for them; ambiguous states therefore expose
no safe default operation.

The seven focused recovery tests cover blocked revision lineage, infrastructure
validation failure, dependency blocking, economy exhaustion, ambiguous blocked
state, non-convergence legality, serialization/bounds, and side-effect-free
inspection. Existing non-convergence, revision, infrastructure, dependency,
queue, economy, and requeue regression suites remain green. No recovery is
executed and no Controller authorization is minted by this task.

Judgment-heavy policy remains for M04-002+: choosing or ranking a recovery
operation, deciding retry/repair value and bounds, resolving dependencies,
selecting or escalating workers/models/economy, and deciding how unusual
infrastructure or repeated failures should be handled.

## Result

All required scenarios and validation passed. Production Controller
recommendation prompt/schema/parser semantics were unchanged, so Qwen was not
rerun. No M04-002 architectural blocker was found; the next seam is the later
Controller/operator policy that chooses among these already-inspected legal
operations without moving that judgment into the kernel.
