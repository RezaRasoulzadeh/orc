# M07-011 — Compose one selected Controller memory maintenance step

**Status:** Planned
**Milestone:** M07 — Supervised autonomy

## Objective

Compose the new M07-010 bounded maintenance-target selection with the existing M07-009 one-target maintenance chain into one explicit supervised operation that may select at most one current-project Project/Episodic target from caller-supplied current facts and then perform at most one canonical maintenance mutation under an existing finite M07-008 grant.

This task advances from caller-supplied target identity to Controller-selected target identity while keeping current facts explicit and caller-owned. It does not derive facts from workflow/task events, iterate over multiple candidates, scan in the background, or create a second orchestration loop.

## Repository-grounded context

M07-010 now provides `OrcApp::select_controller_memory_target(...)`, a read-only bounded judgment over canonical active current-project Project/Episodic candidates. It returns exactly `NoTarget` or `SelectTarget { target }` and validates selection against the exact bounded candidate set supplied to inference.

M07-009 already provides `OrcApp::maintain_controller_memory_once(...)` for one explicit `ControllerMemoryMaintenanceRequest`, composing M06-011 judgment → M06-009 proposal → M07-008 grant inspection → M06-009 execution with state-safe results and correct grant accounting.

The smallest remaining seam is therefore one application-level composition that reuses those two APIs directly: target selection first, then one explicit M06-011 maintenance request for the selected target using the same authoritative current facts.

## Scope

Add one capability-specific `OrcApp` API and the smallest state-safe typed result needed to compose exactly one selected maintenance attempt.

Required production order:

1. caller supplies one existing `ControllerMemorySelectionRequest`, one existing `ControllerMemoryMaintenanceGrant`, and one `LocalInferenceRuntime`;
2. call existing `select_controller_memory_target(...)` exactly once;
3. if selection returns `NoTarget`, stop successfully with no maintenance judgment, proposal, authorization, execution, or grant consumption;
4. if selection returns `SelectTarget { target }`, construct exactly one existing `ControllerMemoryMaintenanceRequest` for that exact target using the exact same `current_facts` from the selection request;
5. call existing `maintain_controller_memory_once(...)` exactly once with that request, the same supplied grant, and the same runtime;
6. map the existing M07-009 state-safe outcome into one bounded composition result without weakening or duplicating M07-009 legality.

Required behavior:

- at most one target-selection inference;
- at most one maintenance-judgment inference;
- therefore at most two Controller inference calls total per composed call;
- at most one M06-009 proposal;
- at most one M07-008 authorization mint;
- at most one M06-009 execution attempt;
- no retry after selection failure, maintenance failure, Keep, or mutation failure;
- no second target selection;
- no fallback to omitted candidates;
- no alternate target;
- no alternate maintenance proposal;
- no direct `MemoryService` mutation;
- no grant replenishment.

## Current-fact preservation

The exact bounded `current_facts` supplied by the caller to M07-010 must be reused unchanged for the selected target's M06-011 `ControllerMemoryMaintenanceRequest`.

Do not summarize, reinterpret, augment, reorder, infer, or derive additional facts between selection and maintenance. This preserves one authoritative evidence set across both Controller judgments and prevents deterministic application code from inventing maintenance evidence.

## Freshness and legality

Selection does not freeze target state. After selection, M07-009/M06-011 must re-resolve the exact selected `MemoryId` through the existing canonical path.

If the target becomes missing, non-active, cross-project, or otherwise invalid between selection and maintenance judgment, the existing M06-011/M07-009 rejection behavior must stop the composed operation before grant authorization. Do not cache a `MemoryRecord` from M07-010 and bypass fresh target resolution.

M07-008 and M06-009 remain authoritative for operation/kind/scope/mutation legality. This task must not duplicate or weaken their checks.

## Result semantics

Introduce the smallest state-safe public result type that distinguishes at minimum:

- `NoTarget`: selector chose no target; no maintenance call or grant consumption occurred;
- selected target was kept by M06-011/M07-009;
- selected target mutated successfully through the canonical M06-009 path;
- selection failed/rejected;
- maintenance composition failed/rejected after a valid target selection.

Where the selected target identity is useful to trusted callers, preserve it in the kept/mutated/rejected-after-selection outcome without allowing callers to construct a mismatch between the selected identity and the wrapped M07-009 result/error.

Do not create a universal capture/maintenance/autonomy result abstraction merely to remove duplication.

Public types must not make impossible states representable, including:

- mutation success wrapping a non-success M06-009 execution result;
- maintenance execution rejection wrapping canonical `Mutated`;
- independently supplied stage/error pairs that can disagree;
- a post-selection outcome paired with an arbitrary target unrelated to the selection result.

Reuse M07-009 state-safe wrappers where practical rather than re-exposing raw execution results.

## Grant accounting

Grant accounting remains entirely owned by M07-009/M07-008:

- `NoTarget`: zero consumption;
- selection request/input/runtime/output failure: zero consumption;
- selected target that M06-011 returns `Keep`: zero consumption;
- maintenance target freshness/validation failure before proposal: zero consumption;
- maintenance proposal rejection: zero consumption;
- maintenance grant rejection: zero consumption;
- successful authorization mint: exactly one unit consumed;
- post-mint fresh-validation/execution/storage failure: no refund.

The new composition layer must not inspect, decrement, refund, or replenish grant state directly.

## Invariants / requirements

- One explicit caller-supplied selection request per call.
- One existing maintenance grant per call.
- One runtime per call.
- At most one M07-010 selection call.
- At most one M07-009 maintenance call.
- At most two Controller inference calls total.
- Exactly the selected canonical `MemoryId` becomes the maintenance request target.
- Exactly the same caller-supplied current facts flow into both judgments.
- M07-010 remains the sole target-selection schema.
- M06-011 remains the sole Keep/Correct/Supersede/Remove judgment schema.
- M07-008 remains the maintenance permission boundary.
- M06-009 remains the sole durable-memory mutation path.
- No cached candidate record may substitute for fresh M06-011 target resolution.
- No automatic iteration over omitted/non-selected candidates.
- No retry/fallback/second orchestration loop.
- No provider token hard cap, Python, or model-specific behavior.

## Non-goals

- Deriving `current_facts` automatically from workflow, tasks, Plans, review, validation, recovery, transcript, or operator history.
- Workflow/lifecycle hooks.
- Background or periodic maintenance.
- Repeated target selection until a mutation happens.
- Batch maintenance.
- Iteration over omitted candidates.
- Automatic capture candidate derivation or capture execution.
- User/Experience/global maintenance.
- Semantic/vector retrieval, embeddings, or learned ranking.
- Grant persistence or new grant semantics.
- Changing M07-010 prompt/schema/bounds.
- Changing M06-011 prompt/schema/bounds.
- Changing M06-009/M07-008 legality.
- CLI/TUI/GUI integration.

## Acceptance criteria

1. One explicit `OrcApp` API composes one M07-010 target selection with at most one M07-009 maintenance call.
2. `NoTarget` performs no maintenance judgment and consumes zero grant units.
3. A selected target is passed to M07-009 through a freshly constructed canonical `ControllerMemoryMaintenanceRequest` using the exact same current facts.
4. A selected target can be kept with zero grant consumption or mutated once through M06-009 with exactly one successful authorization consumption.
5. Selection and all pre-mint maintenance failures consume zero; post-mint failure receives no refund.
6. The selected target is freshly re-resolved by existing M06-011/M07-009 logic; no candidate-record cache bypass exists.
7. One composed call performs at most two inference calls, one proposal, one authorization mint, and one execution attempt.
8. No retry, alternate target, omitted-candidate fallback, batch loop, direct mutation, workflow hook, or automatic current-fact derivation is introduced.
9. Public result types remain state-safe and cannot encode target/result or success/rejection mismatches.
10. Existing M07-010 and M07-009 behavior remains unchanged.
