# M09-003 — Capture reproducible full-surface Controller baseline

**Status:** Planned
**Milestone:** M09 — Controller specialization

## Objective

Add one opt-in, read-only real-model evaluation path that runs the canonical M09-002 full-surface specialization suite against the current local Qwen3 Controller runtime and emits a reproducible baseline report suitable for later candidate-vs-baseline comparison.

This task records baseline evidence only. It does not choose a trainer, transform the M09-001 snapshot into training records, define promotion thresholds, fine-tune a model, or change the default Controller model.

## Repository-grounded context

M09-001 provides the deterministic trainer-neutral Active experience snapshot.

M09-002 provides a deterministic typed evaluation suite covering all nine current inference-backed Controller capabilities with explicit semantic expectations, production-aligned validation, exact global/per-capability accounting, and a model-independent runtime boundary.

The repository already has an older ignored `ORC_QWEN3_GGUF` smoke path from M02 for the recommendation-only corpus. That path proves the native `LlamaCppRuntime` + user-supplied GGUF execution convention, but it predates the current full Controller capability surface.

Before M09 chooses a specialization backend or candidate promotion policy, it needs a stable measured baseline from the current default Controller model over the exact M09-002 suite. Otherwise later candidate comparison would lack pre-training evidence.

## Scope

Add an ignored, feature-gated real-model evaluation target over the existing M09-002 representative suite using the current local `LlamaCppRuntime` and the established `ORC_QWEN3_GGUF` convention.

The real-model path must execute the same production-aligned capability builders and semantic evaluator established by M09-002. Do not create a second scenario corpus or alternate expected-answer authority.

The runner/reporting boundary must make the baseline reproducible enough that a later candidate model can be evaluated against the same suite and compared without changing evaluation semantics.

## Baseline identity

Capture explicit baseline identity metadata sufficient to distinguish one evaluation run from another without embedding model weights or requiring network access.

At minimum record:

- evaluation schema version;
- exact suite schema version;
- stable suite/scenario count;
- model path identity in a privacy-safe/reproducible form appropriate to the existing local-runtime conventions;
- model/runtime configuration that can affect inference semantics, including context length and the production request parameters actually used by each capability;
- exact per-scenario result status;
- exact global aggregate counts;
- exact per-capability aggregate counts.

Do not persist secrets or arbitrary environment contents.

If a model-file digest is added, use a well-supported existing/native Rust dependency or repository capability and document exactly what bytes/identity it covers. Do not require hashing if repository evidence supports a simpler stable model identity boundary.

## Execution semantics

The real-model baseline must:

- use the canonical M09-002 representative suite;
- preserve its deterministic scenario order and explicit semantic expectations;
- route each scenario through the same production capability builder/runtime request path used by M09-002;
- evaluate typed semantics exactly as M09-002 does;
- record incorrect, runtime, parse, and validation failures without aborting later scenarios where the M09-002 evaluator supports non-aborting execution;
- report exact per-scenario, global, and per-capability results;
- remain read-only and execute no Controller intent or mutation.

Do not append evaluation-specific instructions that change the production prompt contract merely to improve score. The purpose is to measure current production behavior, not a separately prompted benchmark persona.

## Reproducible output

Provide one deterministic serializable baseline-report shape or deterministic serialization helper around the real-model evaluation result.

Repeated runs are not required to produce identical model answers if the underlying runtime is nondeterministic, but the report schema, scenario order, metadata fields, aggregate calculations, and serialization order must be deterministic for a fixed observed result set.

The runner should print or expose enough structured evidence to preserve:

- scenario ID;
- capability;
- status;
- expected semantic authority;
- observed semantic result when available;
- structured error/failure evidence when unavailable;
- aggregate totals.

Avoid dumping unbounded model output. Preserve bounded diagnostics where existing production/evaluation types already support them.

## Production-boundary constraints

Do not:

- change M09-002 scenario expectations to make Qwen pass;
- change production prompts, parsers, response schemas, temperatures, token limits, stop sequences, or capability semantics;
- add an evaluation-only prompt suffix like the older M02 smoke test used;
- execute Controller actions;
- mutate tasks, Plans, workflows, memory, experience examples, registry, or project state;
- write model weights;
- automatically create training examples from failures;
- consume M09-001 records as expected answers;
- choose a trainer/backend;
- convert the snapshot to ChatML/prompt-completion/other trainer formats;
- split, sample, balance, deduplicate, rank, or weight the dataset;
- define a pass threshold or promotion gate;
- change the default Controller model;
- add provider fallback, provider token hard caps, embeddings, or Python runtime dependencies.

## Baseline artifact boundary

The canonical baseline result should remain a typed in-memory/report value plus deterministic test/console serialization unless an existing repository persistence boundary clearly justifies a file artifact.

Do not add new canonical database tables merely to store benchmark runs in this task.

A checked-in golden result from one developer machine is not required and should not become semantic authority. Scenario expectations in M09-002 remain the authority; real-model results are evidence.

## Acceptance criteria

1. An ignored llama-cpp feature-gated real-model path runs the exact M09-002 full-surface representative suite using a user-supplied `ORC_QWEN3_GGUF` model.
2. All nine current inference-backed Controller capabilities are exercised through the same production-aligned builder/evaluator path as deterministic M09-002 evaluation.
3. The runner does not alter prompts/runtime parameters or add benchmark-specific instructions to improve model behavior.
4. A versioned typed baseline report includes reproducible suite/model/runtime identity metadata plus exact per-scenario, global, and per-capability results.
5. Incorrect, runtime, parse, and validation failures are preserved as evidence without silently converting them into passes.
6. Baseline execution performs zero canonical state mutation and no Controller action execution.
7. Deterministic report validation/serialization is covered without requiring a real model in normal test runs.
8. No training, dataset transformation, promotion threshold, model-default change, or production inference behavior change is introduced.

## Required validation

Add deterministic tests for at least:

- baseline report schema/version validation;
- canonical M09-002 suite identity/count captured correctly;
- all nine exact capabilities represented;
- deterministic report/scenario/capability ordering;
- exact global/per-capability aggregate reuse or validation;
- bounded structured failure evidence;
- malformed baseline metadata fails closed;
- deterministic serialization for a fixed synthetic observed report;
- no storage/`OrcApp` mutation dependency;
- existing M09-002 deterministic evaluation regressions;
- existing M02 real-model smoke compile regression;
- `cargo test --lib`;
- `cargo test --features llama-cpp --lib`;
- `cargo test --tests` or the relevant full integration set;
- normal and llama-cpp `cargo clippy --all-targets -- -D warnings`;
- `cargo fmt --check`;
- `git diff --check`.

Also compile the new ignored real-model target with `--features llama-cpp --no-run`.

For completion evidence, execute the new ignored full-surface baseline test against the current user-supplied Qwen3 8B GGUF when `ORC_QWEN3_GGUF` is available. The task may still be code-complete if the model file is unavailable in the execution environment, but the absence must be reported explicitly and no baseline scores may be invented.

## Completion evidence

Report changed files, baseline/report types and schema version, model/runtime identity fields, exact suite reuse proof, proof that no prompt/runtime semantics changed, per-scenario/global/per-capability reporting behavior, failure preservation, zero-write evidence, deterministic validation results, real-Qwen execution result if available, and any architectural mismatch.
