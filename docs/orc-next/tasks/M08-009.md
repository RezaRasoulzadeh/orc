# M08-009 — Add explicit typed curation for Controller memory maintenance judgment

**Status:** Planned
**Milestone:** M08 — Experience dataset

## Objective

Add one capability-local curation adapter for an already-produced Controller memory-maintenance judgment, projecting the existing typed `ControllerMemoryMaintenanceInput` and canonical `ControllerMemoryMaintenanceResult` into one M08-001 experience example under explicit trusted verification metadata.

Curate the maintenance judgment itself only. Later mutation proposal validation, maintenance grants, mutation execution, selected-target composition, and durable memory state are downstream boundaries and must remain outside the reasoning target.

## Repository-grounded context

`src/controller_memory_maintenance.rs` already exposes a bounded typed read-only reasoning boundary:

- `ControllerMemoryMaintenanceInput` contains the exact maintenance request, one already-resolved canonical `MemoryRecord` target, and bounded advisory `ControllerMemoryContext`;
- `ControllerMemoryMaintenanceInput::validate()` verifies the request, exact request/target identity match, canonical target validity, memory context, and production target/input bounds;
- `ControllerMemoryMaintenanceResult` has exactly two outcomes: `Keep` or `ProposeMutation { intent }`;
- `ControllerMemoryMaintenanceResult::validate(input)` validates the mutation intent and requires any proposed mutation to target the exact selected record;
- only `Correct`, `Supersede`, or `Remove` are allowed; `Create` is rejected;
- `Correct` and `Supersede` replacements must preserve target kind, scope, and subject;
- maintenance inference is read-only and does not authorize, execute, persist, retarget, or scan memory.

M08-008 completed curation of the preceding memory-capture judgment. M08-009 should extend the same narrow adapter pattern to the next clean typed judgment boundary.

## Scope

Add one memory-maintenance-specific typed curation request and the smallest `OrcApp` API needed to persist one explicitly verified maintenance judgment example.

The request must accept:

- one existing `ControllerMemoryMaintenanceInput`;
- one observed `ControllerMemoryMaintenanceResult`;
- one explicit accepted/expected `ControllerMemoryMaintenanceResult`;
- explicit `ControllerExperienceVerificationBasis`;
- explicit M08 outcome and quality metadata;
- M08 provenance through the existing M08-001 type;
- correction metadata only when observed and accepted canonical outputs differ.

Do not accept a caller-controlled capability identifier.

## Canonical capability

Use fixed code-owned capability identifier:

`controller.memory_maintenance`

The caller must not be able to override it.

## Canonical input projection

The exact supplied `ControllerMemoryMaintenanceInput` is the dataset input authority.

Before projection:

- call production `ControllerMemoryMaintenanceInput::validate()`;
- serialize the exact typed input deterministically;
- preserve exact request packet, requested target identity, bounded current facts, exact resolved target record, and bounded memory context;
- do not re-read current memory storage to refresh or replace the target;
- do not resolve another target;
- do not derive current facts from workflow/task/log state;
- do not summarize, reorder, enrich, truncate, or infer missing facts.

No maintenance inference call is permitted in the curation adapter.

## Canonical output projection

The existing `ControllerMemoryMaintenanceResult` is the dataset output authority.

Observed and accepted values must both pass existing production validation against the exact supplied input:

`ControllerMemoryMaintenanceResult::validate(&input)`

Persist the exact accepted result JSON as M08 `accepted_output`.

For `Keep`, preserve the canonical result exactly.

For `ProposeMutation`, preserve the complete canonical `ControllerMemoryMutationIntent`. Production validation remains authoritative that:

- the intent targets exactly `input.target.id`;
- only `Correct`, `Supersede`, and `Remove` are valid maintenance proposals;
- `Create` is invalid;
- `Correct`/`Supersede` replacement kind, scope, and subject exactly match the resolved target.

Do not replace the reasoning result with:

- mutation proposal validation;
- maintenance grant decisions;
- `ControllerMemoryMaintenanceStepResult`;
- mutation execution outcome;
- resulting/superseded/removed durable `MemoryRecord`;
- selected-target composition result;
- free-form explanation.

## Target and mutation boundary

The supplied resolved target is authoritative for this reasoning example.

M08-009 must not:

- enumerate/select another target;
- invoke `ControllerMemorySelectionBuilder`;
- resolve the target from storage;
- authorize or execute a mutation;
- call the maintenance grant path;
- call the composed maintenance-step path;
- use later durable memory state to redefine the accepted result.

Maintenance-target selection remains a separate later M08 seam.

## Correction semantics

Compare exact canonical serialized observed and accepted `ControllerMemoryMaintenanceResult` values after validating both against the same exact input.

If observed == accepted:

- correction metadata must be absent;
- outcome must satisfy valid non-correction M08-001 semantics;
- no correction evidence is manufactured.

If observed != accepted:

- outcome must be `Corrected`;
- explicit valid correction metadata is required;
- `correction.original_output` must exactly equal the canonical observed maintenance result JSON;
- M08 `accepted_output` must exactly equal the canonical accepted result JSON.

Explicit corrections may change among valid typed outcomes, including `Keep` to a valid target-bound proposal, a valid proposal to `Keep`, or one valid target-bound maintenance proposal to another. Both observed and accepted results must independently pass production validation against the same exact input.

Do not infer correction from later proposal/grant/execution/persistence/maintenance outcomes.

## Verification boundary

Verification remains explicit and caller-owned.

Do not automatically treat any of these as sufficient verification or correction evidence:

- successful mutation-proposal validation;
- maintenance grant issuance;
- successful `Correct`, `Supersede`, or `Remove` execution;
- later target lifecycle/state;
- later retrieval;
- subsequent maintenance;
- selected-target workflow completion;
- task/workflow success or failure.

These are downstream facts, not automatic labels for the reasoning example.

## Production order

1. validate exact `ControllerMemoryMaintenanceInput`;
2. validate observed `ControllerMemoryMaintenanceResult` against the exact input;
3. validate accepted `ControllerMemoryMaintenanceResult` against the exact input;
4. deterministically project exact input/observed/accepted JSON;
5. enforce correction semantics;
6. construct exactly one `ControllerExperienceExampleDraft` with fixed capability;
7. delegate verification/outcome/quality/provenance/bounds validation to M08-001;
8. persist only through existing `OrcApp::create_controller_experience_example(...)`.

At most one row may be written per call. Any validation/projection failure must write zero rows.
