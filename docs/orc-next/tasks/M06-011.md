# M06-011 — Add supervised Controller memory maintenance judgment

**Status:** Done
**Milestone:** M06 — Persistent memory

## Objective

Add the smallest read-only Controller judgment that can inspect one explicitly selected active memory record in bounded canonical memory context and decide whether it should be kept unchanged or proposed for one canonical M06-009 maintenance mutation (`Correct`, `Supersede`, or `Remove`) without authorizing or executing that mutation.

This task completes the missing judgment counterpart to M06-010 capture. It does not add automatic scanning, background consolidation, autonomous cleanup, or semantic retrieval.

## Repository-grounded context

M06-001 already provides canonical durable memory lifecycle/history and `correct`, `supersede`, and `remove` operations. M06-002 provides bounded active-memory projection through `ControllerMemoryContext`, including stable IDs, kinds, scopes, authority, provenance, confidence, lifecycle, and supersession linkage. M06-009 already defines typed `ControllerMemoryMutationIntent::{Correct, Supersede, Remove}`, deterministic target/scope/project legality, one-shot authorization, fresh-state revalidation, and canonical execution through `MemoryService`. M06-010 adds explicit-candidate capture judgment for `Create`.

The remaining M06 judgment seam is supervised maintenance over existing memory. Reuse those canonical abstractions rather than creating a second consolidation store, mutation schema, or workflow engine.

## Scope

Introduce a capability-local, bounded, read-only memory-maintenance request/input/result.

Required behavior:

- accept exactly one explicitly selected active target memory identity supplied by trusted Orc/application code;
- resolve that target from canonical current memory state before inference and include its bounded typed record data in the maintenance input;
- combine the explicit target with existing canonical `ControllerMemoryContext` only to judge contradiction, duplication, obsolescence, or whether the target remains useful;
- current canonical target state and explicit current operator/project facts supplied with the request outrank historical/advisory memory;
- inference returns exactly one of two outcomes: `Keep` or `ProposeMutation`;
- `ProposeMutation` contains exactly one existing canonical M06-009 `ControllerMemoryMutationIntent` limited to `Correct`, `Supersede`, or `Remove` for the explicit target;
- validate returned target identity, operation, replacement kind/scope/subject, bounds, and structure deterministically before exposing the result;
- a successful result remains only a proposal candidate; authorization/execution must occur separately through M06-009;
- inference is read-only and does not mutate memory or history.

## Maintenance judgment rules

Use the three maintenance operations deliberately:

- `Correct`: the active record is materially wrong and the supplied current facts establish the corrected value while preserving the same memory subject/identity lineage semantics.
- `Supersede`: the active record was valid historically but a newer durable value/decision replaces it.
- `Remove`: the active record should no longer participate as durable memory and no replacement should become active.
- `Keep`: no supported maintenance action is warranted.

Do not infer a maintenance mutation merely because two memories are stylistically similar. Prefer `Keep` when evidence is ambiguous. Historical Episodic/Experience memory cannot override explicit current project/operator facts. Project-local evidence must not be used to rewrite unrelated global User/Experience memory.

## Invariants / requirements

- Reuse `ControllerMemoryContext`; do not add another retrieval model.
- Reuse M06-009 `ControllerMemoryMutationIntent`; do not add a second maintenance/consolidation mutation schema.
- Keep the request capability-specific; do not create a universal Controller state/request packet.
- The model receives no `MemoryService`, `Database`, registry, filesystem, workflow, authorization, or execution handle.
- The explicit target must exist, be active, belong to the current project when project-scoped, and be resolved by trusted Orc code before inference.
- Model output cannot target a different memory identity.
- `Correct`/`Supersede` replacements must preserve canonical target kind, scope, and subject requirements already enforced by M06-009; scope/kind/project boundaries remain authoritative.
- `Remove` may only target the explicit selected record.
- Existing M06-009 legality remains authoritative and is re-entered as a separate proposal step.
- Request/current-facts payload, target representation, memory context, and combined inference input are independently bounded; combined serialized input maximum is 64 KiB.
- Structured output/result is bounded and schema-constrained before use, including exact nested enum/object shapes rather than relying on permissive serde field dropping.
- No automatic enumeration of all durable memory for maintenance.
- No implicit maintenance triggered by capture, task completion, reviews, transcripts, lifecycle events, or startup.
- No batch mutations or multi-record atomic consolidation in this task.
- No semantic/vector retrieval, embeddings, learned ranking, background loop, model-specific domain behavior, or Python.

## Non-goals

- Automatically deciding when to run maintenance judgment.
- Periodic/background memory cleanup.
- Scanning the whole memory store for duplicates.
- Batch consolidation or merge-many operations.
- Automatic authorization/execution.
- Creating new memory from maintenance; M06-010 owns capture/Create judgment.
- Semantic search, vector DBs, embeddings, or learned retrieval/ranking.
- Transcript/chat ingestion.
- Interface UX.
- Training/fine-tuning dataset generation.

## Acceptance criteria

1. A bounded capability-local maintenance input accepts exactly one explicit active target plus bounded current facts and canonical `ControllerMemoryContext`, with no persistence handles exposed to inference.
2. Trusted application code resolves and validates the current target before inference; stale, missing, historical, or cross-project targets are rejected before runtime invocation.
3. Controller output is exactly `Keep` or one `ProposeMutation` containing canonical M06-009 `Correct`, `Supersede`, or `Remove` intent for that same target.
4. Model output cannot retarget another memory or change target kind/scope/subject illegally; returned intents are structurally and deterministically validated before exposure.
5. Current canonical target state and explicit current operator/project facts outrank contradictory historical/advisory memory.
6. A separate application seam can pass the proposed intent through the existing M06-009 proposal legality boundary; maintenance inference itself cannot authorize, execute, or persist it.
7. Independent component bounds plus a 64 KiB combined input bound reject oversized input before runtime invocation; structured output is bounded and exact-schema validated.
8. `Keep`, `Correct`, `Supersede`, and `Remove` semantics are covered without introducing automatic/background scanning, batch consolidation, or a second mutation workflow.
