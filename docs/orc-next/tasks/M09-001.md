# M09-001 — Add deterministic trainer-neutral Controller dataset snapshot

**Status:** Done
**Milestone:** M09 — Controller specialization

## Objective

Add one deterministic, read-only snapshot/export boundary over the canonical Active Controller experience dataset so M09 can hand a stable versioned dataset artifact to later specialization/evaluation tooling without introducing trainer-specific transforms or specialization policy.

This task defines the dataset handoff only. It does not fine-tune a model, split/balance/sample examples, choose a trainer, or change Controller inference.

## Repository-grounded context

M08 is complete:

- M08-001 established canonical typed/versioned Controller experience examples in the global registry;
- M08-002 through M08-010 added explicit capability-local curation for every current inference-backed Controller judgment boundary;
- M08-011 added deterministic complete-dataset inventory over canonical persisted metadata.

The next specialization prerequisite is a stable trainer-neutral representation of the Active curated examples. D-006 requires controlled periodic learning from curated verified decisions/corrections/outcomes. D-007 keeps Orc runtime Rust/native and treats training/export as a separate concern rather than a Python runtime dependency.

## Scope

Add a versioned typed dataset snapshot representation and one explicit read-only `OrcApp` API that returns the complete Active canonical Controller experience dataset in deterministic order.

The snapshot must be trainer-neutral and preserve canonical M08 example content exactly rather than translating it into prompt/completion/chat formats.

## Canonical snapshot contents

The snapshot must contain:

- snapshot schema version;
- ordered examples;
- enough deterministic metadata to validate completeness and identity of the snapshot.

Each example entry must preserve the canonical persisted M08 fields required for later specialization/evaluation handoff, including:

- example identity;
- example schema version;
- exact capability;
- exact `input` JSON;
- exact `accepted_output` JSON;
- verification basis;
- provenance;
- correction metadata when present;
- outcome;
- quality;
- created timestamp;
- lifecycle.

Only Active examples belong in the specialization snapshot.

## Deterministic ordering

Use one code-owned deterministic order that does not depend on SQLite incidental row order or caller input. Prefer ascending canonical example ID unless repository evidence requires a stronger key.

Repeated snapshot reads against unchanged storage must return byte-equivalent serialized snapshot content.

## Data authority

Canonical persisted M08-001 global-registry rows are the sole authority.

Do not:

- read runtime `MemoryKind::Experience`;
- rebuild examples from tasks/runs/reviews/workflows;
- reinterpret capability-specific payloads;
- synthesize missing metadata;
- infer quality/readiness;
- silently skip malformed rows.

Every selected persisted row must pass canonical typed M08 validation. Corrupt or unsupported persisted data must fail closed.

## Integrity

Add deterministic snapshot validation covering at least:

- supported snapshot schema version;
- all entries are Active;
- positive unique example IDs;
- deterministic strict ordering;
- canonical M08 example validation for every entry;
- exact snapshot count equals number of entries;
- no duplicate examples.

If a deterministic content digest is added, it must use an existing well-supported Rust/native dependency or standard repository capability and must be computed over one explicitly defined canonical serialization. Do not add hashing merely for aesthetics; count + deterministic content may be sufficient for this task.

## API boundary

Expose one explicit read-only `OrcApp` API returning the complete trainer-neutral snapshot.

The caller must not provide:

- SQL;
- arbitrary ordering;
- capability aliases;
- lifecycle overrides;
- sampling/splitting/balancing rules;
- trainer format settings.

Do not write a filesystem export file in the core API unless an existing repository interface clearly requires one. The canonical core result is the typed in-memory snapshot.

## Acceptance criteria

1. One explicit read-only `OrcApp` API returns a typed versioned snapshot of the complete Active canonical Controller experience dataset.
2. Empty Active dataset returns a valid empty snapshot.
3. Every Active canonical row is represented exactly once and every Retired row is excluded.
4. Canonical M08 fields are preserved exactly without capability-specific transformation.
5. Ordering is stable and deterministic.
6. Repeated reads over unchanged storage serialize identically.
7. Malformed/unsupported persisted rows fail closed.
8. Snapshot construction performs zero writes and no inference.
9. No trainer-specific, split/balance/sample/rank/weight policy is introduced.
