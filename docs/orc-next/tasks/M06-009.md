# M06-009 — Establish supervised Controller memory mutation boundary

**Status:** Planned
**Milestone:** M06 — Persistent memory

## Objective

Establish the smallest safe boundary through which Controller judgment can propose durable memory changes while the deterministic kernel retains validation, authorization, scope enforcement, lifecycle invariants, and canonical mutation.

This is the prerequisite for later Controller memory capture/consolidation. Do not add autonomous memory writing or consolidation inference in this task.

## Repository-grounded context

M06-001 already provides canonical typed memory storage and `MemoryService` operations for create/get/list/correct/supersede/remove/history across project and global persistence authorities. M06-002 provides bounded read-only `ControllerMemoryContext`. M06-003 through M06-008 now supply that context to the existing Controller judgment capabilities.

The repository already has the architectural pattern needed for safe mutation: `src/controller_actions.rs` separates typed Controller proposals from trusted one-shot authorization and canonical execution. Memory should gain an equivalent narrow boundary rather than giving the model `MemoryService`, database, registry, filesystem, or mutation handles.

## Scope

Add a typed supervised memory-mutation boundary over the existing M06-001 APIs.

Required behavior:

- define bounded typed Controller memory mutation intents for the existing durable operations that are appropriate at this boundary: create, correct/supersede, and remove;
- intents carry only bounded declarative memory data and stable target identity where required; they do not carry database handles, persistence locations, SQL, commands, or execution context;
- deterministically validate kind/scope/project binding, payload/provenance/confidence bounds, target identity, lifecycle eligibility, and current project ownership before authorization/execution;
- introduce a trusted one-shot, non-serializable authorization minted by Orc/application code for exactly one validated memory intent;
- execution consumes the authorization, revalidates against fresh canonical memory state, and performs the mutation only through existing `MemoryService`/M06-001 storage APIs;
- stale, mismatched, replayed, cross-project, invalid-lifecycle, or otherwise illegal intents fail without mutation;
- preserve existing global authority: User/Experience remain global; Project/Episodic remain exact-project bound;
- return canonical typed mutation results sufficient for supervised callers to inspect what changed;
- no local-model inference is required in this task.

## Invariants / requirements

- Controller proposes; kernel authorizes and mutates.
- Reuse M06-001 memory types and operations; do not create a second persistence or lifecycle model.
- Reuse the M03 authorization design where it fits, but keep memory authorization distinct from task-action authorization.
- Authorization is opaque/non-serializable, scoped to one exact validated intent, and consumed on execution.
- Fresh canonical validation occurs at execution so authorization cannot make stale state legal.
- No model-facing code receives `MemoryService`, `Database`, registry, filesystem, workflow, or arbitrary command access.
- Correction/supersession/removal lineage and history remain M06-001 authoritative.
- Project/global persistence routing remains unchanged.
- No automatic capture from Controller outputs, Plans, reviews, tasks, transcripts, or worker results.
- No consolidation/deduplication judgment yet.
- No semantic/vector retrieval, embeddings, learned ranking, or model-specific behavior.
- No Python.

## Non-goals

- Deciding what should be remembered.
- Autonomous or implicit memory writes.
- Memory consolidation/deduplication inference.
- Adding memory-write tools directly to local-model prompts.
- Changing `ControllerMemoryContext` retrieval/ranking.
- Semantic search/embeddings.
- Changing task/Plan/workflow action authorization.
- CLI/TUI/GUI memory management UX.

## Acceptance criteria

1. Bounded typed memory mutation intents exist over canonical M06-001 create/correct-or-supersede/remove operations.
2. Deterministic legality validates scope, project binding, target identity/current lifecycle, payload metadata and current ownership before mutation.
3. Trusted Orc code can mint an opaque one-shot authorization for exactly one validated intent.
4. Execution consumes authorization, revalidates fresh canonical state, and mutates only through existing M06-001 memory APIs.
5. Mismatched/replayed/stale/cross-project/invalid intents cannot mutate memory.
6. User/Experience global and Project/Episodic project-bound persistence authority is preserved.
7. Existing correction/supersession/removal history and lineage semantics remain canonical and transactional.
8. No inference, autonomous capture, consolidation, semantic retrieval, or unrelated workflow redesign is introduced.

## Required validation

- focused intent serialization/validation tests for each supported operation;
- project/global kind-scope legality matrix;
- target ownership and lifecycle legality tests;
- authorization is non-serializable/opaque and bound to one exact intent;
- mismatched authorization rejection;
- one-shot/replay rejection;
- stale-state revalidation before execution;
- cross-project mutation rejection;
- create/correct-or-supersede/remove happy paths proving canonical M06-001 history/lineage;
- global memory survives project DB reset and project memory remains project-bound;
- failure paths prove no partial mutation;
- existing M06 memory regressions;
- `cargo test --lib`;
- `cargo test --features llama-cpp --lib`;
- `cargo fmt --check`;
- normal and feature `cargo clippy --all-targets -- -D warnings`;
- `git diff --check`.

No real-Qwen evaluation is required because this task adds no inference or prompt behavior.
