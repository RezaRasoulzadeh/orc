# M07-001 — Establish explicit bounded Controller continuation grants

**Status:** Planned
**Milestone:** M07 — Supervised autonomy

## Objective

Establish the smallest deterministic supervision boundary that lets a trusted operator/application grant Orc permission to continue a bounded set of routine Controller task actions without separately approving every action, while preserving the existing M03 one-shot `ControllerActionAuthorization`, fresh legality checks, canonical execution paths, workflow limits, and explicit user acceptance boundary.

This task creates the permission/budget contract for later supervised continuation. It does **not** add an autonomous execution loop.

## Repository-grounded context

`src/controller_actions.rs` already provides canonical typed `ControllerActionIntent::{Dispatch, SemanticReview, Revise, Accept}`, deterministic legality inspection, trusted one-shot exact-intent `ControllerActionAuthorization`, fresh legality re-check immediately before canonical mutation, and trusted execution context outside model data.

`src/workflow.rs` already owns the authoritative restart-safe continuation path and finite deterministic bounds such as `max_task_revisions`, `max_plan_revisions`, and `max_transitions`. Its default acceptance policy remains user-controlled.

The missing M07 seam is explicit operator permission for routine continuation. Do not replace M03 authorization, duplicate workflow execution, or let the model self-authorize.

## Scope

Add a typed bounded continuation-grant model and deterministic inspection boundary.

Required behavior:

- a continuation grant is created only by trusted Orc/operator/application code; the local model cannot mint, widen, mutate, or serialize itself into a grant;
- bind each grant to exactly one current project and an explicit finite action budget;
- explicitly enumerate which existing `ControllerActionKind` values are permitted by the grant;
- for M07-001, permit only routine `Dispatch`, `SemanticReview`, and `Revise` actions;
- `Accept` is not grantable in this task and remains explicitly authorized by the existing user/application path;
- inspect one exact existing `ControllerActionIntent` against the grant plus current canonical project/task state without mutation;
- reject exhausted, wrong-project, unsupported-action, malformed, and stale/inapplicable grants deterministically;
- successful inspection may produce a trusted one-shot authorization for that exact intent by reusing the existing M03 authorization seam; it must not execute the action;
- consume/decrement the finite continuation budget only when a one-shot authorization is successfully minted for an allowed exact intent, with deterministic state preventing unlimited reuse;
- fresh M03 legality inspection at actual execution remains authoritative; a grant never makes an otherwise illegal action legal;
- existing workflow revision/transition limits and economy/quota facts remain independent hard facts and are not overridden by the grant.

## Grant semantics

The grant is operator supervision, not model judgment.

At minimum it must carry:

- stable project binding;
- explicit allowed action kinds from the routine subset;
- a positive finite remaining-action budget;
- inspectable lifecycle/state sufficient to distinguish active from exhausted/revoked/invalid grants;
- stable identity or equivalent trusted state needed to prevent budget reset/replay through value copying.

Choose the smallest canonical persistence/ownership seam already available. If restart-safe use requires persistence, persist only the grant facts needed for deterministic supervision; do not create a second workflow or authorization database.

## Invariants / requirements

- Reuse `ControllerActionIntent`, `ControllerActionKind`, `ControllerActionAuthorization`, `ControllerActionIntent::inspect`, and `OrcApp::execute_authorized_controller_action`.
- Do not add a second action intent schema or canonical mutation path.
- Do not expose authorization constructors, persistence handles, workflow handles, provider credentials, filesystem access, or command execution to the model.
- The model cannot request `allowed=true`, a larger budget, new action kinds, another project, or grant renewal as part of action inference.
- `Accept` must be deterministically rejected by the continuation-grant boundary in M07-001.
- A grant cannot bypass scheduler/agent permissions, quota availability, task lifecycle legality, review evidence, validation state, revision feedback requirements, or workflow limits.
- Minted M03 authorization remains exact-intent and one-shot.
- Grant budget is finite; zero means no authorization may be minted.
- Failed inspection must not consume budget.
- Successful authorization mint must consume exactly one grant action budget unit atomically with the grant-state change required to prevent replay/reset.
- Execution failure after authorization mint does not silently restore grant budget in this task; later retry/recovery remains explicit Controller judgment.
- No provider token hard cap is introduced. Existing economy/quota observability remains canonical.
- No autonomous loop, background execution, timer, polling, automatic task enumeration, or automatic memory capture/maintenance invocation.
- No model-specific behavior or Python.

## Non-goals

- Automatically choosing when Orc should continue.
- Automatically executing a sequence of actions.
- Granting automatic `Accept`.
- Automatic Plan approval or operator-decision resolution.
- New workflow engine or scheduler.
- Replacing M03 authorization.
- Replacing existing workflow revision/transition bounds.
- Token-budget enforcement.
- Automatic memory capture/maintenance.
- UI/CLI policy design beyond the smallest API needed for deterministic tests.

## Acceptance criteria

1. A trusted typed continuation grant exists with exact project binding, explicit routine allowed actions, finite budget, and deterministic active/exhausted/revoked-or-equivalent state.
2. Only `Dispatch`, `SemanticReview`, and `Revise` may be grantable; `Accept` is rejected deterministically.
3. One exact existing `ControllerActionIntent` can be inspected against a grant and current canonical legality without mutation.
4. Allowed inspection can mint only the existing exact-intent one-shot M03 `ControllerActionAuthorization`; it cannot execute the action.
5. Successful mint consumes exactly one finite budget unit with replay/reset protection; rejected inspection consumes none.
6. Wrong-project, exhausted, invalid/stale, unsupported-action, or canonically illegal intents cannot mint authorization.
7. The subsequent existing M03 execution boundary still performs fresh legality and canonical mutation; grants do not bypass permissions, quota/economy facts, lifecycle, validation/review evidence, or workflow limits.
8. No autonomous continuation loop, automatic acceptance, background work, or second workflow/action system is introduced.
