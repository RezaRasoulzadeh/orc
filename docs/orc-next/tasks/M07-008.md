# M07-008 — Establish explicit bounded Controller memory maintenance grants

**Status:** Planned
**Milestone:** M07 — Supervised autonomy

## Objective

Establish the smallest explicit finite permission boundary required before M06-011 Controller memory-maintenance judgment can later be composed with durable Correct/Supersede/Remove execution without bypassing the existing M06-009 supervised mutation boundary.

This task adds permission only. It does **not** select maintenance targets automatically, invoke maintenance judgment automatically, execute maintenance automatically, scan memory, or integrate maintenance into workflow/background loops.

## Repository-grounded context

M06-011 already owns bounded read-only maintenance judgment over one explicitly selected active target. It can return only `Keep` or one exact-target M06-009 `Correct`, `Supersede`, or `Remove` intent and cannot authorize or execute it.

M06-009 remains the sole canonical durable-memory mutation boundary: validated proposal, deterministic legality, exact one-shot authorization, fresh validation, and mutation through `MemoryService`.

M07-006/M07-007 established a separate permission/composition domain for capture Create. That grant must not be broadened to maintenance because Create and maintenance have different operation and target legality. Likewise `ControllerContinuationGrant` remains task-action-specific.

The missing seam is therefore a capability-specific finite maintenance permission that may mint the existing M06-009 authorization for one already validated, eligible project-bound maintenance proposal.

## Scope

Add one opaque in-process `ControllerMemoryMaintenanceGrant` (exact name may follow source conventions) and the smallest `OrcApp` creation/inspection seam.

Required behavior:

- trusted `OrcApp` code creates the grant for the current positive project ID;
- opaque and non-serializable;
- positive finite authorization budget with hard maximum 128 unless a smaller existing constraint is clearly required;
- cloned handles share the same mutable budget/lifecycle state;
- lifecycle at minimum Active / Exhausted / Revoked;
- maintenance operations only: `Correct`, `Supersede`, `Remove`;
- `Create` is impossible through this grant;
- only project-bound `MemoryKind::Project` and `MemoryKind::Episodic` targets for the exact current project are eligible;
- `MemoryKind::User` and `MemoryKind::Experience` remain excluded from automatic-capable maintenance permission;
- inspection accepts one already validated canonical `ControllerMemoryMutationProposal`;
- exact proposal project binding, operation, target identity, target kind/scope, and current project are checked deterministically before authorization;
- replacement data for Correct/Supersede remains subject to existing M06-009 target kind/scope/subject legality; do not duplicate or weaken it;
- successful inspection mints the existing exact M06-009 `ControllerMemoryMutationAuthorization` and consumes exactly one unit;
- rejected inspection consumes zero;
- exhausted/revoked/wrong-project/global/Create/invalid/ineligible proposal returns no authorization and consumes zero;
- execution remains exclusively `OrcApp::execute_authorized_controller_memory_mutation(...)` with existing fresh validation and `MemoryService` mutation;
- post-mint execution/fresh-validation/storage failure receives no refund;
- grant is in-process only and is never persisted or reconstructed after restart.

## Why this is a separate grant

Do not broaden `ControllerMemoryCaptureGrant` or `ControllerContinuationGrant` into universal Controller permissions. Routine task actions, durable capture Create, and durable maintenance are distinct capability domains with different legal operation sets and risk boundaries.

Reuse the finite explicit-permission pattern and the existing M06-009 authorization type, but do not share action enums or execution code across domains.

## Invariants / requirements

- M06-009 remains the sole canonical mutation legality/authorization/execution path.
- M06-011 remains the sole maintenance judgment schema.
- The grant contains no runtime, `MemoryService`, database, filesystem, workflow, or mutation handle.
- The model never sees, constructs, extends, revokes, or inspects grants.
- No Create authorization can be minted through maintenance permission.
- No User/Experience authorization can be minted through maintenance permission.
- Correct/Supersede/Remove must target an exact project-bound Project/Episodic record in the grant's project.
- One successful exact authorization mint consumes exactly one unit.
- Pre-mint rejection consumes zero.
- Post-mint execution failure is not refunded.
- Clones cannot reset budget or revocation.
- Budget exhaustion and revocation are deterministic and observable.
- No provider token hard cap, Python, or model-specific behavior.

## Non-goals

- Automatically invoking `judge_controller_memory_maintenance()`.
- Automatically selecting/enumerating maintenance targets.
- Composing judgment through execution; that is a later one-step task.
- Global User/Experience maintenance permission.
- Capture/Create permission.
- Workflow or lifecycle hooks.
- Periodic/background memory cleanup.
- Batch consolidation or multi-record mutation.
- Grant persistence/restart reconstruction.
- Semantic/vector retrieval, embeddings, or learned ranking.
- CLI/TUI/GUI integration.

## Acceptance criteria

1. Trusted application code can create a finite project-bound maintenance grant with observable remaining budget and lifecycle.
2. It can authorize only an already validated M06-009 Correct/Supersede/Remove proposal targeting exact-current-project Project/Episodic memory.
3. Successful inspection returns the existing M06-009 one-shot authorization and consumes exactly one unit.
4. Create, User/Experience, wrong-project, invalid-scope, revoked, exhausted, or otherwise ineligible proposals mint nothing and consume zero.
5. M06-009 execution remains unchanged and authoritative.
6. Post-mint failure is not refunded.
7. Shared handles cannot reset budget or revocation state.
8. Grant state is non-serializable/in-process only and existing capture/task-continuation APIs remain unchanged.
