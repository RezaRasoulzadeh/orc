# M06-004 — Integrate bounded memory into Controller recovery

**Status:** Done
**Milestone:** M06 — Persistent memory

## Objective

Feed the reusable M06-002 `ControllerMemoryContext` into the existing read-only Controller recovery recommendation capability without widening recovery authority or changing deterministic legality/execution semantics.

M06-003 proved the capability-specific integration pattern in planning. M06-004 should apply the same smallest seam to recovery: current recovery inspection and exact legal operations remain authoritative; durable/historical memory is advisory context only.

## Repository-grounded context

Recovery already has an independent bounded model input in `src/recovery_controller.rs`:

- `RecoveryInferenceRequest` contains the canonical `RecoveryObservation` plus exact `RecoveryOperationLegality` entries;
- its serialized request is bounded to 64 KiB;
- `RecoveryRecommendationBuilder` performs one read-only inference and deterministically validates the returned operation against the exact inspected Allowed set;
- `OrcApp::recommend_recovery` is the canonical application entrypoint;
- authorization and mutation remain downstream in the existing recovery execution boundary.

M06-002 exposes the current project's bounded typed memory through `OrcApp::controller_memory_context()`.

Use these seams directly. Do not redesign planning, normal next-action recommendation, intake, Plan review, Plan revision, recovery execution, or authorization.

## Scope

Integrate M06-002 memory into recovery recommendation only.

Required behavior:

- introduce a narrow recovery inference input containing the existing `RecoveryInferenceRequest` plus typed `ControllerMemoryContext`, or equivalently extend only the recovery capability's own input while preserving its meaning;
- `OrcApp::recommend_recovery` obtains memory through `controller_memory_context()` and passes it to the recovery recommendation path;
- keep direct test/evaluation helpers compatible with explicit empty memory where necessary;
- preserve typed memory identity/kind/scope/authority/provenance metadata in serialized model input;
- validate the combined recovery inference input against the existing 64 KiB request limit, while preserving the independent M06-002 memory bound;
- empty memory remains valid;
- retrieval and inference remain read-only.

## Authority and precedence

The recovery request/prompt must preserve this precedence:

```text
current RecoveryObservation and exact RecoveryOperationLegality set
→ durable Project memory
→ durable User memory
→ Episodic project history
→ cross-project Experience memory
→ base model tendencies
```

For recovery specifically:

- the exact current `legal_operations` set is the only source of actionability;
- memory may help interpret failure/recovery context but can never make a forbidden operation legal;
- current recovery observation facts outrank contradictory memory;
- Project memory may provide durable project recovery context;
- User memory is preference/context only;
- Episodic/Experience memory is historical guidance only and must not be presented as current task truth;
- the deterministic post-inference legality validation remains mandatory and unchanged in authority.

No natural-language conflict resolver is required. Structure and prompt must make the authority order explicit.

## Invariants / requirements

- Reuse `ControllerMemoryContext`; no recovery-specific persistence model.
- `controller_memory_context()` remains the canonical application retrieval seam.
- `recovery_controller` receives typed bounded memory, not `Database`, `MemoryService`, registry, filesystem, or other persistence handles.
- Existing recovery request remains capability-specific; do not merge it with planning or `ControllerStatePacket`.
- Existing 64 KiB recovery request bound applies to the combined current recovery input plus memory.
- `RecoveryRecommendation` schema remains unchanged solely because memory was added.
- `validate_recommendation()` or its exact deterministic equivalent must still decide actionability only by membership in the inspected Allowed set.
- Recovery authorization/execution, task lifecycle mutation, worker invocation, validation, revision lineage, and economy behavior remain unchanged.
- No memory writes/capture/correction/removal/consolidation.
- No semantic/vector retrieval, embeddings, learned ranking, or model-based memory selection.
- No model-specific domain behavior.
- No Python.

## Non-goals

- Adding memory to normal task recommendation.
- Adding memory to intake.
- Adding memory to Plan review or Plan revision.
- Changing recovery operation definitions or legality rules.
- Changing recovery authorization/execution semantics.
- Automatically recording recovery outcomes as memories.
- Memory consolidation/deduplication.
- Semantic search or embeddings.
- Creating a universal Controller request/state type.

## Acceptance criteria

1. `OrcApp::recommend_recovery` supplies the current bounded M06-002 memory context through the existing recovery capability path.
2. Recovery inference retains typed memory identity/kind/scope/authority/provenance metadata.
3. Current recovery observation and exact legal-operation set are structurally and prompt-level authoritative over memory.
4. A memory item can never cause an operation absent from the current Allowed set to become actionable.
5. The existing deterministic recommendation validation remains the final actionability gate.
6. The existing 64 KiB recovery request limit includes memory and deterministically rejects an oversized combined request.
7. Empty memory remains compatible.
8. Recovery output schema, authorization, execution, lifecycle, revision-lineage, and workflow semantics remain unchanged.
9. Retrieval/inference causes no durable memory mutation.
10. No unrelated Controller capability is redesigned.
