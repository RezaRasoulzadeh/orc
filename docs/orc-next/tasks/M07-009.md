# M07-009 — Compose one supervised Controller memory maintenance step

**Status:** Done
**Milestone:** M07 — Supervised autonomy

## Objective

Compose the existing M06-011 maintenance judgment, M06-009 mutation proposal/execution boundary, and M07-008 finite maintenance grant into one explicit application-level operation that processes exactly one caller-supplied maintenance request and may perform at most one eligible project-bound maintenance mutation.

## Result

Implemented `OrcApp::maintain_controller_memory_once(...)` as the capability-specific one-step composition:

1. `judge_controller_memory_maintenance(...)`;
2. `Keep` stops without proposal, authorization, mutation, or grant consumption;
3. proposed intent passes through `propose_controller_memory_mutation(...)`;
4. exact proposal passes through `inspect_controller_memory_maintenance_grant(...)`;
5. exact authorization executes only through `execute_authorized_controller_memory_mutation(...)`.

The operation performs at most one inference, one proposal, one authorization mint, and one execution attempt. Pre-mint failure/rejection consumes zero; successful authorization consumes one; post-mint failure is not refunded. No retry, fallback, alternate proposal, direct mutation, automatic target selection, workflow hook, or background maintenance was introduced.

Public result types are state-safe: `Kept`, successful `Mutated` through a private success wrapper that can contain only canonical M06-009 `Mutated`, or `Rejected` through intrinsically paired judgment/proposal/grant/execution errors. A successful execution cannot be represented as rejection, a rejected execution cannot be represented as success, and stage/error mismatch is not publicly constructible.

M06-011 prompt/schema/bounds and inference behavior remain unchanged. M06-009 remains the sole canonical mutation path and M07-008 remains the maintenance permission boundary.
