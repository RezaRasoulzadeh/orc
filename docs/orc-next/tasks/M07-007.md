# M07-007 — Compose one supervised Controller memory capture step

**Status:** Planned
**Milestone:** M07 — Supervised autonomy

## Objective

Compose the existing M06-010 capture judgment, M06-009 mutation proposal/execution boundary, and M07-006 finite capture grant into one explicit application-level operation that processes exactly one caller-supplied capture candidate and may persist at most one eligible project-bound memory record.

This task proves the complete supervised capture chain without yet deciding when Orc should derive candidates or invoke capture automatically from workflow/task/review/Plan/lifecycle events.

## Repository-grounded context

The required pieces already exist:

- `OrcApp::judge_controller_memory_capture(...)` performs one bounded read-only M06-010 judgment over one explicit `ControllerMemoryCaptureRequest` and returns only `Ignore` or one exact candidate-backed Create intent.
- `OrcApp::propose_controller_memory_mutation(...)` converts one intent into the canonical M06-009 proposal after deterministic current-project/scope validation.
- `OrcApp::inspect_controller_memory_capture_grant(...)` checks one existing M06-009 proposal against a finite M07-006 grant and mints the existing exact one-shot M06-009 authorization for eligible Project/Episodic Create only.
- `OrcApp::execute_authorized_controller_memory_mutation(...)` performs fresh M06-009 validation and canonical `MemoryService` mutation.

No new inference schema, permission model, mutation schema, persistence path, retry loop, or workflow engine is required. The missing seam is composition analogous to M07-002's one-step task-action composition, but capability-specific to memory capture.

## Scope

Add the smallest `OrcApp` API needed to process exactly one explicit capture request with one supplied local Controller runtime and one existing M07-006 capture grant.

Required behavior:

- accept exactly one existing `ControllerMemoryCaptureRequest`, one `LocalInferenceRuntime`, and one existing `ControllerMemoryCaptureGrant`;
- validate the request through the existing M06-010 path;
- perform at most one capture inference;
- if M06-010 returns `Ignore`, stop successfully with an explicit non-mutating outcome; consume zero grant units and perform no proposal/authorization/execution;
- if M06-010 returns `ProposeMutation`, preserve the exact returned candidate-backed intent and pass it through `OrcApp::propose_controller_memory_mutation(...)`;
- pass the resulting exact canonical proposal through `OrcApp::inspect_controller_memory_capture_grant(...)`;
- execute only via `OrcApp::execute_authorized_controller_memory_mutation(...)` using the exact authorization minted for that proposal;
- at most one durable memory mutation may occur per call;
- successful authorization mint consumes exactly one M07-006 grant unit;
- any failure/rejection before grant authorization consumes zero grant units;
- a failure after grant authorization is minted receives no refund;
- no retry, second inference, alternate proposal, fallback authorization, fallback direct mutation, or grant replenishment;
- returned result must clearly distinguish at minimum: ignored/no mutation, mutated, and failure/rejection after a proposed capture path;
- do not expose a raw mutation/storage handle to the model;
- do not let the model select or modify grant scope, budget, project identity, execution path, or persistence metadata.

## Exact composition order

The canonical path must remain:

1. caller supplies one explicit `ControllerMemoryCaptureRequest`;
2. existing M06-010 `judge_controller_memory_capture(...)`;
3. if `Ignore`: stop, zero grant consumption;
4. if `ProposeMutation`: existing M06-009 `propose_controller_memory_mutation(...)`;
5. existing M07-006 `inspect_controller_memory_capture_grant(...)`;
6. existing M06-009 `execute_authorized_controller_memory_mutation(...)`;
7. return one bounded typed outcome.

Do not collapse or bypass these boundaries merely to reduce code.

## Result semantics

Introduce the smallest typed result needed for the composed operation. Exact naming may follow repository conventions.

The result should make the following observable without exposing authorization internals:

- capture was ignored and no mutation occurred;
- an eligible capture was mutated successfully, including the canonical mutation result/record identity needed by trusted callers;
- the composed step stopped because proposal/grant/execution failed or was rejected.

Use existing underlying error/result types where practical. Avoid duplicating M06-009 or M07-006 rejection enums unless a thin composition-level wrapper is needed.

Inference/runtime errors and malformed M06-010 output must remain distinguishable from grant rejection and mutation execution failure.

## Invariants / requirements

- Exactly one explicit candidate per call.
- At most one Controller capture inference per call.
- At most one M06-009 proposal per call.
- At most one M07-006 authorization mint per call.
- At most one M06-009 execution attempt per call.
- `Ignore` consumes zero grant units.
- M06-010 request/input/output failure before proposal consumes zero.
- M06-009 proposal rejection before authorization consumes zero.
- M07-006 grant rejection consumes zero.
- Successful M07-006 authorization consumes exactly one.
- Post-mint M06-009 execution/fresh-validation/storage failure is not refunded.
- Only Project/Episodic Create remains eligible through the M07-006 grant; this task must not weaken those checks.
- User/Experience and maintenance operations remain outside this composed path.
- M06-009 remains the sole canonical durable mutation path.
- M06-010 remains the sole capture judgment schema.
- M07-006 remains the sole automatic-capable capture permission boundary.
- No grant persistence or restart reconstruction.
- No second loop or retry policy.
- No provider fallback.
- No provider token hard cap.
- No Python or model-specific behavior.

## Non-goals

- Deriving capture candidates automatically from workflow/task/Plan/review/validation/recovery/transcript/lifecycle data.
- Invoking capture automatically after workflow transitions.
- Batch capture or repeated capture loops.
- Automatic User/Experience capture.
- Automatic memory maintenance Correct/Supersede/Remove.
- Background scans or consolidation.
- Semantic/vector retrieval or embeddings.
- Changing capture prompt/schema/bounds.
- Changing M06-009 mutation legality or execution semantics.
- Changing M07-006 grant eligibility or budget semantics.
- CLI/TUI/GUI integration.

## Acceptance criteria

1. One explicit `OrcApp` API composes one caller-supplied capture request through M06-010 → M06-009 proposal → M07-006 grant → M06-009 execution.
2. One call performs at most one inference and at most one durable memory mutation attempt.
3. `Ignore` returns a clear non-mutating outcome, leaves memory unchanged, and consumes zero grant units.
4. A valid Project or Episodic proposal can persist exactly one record through the existing M06-009 execution path and consumes exactly one grant unit.
5. Invalid/global/ineligible proposals cannot bypass M07-006 and consume zero before authorization.
6. Exhausted/revoked/wrong-project grants stop with no mutation and zero additional consumption.
7. Proposal or inference failure before authorization consumes zero.
8. Post-authorization fresh-validation/execution failure consumes one and is not refunded.
9. No retry, fallback, second inference, second proposal, direct mutation, or automatic candidate derivation is introduced.
10. Existing M06-009, M06-010, M07-006, routine-continuation, and workflow behavior remain unchanged.
