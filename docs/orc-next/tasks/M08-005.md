# M08-005 — Add explicit typed curation for Controller workflow intake

**Status:** Done
**Milestone:** M08 — Experience dataset

## Objective

Add one capability-local curation adapter for an already-produced Controller workflow-intake interaction, projecting the existing typed `ControllerIntakeInput` and existing canonical `ControllerIntakeResult` into one M08-001 experience example under explicit trusted verification metadata.

This continues the narrow M08 capability-local pattern without introducing a generic experience framework, automatic workflow harvesting, or labels inferred from downstream task/Plan execution.

## Repository-grounded context

`src/controller_intake.rs` already exposes a complete bounded typed reasoning boundary:

- `ControllerIntakeInput` contains the current authoritative `ControllerIntakeRequest` plus bounded advisory `ControllerMemoryContext` and exposes public `validate()`;
- `ControllerIntakeResult` is the canonical bounded output with exactly `DirectTasks`, `PlanRequired`, or `UserDecisionRequired`, details, and optional canonical direct task proposals, and exposes public `validate()`;
- `ControllerIntakeResult::validate()` already enforces decision/direct-task consistency and validates `TaskProposal` values through the canonical Plan protocol;
- the intake inference boundary remains read-only and does not itself persist tasks, Plans, routing decisions, or workflow transitions.

M08-001 remains the sole durable experience-record format. M08-002 through M08-004 established narrow typed adapters over existing production capability contracts.

## Scope

Add one intake-specific typed curation request and the smallest `OrcApp` API needed to persist one explicitly verified workflow-intake example.

The request must accept:

- one existing `ControllerIntakeInput`;
- one observed `ControllerIntakeResult`;
- one explicit accepted/expected `ControllerIntakeResult`;
- explicit `ControllerExperienceVerificationBasis`;
- explicit M08-001 outcome and quality metadata;
- optional M08-001 provenance;
- correction metadata only when observed and accepted canonical outputs differ.

Do not accept a caller-controlled capability identifier.

## Canonical capability

Use fixed code-owned capability identifier:

`controller.workflow_intake`

The caller must not be able to override it.

## Canonical input projection

The exact supplied `ControllerIntakeInput` is the dataset input authority.

Before projection:

- call the existing production `ControllerIntakeInput::validate()`;
- serialize the exact typed value deterministically;
- preserve the exact current request and embedded bounded memory;
- do not rebuild, summarize, reorder, enrich, truncate, or replace the input with later discovery/task/workflow state;
- do not query the workflow or project database to synthesize a newer intake packet.

No intake inference call is permitted in this adapter.

## Canonical output projection

The existing `ControllerIntakeResult` is the dataset output authority.

Observed and accepted values must both pass existing production `ControllerIntakeResult::validate()`.

Persist the exact accepted `ControllerIntakeResult` JSON as M08 `accepted_output`, including:

- exact `decision`;
- exact bounded `details`;
- exact `direct_tasks`, including complete canonical `TaskProposal` values when the decision is `DirectTasks`.

Do not replace the intake result with later persisted tasks, Plan identity, workflow stage/status, task IDs assigned during application, Lead state, or free-form prose.

## Provenance

M08-001 provenance remains optional, explicit, and non-owning.

`ControllerIntakeInput` carries project name and discovery/current task facts but not a canonical project identity intended as dataset provenance authority. M08-005 must not invent a project-ID lookup or derive provenance from later workflow/application state.

If provenance is supplied, validate it only through M08-001.

## Correction semantics

Compare exact canonical serialized observed and accepted `ControllerIntakeResult` values.

If observed == accepted:

- correction metadata must be absent;
- outcome must satisfy valid non-correction M08-001 semantics;
- no correction evidence is manufactured.

If observed != accepted:

- outcome must be `Corrected`;
- explicit valid correction metadata is required;
- `correction.original_output` must exactly equal the canonical observed `ControllerIntakeResult` JSON;
- M08 `accepted_output` must exactly equal the canonical accepted `ControllerIntakeResult` JSON.

A correction may change decision, details, and/or direct task proposals, but only through the explicit accepted typed result. Do not infer a correction because routing, task application, Plan creation, later operator resolution, or eventual task outcomes differed from the observed intake recommendation.

## Verification boundary

Verification remains explicit and caller-owned.

Do not automatically treat any of these as sufficient verification or correction evidence:

- successful DirectTasks application;
- successful Plan creation/application;
- workflow routing or advancement;
- later operator resolution;
- task validation/review/acceptance;
- eventual task or workflow completion;
- absence of downstream errors.

These may become evidence for a future explicit curation policy, but this task must not derive labels from them.

## Production order

1. validate exact `ControllerIntakeInput`;
2. validate observed `ControllerIntakeResult`;
3. validate accepted `ControllerIntakeResult`;
4. deterministically project exact input/observed/accepted JSON;
5. enforce correction semantics;
6. construct exactly one `ControllerExperienceExampleDraft` with fixed capability;
7. delegate verification/outcome/quality/provenance/bounds validation to M08-001;
8. persist only through existing `OrcApp::create_controller_experience_example(...)`.

At most one row may be written per call. Any validation/projection failure must write zero rows.

- Workflow-intake curation only; no generic experience adapter.
- Explicit trusted call only.
- No Controller inference.
- No automatic capture/harvesting.
- No intake/workflow hook.

## Non-goals

- Automatic curation from workflow routing/application/outcomes.
- Plan review, Plan revision, or memory-judgment curation yet.
- Generic curation framework.
- Dataset export/trainer formats.
- Dataset deduplication/ranking/sampling/balancing/splitting.
- Fine-tuning/evaluation runner changes.
- Runtime memory changes.

## Acceptance criteria

1. One explicit application API persists one verified Controller workflow-intake interaction as one M08-001 example.
2. Capability identity is fixed as `controller.workflow_intake` and not caller-controlled.
3. Dataset input is the exact validated `ControllerIntakeInput` projection.
4. Dataset accepted output is the exact validated `ControllerIntakeResult` projection.
5. Observed and accepted values use the existing production intake validation contract, including canonical DirectTasks validation.
6. Equal outputs create non-correction examples; differing outputs require explicit corrected outcome and exact observed-output correction metadata.
7. Invalid/mismatched/unbounded data creates zero rows.
8. Successful curation creates exactly one row through M08-001 only.
9. No intake inference/workflow behavior changes and no automatic harvesting/verification is introduced.
