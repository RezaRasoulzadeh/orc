# M09-005 — Investigate native/offline Controller specialization backend

**Status:** Planned
**Milestone:** M09 — Controller specialization

## Objective

Investigate and recommend the smallest viable native/offline specialization path for the existing Qwen3 8B Controller, using repository evidence and current upstream capabilities. Establish a justified backend and artifact boundary before implementing dataset transformation or training.

## Context

M09-001 provides a trainer-neutral canonical Active experience snapshot. M09-002 provides the nine-capability semantic suite. M09-003 provides reproducible real-model baseline reporting; no actual Qwen score has yet been recorded. M09-004 fixes deterministic candidate promotion rules. D-007 requires a Rust/native Orc runtime, permits C/C++ inference/performance components, and treats training/export as a separate concern with native options investigated first.

The current Cargo manifest uses optional llama-cpp-2 0.1.155. The existing runtime is an inference boundary, not evidence that training is supported. Do not assume a training backend, hardware capability, dataset size, or available model file.

## Scope

Perform a bounded repository and upstream feasibility investigation. Inspect the existing runtime, model configuration, M09-001 snapshot, M08 example schema, M09-002/003/004 evaluation boundaries, relevant build/dependency conventions, and available local hardware/model evidence.

Compare credible native/offline approaches for Qwen3 8B specialization, including llama.cpp-compatible/native training or adapter paths where actually supported, and other justified native alternatives. Distinguish inference, adapter training, full fine-tuning, conversion, quantization, and export capabilities. Do not infer training support from inference support.

For each credible option record verified upstream version/revision, supported model architecture and weight/adapter formats, training capability and limitations, runtime dependencies, licensing, hardware/memory requirements, reproducibility controls, and compatibility with Orc's existing GGUF inference boundary. Identify whether training can consume the existing model artifact or requires original/base weights and a separate conversion/export step.

Assess the available canonical dataset inventory and actual local hardware/model availability. If unavailable, record unknowns and provide a concrete non-destructive verification plan rather than inventing capacity, scores, or readiness.

Recommend one smallest justified path, or explicitly recommend deferring selection if evidence is insufficient. Define the minimum future dataset/export boundary, candidate artifact lineage, offline execution boundary, and validation/evaluation sequence. Keep all proposed transformations separate from canonical M08/M09-001 records and preserve the fixed M09-002/003/004 evaluation authority.

## Required deliverable

Produce a repository-grounded investigation report under `docs/orc-next/` with an evidence table, alternatives/tradeoffs, verified compatibility constraints, hardware/data readiness, recommendation, unresolved blockers, and proposed independently reviewable follow-on tasks. Update D-007 or add a new decision only if evidence supports an actual durable architecture decision. Do not silently declare a backend selected.

## Non-goals

No training, weight/adapter mutation, dataset export/transformation/splitting/sampling/balancing/deduplication/ranking/weighting implementation, new runtime dependency, production inference change, model-default change, benchmark expectation/gate change, automatic deployment, storage migration, embeddings, provider fallback, provider token hard cap, or Python runtime dependency. Do not install large toolchains or download model weights without explicit operator approval. Do not require a real model to complete the investigation.

## Acceptance criteria

1. Repository and upstream evidence supports every asserted backend capability and compatibility claim.
2. Native/offline alternatives are compared without treating inference support as training support.
3. Qwen3 8B model/adapter format and GGUF compatibility constraints are explicit.
4. Hardware, model, and dataset readiness are measured or explicitly unknown.
5. The recommended path is justified, or selection is deferred with precise blockers.
6. Future export/training/evaluation boundaries preserve canonical data and fixed promotion semantics.
7. No production code, weights, datasets, or default-model behavior changes.
8. Follow-on tasks are narrow and depend on verified prerequisites rather than speculative implementation details.

## Required review

Independently verify cited upstream capabilities, versions, model-format claims, repository compatibility, hardware/data evidence, and the absence of premature training or architecture changes. No full code validation is required for a documentation-only investigation. If any code is changed unexpectedly, stop and review that scope separately.

## Completion evidence

Report inspected repository surfaces, sources and versions, alternatives, actual readiness evidence, recommendation/defer decision, unresolved blockers, proposed next tasks, changed documentation, and any architectural mismatch. Do not commit or push before independent review.
