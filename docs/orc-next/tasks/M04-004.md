# M04-004 — Route validation-repair exhaustion into supervised Controller recovery

**Status:** Done
**Milestone:** M04 — Recovery intelligence

## Objective

Replace one concrete rigid recovery dead-end with the supervised M04 Controller recovery boundary: when implementation/revision validation repair is exhausted, preserve deterministic validation truth and existing run/revision evidence, then expose the resulting abnormal state to Controller recovery instead of forcing a blind policy continuation or destroying actionability.

## Result

Implemented narrowly. The prior post-exhaustion path invoked economy escalation, which could create a pending escalation or `economy_escalation_exhausted` execution condition before blocking the task. M04-004 removes only that post-exhaustion escalation call from the validation-repair loop. Deterministic validation, bounded repair attempts, validation evidence, failed-run persistence, and blocked-task persistence remain unchanged.

Implementation exhaustion now preserves failing validation and failed-run evidence in a blocked task without fabricating semantic revision lineage. Revision exhaustion preserves the actionable REVISE review/contract lineage; M04-001 can allow `ResumeRevision` while rejecting generic `Requeue` with `RequeueWouldDiscardRevisionLineage`. Infrastructure validation failures remain `InfrastructureFailure` and do not enter repair non-convergence. Economy/quota classification remains canonical factual state, but repair exhaustion no longer automatically requests escalation or creates an `economy_escalation_exhausted` policy dead-end.

The existing M04-001 legality, M04-002 recommendation, and M04-003 supervised authorization/execution boundaries remain unchanged. No new recovery operation or replacement recovery-choice heuristic was added.
