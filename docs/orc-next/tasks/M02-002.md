# M02-002 — Evaluate read-only Controller decision quality

**Status:** Done
**Milestone:** M02 — Read-only Controller

## Objective

Evaluate whether the local Controller baseline can make acceptable read-only
decisions on representative Orc states before any mutation-capable tools are
introduced.

## Why

The Controller must demonstrate useful judgment while the deterministic kernel
still owns every lifecycle invariant and mutation. A small typed evaluation
corpus provides an evidence gate before expanding the Controller's authority.

## Scope

- Add a bounded deterministic evaluation harness around
  `ControllerStatePacket` and `ControllerStateBuilder`'s recommendation path.
- Curate representative Ready, acceptance-ready, revision, blocked,
  infrastructure-failure, dependency-blocked and inconsistent states.
- Record each scenario's expected action class, typed expected decision,
  genuinely equivalent alternatives and pass/fail result.
- Evaluate typed recommendation semantics rather than exact natural-language
  output.
- Retain raw model output and parse errors for malformed structured responses;
  report rationale and optional confidence for successfully parsed responses.
- Keep normal tests model-free with a fake `LocalInferenceRuntime`.
- Add an ignored, feature-gated Qwen3 evaluation using `ORC_QWEN3_GGUF` that
  prints a concise per-scenario report and aggregate pass/fail counts.

## Integration constraints

- The Controller remains strictly read-only; evaluation never calls lifecycle,
  dispatch, review, revise, recovery, planning, memory, scheduler or tool APIs.
- Reuse the existing model-independent packet and runtime boundaries.
- Do not download or commit model weights, add Python, or add GPU-specific work.
- Do not tune scenario expectations to a model's output; expectations encode
  the deterministic Orc policy and lineage requirements.

## Non-goals

- Do not add mutation-capable Controller tools.
- Do not change lifecycle legality, validation execution, economy resolution,
  planning/Lead behavior or persistence.
- Do not require a model file or network access for deterministic tests.

## Dependencies

- M02-001.

## Acceptance criteria

1. A bounded scenario corpus covers at least: Ready → dispatch; Review PASS →
   acceptance; Review REVISE with valid lineage → revise; validation-repair
   exhaustion/blocked lineage preservation without generic requeue;
   infrastructure failure without semantic-revision classification;
   dependency blocking without dispatch; and ambiguous/inconsistent state →
   operator decision.
2. Each scenario carries bounded input state, an expected action class, typed
   expected decision, explicitly listed acceptable alternatives and an
   evaluation result.
3. Evaluation compares typed recommendation semantics (`OperationalNextStep`
   or an explicit structured operator-decision class), never exact prose.
4. Deterministic fake-runtime tests cover the complete corpus, incorrect typed
   decisions, runtime failures and aggregate pass/fail accounting without
   mutating Orc state.
5. The opt-in real-model path uses the existing `ORC_QWEN3_GGUF` convention,
   is ignored/feature-gated, emits per-scenario plus aggregate results,
   retains raw output and parse errors for malformed responses, reports
   rationale/optional confidence for parsed responses, and performs no action
   execution.
6. No Controller mutation/tools, lifecycle or scheduler behavior, memory,
   planning/Lead migration, model downloading, Python or GPU work is added.

## Required tests/evidence

- Focused deterministic `controller_evaluation` tests with a fake runtime.
- `cargo fmt --check`.
- `cargo test --lib`.
- `cargo clippy --all-targets -- -D warnings`.
- `git diff --check`.
- Optional real-model evaluation (not required for deterministic validation):

```text
ORC_QWEN3_GGUF=~/models/qwen3/Qwen3-8B-Q4_K_M.gguf \

```

## Result

Implemented `src/controller_evaluation.rs` with seven bounded typed scenarios
and an aggregate evaluator that reuses `ControllerStateBuilder::recommend_packet`.
The harness records expected classes, typed expected/alternative decisions,
observed decisions, rationale/optional confidence and pass/fail outcomes. The
evaluation report can retain raw model output plus the parser error when the
evaluation-only JSON parser rejects a response. Fake runtime tests prove all
curated expectations, reject incorrect typed decisions without prose matching,
and record malformed-output diagnostics/runtime failures without aborting the
report.

The ignored native smoke target is
`tests/controller_evaluation_smoke.rs`. It uses the existing
`ORC_QWEN3_GGUF` convention, asks the model for a small JSON semantic result,
prints one concise line per scenario and an aggregate count, includes raw
output/parse-error evidence for malformed responses and rationale/optional
confidence for parsed responses, and never executes the recommendation. The
opt-in evaluation was executed with the documented
Qwen3 8B Q4_K_M file on the CPU-backed native path:

```text
ORC_QWEN3_GGUF=~/models/qwen3/Qwen3-8B-Q4_K_M.gguf cargo test --features llama-cpp --test controller_evaluation_smoke -- --ignored --nocapture
```

It reported a strict-harness result of `4 passed; 3 failed` in `376.86s`. The
passing scenarios were Review REVISE, revision-validation exhaustion,
dependency blocking and the ambiguous-state operator decision. The three strict
failures nevertheless contained the correct intended action in their first JSON
object: `ready-dispatch` → `dispatch`, `review-pass-accept` → `accept`, and
`infrastructure-no-revise` → `resolve_blocker`. On this curated set, semantic
action selection was therefore `7/7`, while strict structured-output compliance
was only `4/7`.

The remaining blocker is structured-output reliability: Qwen emitted valid JSON
followed by extra prose/repeated JSON, so the strict contract rejected those
responses. The semantic `7/7` observation does not reinterpret the strict
`4/7` result as contract compliance; both measures remain recorded separately.
Scenario expectations were not relaxed or tuned to the model.

Validation: focused evaluation tests pass,
`cargo test --features llama-cpp --test controller_evaluation_smoke --no-run`,
`cargo fmt --check`, `cargo test --lib`,
`cargo clippy --all-targets -- -D warnings`, and `git diff --check` pass.
