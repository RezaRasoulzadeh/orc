# M05-007 — Persist Controller Plan revisions through explicit authorization

**Status:** Planned
**Milestone:** M05 — Planning and Lead unification

## Objective

Persist a validated M05-006 Controller-generated Plan revision and atomically supersede its parent/revision review through explicit trusted one-shot authorization, preserving canonical Plan version, parent, provenance, and supersession invariants without fabricating legacy Planner or Lead lineage.

## Required path

```text
validated ControllerPlanRevisionResult
              ↓
 typed revision-persistence proposal
              ↓
 trusted one-shot authorization
              ↓
 fresh deterministic parent/review eligibility check
              ↓
 atomic canonical Controller revision persistence
              ↓
 new current Controller-origin Proposed Plan
 + parent/review supersession
```

## Scope

- Inspect M05-006 revision result/eligibility, M05-002 Plan provenance, M05-005 review provenance, legacy `Database::store_plan_revision`, Plan version/parent/supersession schema, current-plan selection, and M03/M04/M05 authorization patterns before editing.
- Determine the smallest canonical storage seam for Controller-origin Plan revisions. Reuse shared revision/version/supersession transaction logic where possible rather than duplicating legacy semantics.
- Add a typed revision-persistence proposal derived from a validated `ControllerPlanRevisionResult`. Trusted parent Plan ID and source review ID must remain application-owned identity, not model-controlled fields.
- Add an opaque trusted one-shot authorization token: private-field, non-serializable, non-cloneable, consumed by value, and bound to exact project, parent Plan, source review, and complete revised `PlanResponse` or deterministic content identity.
- Add `OrcApp` authorization and authorized execution entry points.
- Immediately before mutation, freshly reload and verify: project identity; parent is still the current Controller-origin Plan; parent remains `RevisionRequested`; source review is still the latest unsuperseded Controller-origin `RevisePlan` review for that parent; the review feedback/identity remains consistent; authorization matches the exact proposal; revised `PlanResponse` still passes canonical validation.
- Atomically persist exactly one new Controller-origin Plan revision with canonical next version and parent linkage, supersede the parent Plan as required by existing Plan semantics, and supersede/consume the source revision review exactly as canonical revision persistence requires.
- Preserve truthful Controller provenance with no fabricated Planner run, Lead decision, or Lead run.
- Return a bounded typed result containing new Plan ID/version/status/origin, parent ID, and source review identity/status as appropriate.
- Add deterministic tests for success, exact version/parent linkage, truthful provenance, authorization mismatch/substitution/reuse, stale parent, stale/superseded review, non-revise review, changed current Plan, invalid revised Plan, atomic rollback, and absence of unrelated side effects.

## Preserve

- M05-006 revision-generation prompt/schema/parser semantics.
- Canonical `PlanResponse` validation.
- Existing Plan version/parent/current/supersession semantics.
- M05-002 Plan provenance semantics.
- M05-005 Plan-review provenance/status semantics.
- Legacy Planner revision persistence and truthful legacy lineage.
- Existing Plan review and approved-plan application behavior.

## Constraints

- Controller/model output is never authorization.
- Model output cannot choose project ID, parent Plan ID, source review ID, version, provenance, supersession metadata, or persistence metadata.
- Do not fabricate Planner runs, Lead runs, or Lead decision IDs.
- Do not invoke legacy Planner/Lead backends.
- Do not duplicate revision/version/supersession transaction logic if a narrow shared canonical seam can be extracted.
- Persistence and all supersession effects must be atomic.
- A stale authorization/proposal must not persist a revision against a changed parent/review state.
- Successful persistence creates exactly one new Plan revision and only the canonical parent/review supersession effects.
- Do not approve/apply the new Plan.
- Do not create tasks.
- Do not automatically review the new Plan or continue workflow execution.
- Do not remove legacy Lead/Planner machinery.
- If legacy `store_plan_revision` cannot be safely generalized without weakening lineage or atomicity, stop and report the exact repository constraint before implementing a parallel inconsistent path.
- No autonomous planning/revision loop.
- No Qwen-specific core/domain behavior.
- No Python.

## Non-goals

- Automatic review of the revised Plan.
- Plan approval/application.
- Task creation.
- Removing legacy Planner revision persistence.
- Removing Lead/Planner roles or workflow stages.
- DIRECT_TASKS migration.
- General user-decision routing migration.
- Memory/autonomy/UI work.

## Dependencies

- M05-002 complete: Controller-compatible Plan provenance.
- M05-005 complete: Controller-compatible Plan-review provenance and persistence.
- M05-006 complete: validated read-only Controller Plan revision generation.

## Acceptance criteria

1. A validated `ControllerPlanRevisionResult` can produce a typed persistence proposal without mutation.
2. Explicit opaque one-shot authorization is required and bound to the exact project/parent/review/revised-plan proposal.
3. Execution freshly verifies parent/current/status/review/provenance/actionability and canonical revised-Plan validity immediately before mutation.
4. Successful execution atomically creates exactly one next-version Controller-origin Plan with correct parent linkage and truthful provenance.
5. Parent Plan and source revise review are superseded/consumed exactly according to canonical existing revision semantics, with no partial state on failure.
6. Legacy Planner-origin revision persistence remains unchanged and retains strict truthful legacy lineage.
7. Authorization mismatch/reuse, stale parent/review, changed current Plan, invalid revised Plan, or persistence failure causes no partial mutation.
8. Successful execution performs no Lead/Planner invocation, approval/application, task creation, automatic review, or workflow continuation.
