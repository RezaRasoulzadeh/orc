# M08-007 — Add explicit typed curation for Controller Plan revision generation

**Status:** Planned
**Milestone:** M08 — Experience dataset

## Objective

Add one capability-local curation adapter for an already-produced Controller Plan-revision generation interaction, projecting the existing typed `ControllerPlanRevisionInput` and the actual model-generated revised `PlanResponse` into one M08-001 experience example under explicit trusted verification metadata.

The dataset target must follow the actual inference boundary. `ControllerPlanRevisionResult` is not the reasoning output authority because application code attaches trusted parent Plan/version/review lineage after inference.

## Repository-grounded context

`src/controller_plan_revision.rs` already exposes a bounded read-only generation boundary:

- `ControllerPlanRevisionInput` contains the authoritative revision request plus bounded advisory memory and exposes public `validate()`;
- `ControllerPlanRevisionRequest` contains the current Plan, persisted revision feedback, and bounded planning context;
- `ControllerPlanRevisionBuilder::revise_with_memory(...)` validates the typed input and returns a canonical `PlanResponse` from model inference;
- the generated `PlanResponse` is validated through the existing canonical Plan parser/validation path;
- `ControllerPlanRevisionResult` is constructed only afterward by trusted application code and adds `parent_plan_id`, `parent_plan_version`, and `review_id` around the generated Plan.

Therefore the M08 reasoning target is the generated `PlanResponse`, not the lineage-bearing application result.

## Scope

Add one Plan-revision-specific typed curation request and the smallest `OrcApp` API needed to persist one explicitly verified Plan-revision generation example.

The request must accept:

- one existing `ControllerPlanRevisionInput`;
- one observed generated `PlanResponse`;
- one explicit accepted/expected `PlanResponse`;
- explicit `ControllerExperienceVerificationBasis`;
- explicit M08 outcome and quality metadata;
- optional M08 provenance;
- correction metadata only when observed and accepted canonical outputs differ.

Do not accept a caller-controlled capability identifier or lineage fields.

## Canonical capability

Use fixed code-owned capability identifier:

`controller.plan_revision`

## Canonical input projection

The exact supplied `ControllerPlanRevisionInput` is the dataset input authority.

Before projection:

- call existing `ControllerPlanRevisionInput::validate()`;
- serialize the exact typed input deterministically;
- preserve the exact current Plan, revision feedback, planning context, and bounded memory already supplied;
- do not re-read the current Plan, review, workflow, project, or task state;
- do not inject parent Plan ID/version or review ID from later application state;
- do not summarize, reorder, enrich, truncate, or infer later facts.

No Plan-revision inference call is permitted in the curation adapter.

## Canonical output projection

The model-generated canonical `PlanResponse` is the dataset output authority.

Observed and accepted values must both pass the existing canonical `PlanResponse::validate()` contract used by production Plan-revision generation.

Persist the exact accepted `PlanResponse` JSON as M08 `accepted_output`, including complete objective, assumptions, risks, questions, task proposals, dependencies, execution hints, acceptance criteria, required tests, and all other canonical Plan fields.

Do not wrap it in `ControllerPlanRevisionResult`. Do not persist parent Plan ID/version, review ID, persisted revised-Plan identity/status, workflow state, or downstream application results as the reasoning target.

## Lineage boundary

Trusted lineage is application metadata, not model output.

M08-007 must not:

- accept or synthesize `parent_plan_id`, `parent_plan_version`, or `review_id` as part of accepted/observed output;
- reconstruct `ControllerPlanRevisionResult` merely to curate an example;
- query storage to validate or refresh lineage;
- infer verification from successful persistence of a revised Plan.

If useful lineage is supplied as M08 provenance, it remains explicit caller-owned metadata and is validated only through existing M08-001 rules.

## Correction semantics

Compare exact canonical serialized observed and accepted `PlanResponse` values.

If observed == accepted:

- correction metadata must be absent;
- outcome must satisfy valid non-correction M08-001 semantics.

If observed != accepted:

- outcome must be `Corrected`;
- explicit valid correction metadata is required;
- `correction.original_output` must exactly equal the canonical observed `PlanResponse` JSON;
- M08 `accepted_output` must exactly equal the canonical accepted `PlanResponse` JSON.

Do not infer correction because the revised Plan was later persisted, rejected, reviewed again, superseded, applied, or produced successful/failed tasks.

## Verification boundary

Verification remains explicit and caller-owned.

Do not automatically treat any of these as sufficient verification or correction evidence:

- successful revised-Plan persistence;
- matching parent/review lineage;
- later Plan review approval;
- task application;
- workflow advancement;
- validation/review success;
- operator acceptance;
- eventual task/workflow success or failure.

## Production order

1. validate exact `ControllerPlanRevisionInput`;
2. validate observed `PlanResponse`;
3. validate accepted `PlanResponse`;
4. deterministically project exact input/observed/accepted JSON;
5. enforce correction semantics;
6. construct exactly one `ControllerExperienceExampleDraft` with fixed capability;
7. delegate verification/outcome/quality/provenance/bounds validation to M08-001;
8. persist only through existing `OrcApp::create_controller_experience_example(...)`.

At most one row may be written per call. Any validation/projection failure must write zero rows.

## Invariants / requirements

- Plan-revision generation curation only; no generic experience adapter.
- Fixed capability `controller.plan_revision`.
- Exact `ControllerPlanRevisionInput` preserved as dataset input.
- Exact generated canonical `PlanResponse` preserved as dataset output authority.
- Trusted lineage must remain outside the reasoning target.
- Existing Plan-revision prompt/schema/parser/bounds remain unchanged.
- Existing revision persistence/authorization/workflow semantics remain unchanged.
- No inference, harvesting, hooks, storage lookup, automatic verification, or correction inference.
- M08-001 remains sole persistence format.
- Runtime `MemoryKind::Experience` remains unchanged.
- No provider/model-specific behavior, provider token hard cap, embeddings, Python, export, splitting, balancing, or training.

## Non-goals

- Curation of `ControllerPlanRevisionResult` lineage metadata.
- Automatic Plan-revision-call capture.
- Automatic curation from persistence/review/workflow outcomes.
- Memory capture/maintenance judgment curation yet.
- Generic curation framework.
- Dataset export/trainer formats.
- Dataset deduplication/ranking/sampling/balancing/splitting.
- Fine-tuning/evaluation runner changes.
- Runtime memory changes.

## Acceptance criteria

1. One explicit application API persists one verified Controller Plan-revision generation interaction as one M08-001 example.
2. Capability is fixed as `controller.plan_revision` and not caller-controlled.
3. Dataset input is the exact validated `ControllerPlanRevisionInput` projection.
4. Dataset accepted output is the exact validated generated `PlanResponse`, not `ControllerPlanRevisionResult`.
5. Observed and accepted outputs reuse canonical Plan validation.
6. Trusted parent/review lineage is excluded from the reasoning target.
7. Equal/differing output correction semantics are exact.
8. Invalid/mismatched/unbounded data writes zero rows.
9. Success writes exactly one row through M08-001 only.
10. No Plan-revision inference/persistence/workflow semantics change.
