# M05-002 — Persist Controller plan proposals through explicit authorization

**Status:** Planned
**Milestone:** M05 — Planning and Lead unification

## Objective

Connect the valid read-only Controller plan result from M05-001 to Orc's existing durable Plan review/application machinery through an explicit trusted one-shot authorization boundary.

This task migrates proposal creation/persistence, not plan review judgment or application. A Controller-generated plan may become a canonical persisted `Proposed` Plan only after trusted authorization; existing review and approved-plan application remain unchanged.

## Repository-grounded context

- M05-001 provides `OrcApp::propose_controller_plan` and a validated typed Controller plan result without mutation.
- Existing `plans` persistence already stores canonical `PlanResponse`, status, version/parent lineage, and legacy source Lead/Planner lineage.
- Existing workflow derives proposed/revision-requested plans into `plan_review` and applies only an approved plan through `apply_approved_plan`.
- Existing direct `apply_plan` creates tasks and is not the target path for Controller proposals.

The Controller must not gain direct DB or task-creation authority.

## Required path

```text
validated ControllerPlanResult
            ↓
 typed persistence intent/proposal
            ↓
 explicit trusted authorization
            ↓
 fresh deterministic validation
            ↓
 canonical Plan persistence as Proposed
            ↓
 existing plan review/application machinery
```

## Scope

- Inspect current plan persistence APIs, Plan status/version/parent/source invariants, plan-review entry behavior, and `apply_approved_plan` before editing.
- Add a narrow typed intent/proposal representing persistence of one validated Controller plan proposal.
- Add an opaque one-shot trusted authorization token following the M03/M04 authorization pattern; model output must never manufacture or serialize authorization.
- On execution, revalidate the canonical `PlanResponse` immediately before mutation.
- Persist through a canonical application/storage method rather than direct ad-hoc SQL from Controller code.
- Persist the Controller plan as `Proposed` so existing plan-review semantics remain authoritative.
- Preserve version and parent-plan invariants for initial proposals. If current persistence requires legacy Lead/Planner source IDs that cannot honestly represent Controller provenance, stop and report before inventing fake IDs or weakening foreign-key/lineage semantics.
- Return a bounded typed execution result containing the canonical persisted plan identifier/status and no model-owned authority.
- Add deterministic tests for authorization matching/consumption, invalid/stale proposal rejection, successful Proposed persistence, no task creation, and compatibility with existing plan review state.

## Preserve

- Canonical `PlanResponse` validation.
- Existing Plan status semantics.
- Existing plan-review machinery and Lead-based plan review for now.
- Existing `apply_approved_plan` task creation/application behavior.
- Existing persisted version/parent lineage.
- `OrcApp` as mutation boundary.

## Constraints

- Controller recommendation/result is not authorization.
- Authorization is trusted, opaque, one-shot, non-model data and consumed by execution.
- Fresh deterministic validation occurs immediately before persistence.
- Do not create tasks in this task.
- Do not approve or apply the plan in this task.
- Do not automatically invoke plan review.
- Do not consume or fabricate a Lead decision merely to satisfy legacy lineage.
- Do not fabricate a Planner run ID for Controller provenance.
- Do not delete or broadly rewrite legacy Planner/Lead machinery.
- Do not expose SQLite, Git/worktree mutation, shell, credentials, or worker execution to the Controller.
- No autonomous plan→review→apply loop.
- No Qwen-specific behavior.
- No Python.

## Non-goals

- Controller plan-review judgment.
- Controller approval/revision of persisted plans.
- Applying approved plans.
- Removing Lead plan review.
- Removing Planner commands/roles/workflow stages.
- Plan revision migration.
- DIRECT_TASKS migration.
- User-decision routing migration.
- Workflow-engine rewrite.
- Memory/autonomy/UI work.

## Dependencies

- M05-001 complete.
- M03 trusted authorization pattern available as precedent.
- Existing durable Plan review/application machinery remains canonical.

## Acceptance criteria

1. A validated M05-001 Controller plan result can be converted to a typed persistence proposal without mutation.
2. Persistence requires an explicit trusted one-shot authorization that cannot originate from model output.
3. Execution freshly validates the canonical plan and authorization immediately before mutation.
4. Successful execution creates exactly one canonical persisted `Proposed` Plan and returns its bounded typed identity/status.
5. Successful execution creates no tasks, consumes no Lead decision, invokes no Planner/worker, and does not approve/apply the plan.
6. Existing plan-review state recognizes the persisted Controller proposal through canonical Plan status semantics without a parallel review state machine.
7. Existing version/parent/provenance invariants remain truthful; no fake Lead decision or Planner run IDs are introduced.
8. Existing legacy Planner/Lead proposal, review, revision, and approved-plan application behavior remains unchanged.
