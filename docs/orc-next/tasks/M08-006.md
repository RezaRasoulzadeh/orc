# M08-006 — Add explicit typed curation for Controller Plan review

**Status:** Done
**Milestone:** M08 — Experience dataset

## Objective

Add one capability-local curation adapter for an already-produced Controller Plan-review interaction, projecting the existing typed `ControllerPlanReviewInput` and existing canonical `ControllerPlanReviewResult` into one M08-001 experience example under explicit trusted verification metadata.

Continue the established M08 pattern without introducing generic experience-capture abstractions, automatic Plan-review harvesting, or labels inferred from later Plan persistence/revision/workflow outcomes.

## Repository-grounded context

`src/controller_plan_review.rs` already exposes a bounded typed reasoning boundary:

- `ControllerPlanReviewInput` contains the authoritative current `ControllerPlanReviewRequest` plus bounded advisory `ControllerMemoryContext` and exposes public `validate()`;
- the current request includes persisted Plan identity/version/status/origin, exact Plan content, current project/task state, project name, and optional operator resolution;
- `ControllerPlanReviewResult` contains exactly one semantic decision (`Approve`, `RevisePlan`, or `OperatorDecisionRequired`), bounded details, and optional bounded revision feedback and exposes public `validate()`;
- `ControllerPlanReviewResult::validate()` already requires revision feedback for `RevisePlan` and rejects empty supplied feedback;
- the inference boundary is read-only; review persistence, Plan status transitions, revision authorization, task application, and workflow routing are separate deterministic application/kernel work.

M08-001 remains the sole durable experience-record format. M08-002 through M08-005 established narrow capability-local curation adapters over existing production input/output contracts.

## Scope

Add one Plan-review-specific typed curation request and the smallest `OrcApp` API needed to persist one explicitly verified Controller Plan-review example.

The request must accept one existing `ControllerPlanReviewInput`, observed and accepted `ControllerPlanReviewResult` values, explicit verification/outcome/quality metadata, optional provenance, and correction metadata only when observed and accepted canonical outputs differ. Capability identity is fixed by code.

## Canonical capability

`controller.plan_review`

## Canonical input projection

The exact supplied `ControllerPlanReviewInput` is the dataset input authority. Validate it with the existing production validator and preserve the exact Plan identity/version/status/origin/content, project/current state, operator resolution, and bounded memory already present in the input. Do not re-read or enrich it from later state.

## Canonical output projection

Observed and accepted values use existing production `ControllerPlanReviewResult::validate()`. Persist the complete exact accepted result, including decision, details, and optional revision feedback. Do not substitute persisted `PlanReview`, Plan status, later revised Plan, workflow state, or downstream outcomes.

## Provenance and correction semantics

M08-001 provenance remains optional and caller supplied. Equal observed/accepted outputs require no correction and a non-corrected outcome. Differing outputs require `Corrected`, explicit correction metadata, and exact preservation of the complete observed result in `correction.original_output`.

## Verification boundary

Verification remains explicit and caller-owned. Plan-review persistence, Plan transitions, later revision/approval, task application, workflow advancement, operator acceptance, and eventual success/failure do not automatically verify or correct examples.

## Production order

1. validate exact input;
2. validate observed result;
3. validate accepted result;
4. project exact JSON;
5. enforce correction semantics;
6. construct one `ControllerExperienceExampleDraft` with fixed capability;
7. delegate final M08 validation to M08-001;
8. persist only through `OrcApp::create_controller_experience_example(...)`.

Any failure writes zero rows; success writes exactly one.

## Invariants / requirements

No inference, automatic harvesting, Plan-review/workflow hook, Plan/project/workflow lookup, automatic verification, generic curation framework, direct SQL, runtime `MemoryKind::Experience` behavior change, provider/model-specific behavior, provider token hard cap, embeddings, Python, export, splitting, balancing, or training.

## Non-goals

Automatic Plan-review capture, downstream-derived labels, Plan revision curation, memory-judgment curation, dataset export/trainer formats, deduplication/ranking/sampling/balancing/splitting, fine-tuning/evaluation runner changes, or runtime memory changes.

## Acceptance criteria

1. One explicit application API persists one verified Controller Plan-review interaction as one M08-001 example.
2. Capability is fixed as `controller.plan_review`.
3. Exact validated `ControllerPlanReviewInput` is preserved.
4. Exact validated accepted `ControllerPlanReviewResult` is preserved.
5. Existing production validation remains authoritative.
6. Correction semantics are exact.
7. Invalid/mismatched/unbounded data writes zero rows.
8. Success writes exactly one row through M08-001 only.
9. No inference/persistence/workflow semantics change.
