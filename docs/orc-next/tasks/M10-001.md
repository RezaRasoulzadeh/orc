# M10-001 — Complete the TUI normal task lifecycle vertical slice

**Status:** Planned
**Milestone:** M10 — Interface integration

## Objective

Make the Rust TUI capable of completing a real normal Orc task lifecycle through existing canonical application APIs, without requiring the CLI for the covered workflow.

The slice must be operational rather than cosmetic: an operator can create a complete task, inspect it, dispatch it, observe execution/review evidence, provide revision feedback when required, and explicitly accept the task through canonical transitions.

## Repository-grounded context

`docs/orc-next/M10-interface-audit.md` found that the CLI has the broadest complete workflow coverage, while the TUI is currently limited to queue/detail plus dispatch, automated review, revision through the previous implementation agent, and accept. The audit also found that existing `OrcApp`, `ProjectOperations`, read-model, dispatch, revision, recovery, run, and validation APIs are sufficient for this first slice. No prerequisite shared API change is required.

General post-creation task metadata editing remains a separate shared application seam and is not required by this task. M09-007 remains blocked on genuine source-data availability; specialization/backend selection remains deferred; M08 experience curation remains explicit and supervised only.

## Dependencies

- M00–M08 complete.
- M09-001–M09-006 complete.
- M09-007 may remain blocked; this task does not depend on resolving specialization source-data availability.
- The reviewed M10 interface audit is present at `docs/orc-next/M10-interface-audit.md`.

## Scope

Extend the existing TUI using canonical `OrcApp`, `ProjectOperations`, and shared read-model APIs so one normal task can be carried through its ordinary lifecycle.

### Task creation

Add a TUI task-creation flow backed by the existing canonical `CreateTaskInput` path. The operator must be able to provide every field required for a valid complete task and receive deterministic validation/error feedback from the existing application boundary.

Do not create a second task model or duplicate task validation in the TUI.

### Queue and task detail

Preserve the existing queue/detail model and make it sufficient to understand the next legal action for the selected task. Display the canonical task state and the existing actionable evidence needed for the covered lifecycle, including dependencies/blockers where relevant.

### Dispatch and agent selection

Dispatch through the existing `OrcApp` path. Expose agent selection only through existing canonical scheduling/eligibility semantics; do not duplicate scheduler logic in TUI state.

If the application API supports both canonical automatic selection and an explicit eligible agent, the TUI may expose that choice, but eligibility and authorization remain kernel-owned.

### Execution state and refresh

Provide a usable way to follow the active run until the task advances. Reuse existing run/read-model state and lifecycle events where available; bounded refresh/polling is acceptable when no subscription seam exists.

The TUI must not invent progress states or infer success from process output.

### Validation and review evidence

Expose the validation and review evidence already produced by the canonical workflow sufficiently for an operator to understand whether the task passed, needs revision, is blocked, or is ready for acceptance.

Validation remains owned by the canonical review-stage workflow. Task execution and revision provider agents must not introduce independent validation turns.

### Revision

Allow operator revision feedback through the canonical revision path. Preserve the existing previous-implementation-agent continuity behavior unless the operator explicitly chooses another eligible agent through an already-supported API.

Do not add a second review/revision loop or TUI-local convergence logic.

### Acceptance

Expose explicit acceptance through the canonical application transition. The TUI must display the resulting canonical state after refresh and must not locally mark a task complete before the application transition succeeds.

### Interaction quality

For the covered workflow, provide usable keyboard navigation and form interaction, clear loading/running states, bounded error messages, cancellation/back navigation where locally safe, and confirmation before destructive or irreversible operator actions when applicable.

This task is about functional usability, not visual redesign.

## Non-goals

- No new lifecycle rules, workflow engine, state machine, or direct database mutation.
- No general post-creation task metadata editor for title, objective, role, or priority.
- No full TUI parity with CLI or desktop.
- No Plan/Lead UI, approvals UI, Controller recommendation/authorization UI, agent-governance workspace, economy workspace, or M08 curation UI.
- No automatic experience harvesting or ordinary-workflow-to-training-data capture.
- No M09 source fabrication, transform execution, trainer/backend selection, training, model download, model promotion, runtime-default change, or evaluation-gate change.
- No duplicate scheduler, validation, review, revision, recovery, authorization, or persistence logic in the TUI.
- No appearance-only redesign or unrelated styling work.

## Acceptance criteria

1. From the TUI, an operator can create a valid complete task through the canonical `CreateTaskInput` application path without using the CLI.
2. The created task appears in the canonical queue/detail read model and the TUI exposes enough state/evidence to identify its next legal normal-lifecycle action.
3. The operator can dispatch the task through `OrcApp`; agent choice, when exposed, uses existing scheduler/eligibility semantics and does not duplicate them.
4. The TUI can follow the active run through canonical run/read-model state until the task leaves execution, without fabricated progress or local lifecycle mutation.
5. Existing validation and review evidence required to understand the task outcome is inspectable in the TUI.
6. When revision is required, the operator can submit feedback through the canonical revision path; previous implementation-agent continuity is preserved by default.
7. When acceptance is legal, the operator can explicitly accept through the canonical transition and observe the resulting canonical task state.
8. Covered actions handle application errors and illegal transitions without crashing or silently changing local state.
9. No new lifecycle, scheduler, validation, review, revision, recovery, authorization, or persistence rules are implemented in the TUI.
10. No M09 behavior/state, Controller specialization path, model default, promotion gate, or M08 supervised-curation authority changes.

## Required review

Perform one independent review after implementation. Review the complete vertical slice against the canonical application/read boundaries and verify that the TUI delegates legality, authorization, lifecycle mutation, validation, scheduling, and persistence to existing Rust APIs.

Validation belongs to the review stage. Execution and revision provider agents must not spend separate turns running validation. The independent review should run focused TUI/application tests plus the smallest relevant repository regression set required by the changed Rust surface, then `cargo fmt --check`, clippy for affected supported feature sets, and `git diff --check`.

The reviewer must exercise or test the normal sequence: create → queue/detail → dispatch → execution refresh → validation/review evidence → revision when required → accept. Error/illegal-action behavior must also be covered.
