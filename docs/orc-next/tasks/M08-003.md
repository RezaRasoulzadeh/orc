# M08-003 — Add explicit typed curation for Controller recovery recommendations

**Status:** Planned
**Milestone:** M08 — Experience dataset

## Objective

Add the next capability-local curation adapter for one already-produced Controller recovery interaction, projecting the existing typed recovery inference input and existing canonical recovery recommendation into one M08-001 experience example under explicit trusted verification metadata.

This extends the proven M08-002 pattern to recovery without introducing a generic capture framework, automatic harvesting, or workflow-derived labeling.

## Repository-grounded context

M08-001 provides the canonical global dataset record and bounded persistence APIs. M08-002 proved one capability-local typed projection for normal task recommendation.

Recovery already has canonical typed inference data in `src/recovery_controller.rs`:

- `RecoveryInferenceInput` — current recovery request plus bounded advisory memory;
- `RecoveryRecommendation` — canonical structured output containing `decision`, bounded rationale, and optional confidence;
- `RecoveryRecommendationValidation` — deterministic post-inference legality/actionability result against the exact inspected legal-operation set.

Recovery output intentionally contains no task identity or execution authority. The recovery input's `current_request.observation.task_id` is the canonical task identity for provenance consistency.

The smallest next M08 seam is explicit curation of the reasoning interaction itself. Dataset creation must not infer trust from whether a recovery operation later executed, succeeded, advanced workflow, or passed another gate.

## Scope

Add one recovery-specific typed curation request and the smallest `OrcApp` API needed to persist one explicitly verified recovery example.

The adapter must accept:

- one existing `RecoveryInferenceInput`;
- one observed existing `RecoveryRecommendation`;
- one explicit accepted/expected `RecoveryRecommendation`;
- explicit `ControllerExperienceVerificationBasis`;
- explicit M08-001 outcome and quality metadata;
- optional M08-001 provenance;
- correction metadata only when observed and accepted canonical outputs differ.

Do not accept a caller-controlled capability identifier.

## Canonical capability

Use one fixed code-owned capability identifier for Controller recovery recommendation, e.g. `controller.recovery_recommendation` unless an established repository naming convention requires an equivalent exact identifier.

The identifier must not be caller-overridable.

## Canonical input projection

Use the exact supplied `RecoveryInferenceInput` as the dataset input authority.

Before projection:

- call/reuse its existing canonical validation;
- serialize the exact typed value deterministically;
- do not rebuild another recovery-input schema;
- do not summarize, reorder, enrich, truncate, or derive fields;
- do not replace current recovery facts with later workflow state.

If existing validation returns a serialized string rather than a reusable unit validation result, expose only the smallest reusable deterministic seam necessary. Do not alter inference prompt/schema/bounds or behavior.

## Canonical output projection

Use the existing `RecoveryRecommendation` structured contract as the dataset output authority.

Observed and accepted recommendations must both pass the exact production recovery recommendation validation contract.

Persist the exact accepted canonical structured recovery recommendation as M08 `accepted_output`.

Do not use execution outcome, `RecoveryRecommendationValidation`, free-form workflow events, or later operator actions as substitutes for the accepted reasoning output.

`RecoveryRecommendationValidation` may be preserved only as explicit bounded provenance/evidence if the existing M08 provenance model already supports it without schema expansion; otherwise it remains outside this task. Do not widen M08-001 merely to store it.

## Task/provenance consistency

The canonical task identity is `input.current_request.observation.task_id`.

If M08 provenance contains `task_id`, it must either be absent or exactly equal to that input task identity. A conflicting provenance task ID must reject before persistence.

Project/run/Plan/review/memory provenance remains non-owning metadata under M08-001 rules.

Do not query workflow state merely to fill missing provenance.

## Correction semantics

Compare the canonical serialized/structured observed and accepted `RecoveryRecommendation` values.

If observed == accepted:

- correction metadata must be absent;
- outcome must satisfy the existing valid non-correction M08-001 semantics;
- do not manufacture correction data.

If observed != accepted:

- outcome must be `Corrected`;
- explicit valid correction metadata is required;
- `correction.original_output` must exactly equal the canonical observed recovery recommendation projection;
- M08-001 accepted output must exactly equal the canonical accepted recommendation projection.

Do not infer a correction because a recovery action was rejected, failed, retried, or later changed.

## Verification boundary

Verification remains explicit and caller-owned.

Do not automatically treat any of the following as sufficient verification:

- `RecoveryRecommendationValidation::Actionable`;
- recovery authorization success;
- recovery execution success;
- task requeue/resume success;
- workflow advancement;
- validation/review results;
- operator continuation or acceptance.

Those are potential evidence sources for later explicit curation policy, not automatic labels in M08-003.

## Production order

1. validate the exact `RecoveryInferenceInput` through the existing canonical recovery input contract;
2. validate observed `RecoveryRecommendation` through the existing canonical recovery output contract;
3. validate accepted `RecoveryRecommendation` through the same contract;
4. validate provenance task identity consistency;
5. deterministically project exact input, observed output, and accepted output;
6. enforce observed/accepted correction semantics;
7. construct exactly one `ControllerExperienceExampleDraft` with the fixed capability identifier;
8. delegate final bounds/verification/outcome/quality/provenance validation to M08-001;
9. persist only through existing `OrcApp::create_controller_experience_example(...)`.

At most one dataset row may be written per call. Every pre-persistence failure writes zero rows.

## Invariants / requirements

- Recovery recommendation only; no generic experience adapter.
- Explicit trusted call only.
- No Controller inference.
- No automatic harvesting.
- No workflow/recovery hook.
- No automatic label or verification inference.
- No caller-controlled capability string.
- Exact canonical `RecoveryInferenceInput` preserved as dataset input.
- Exact canonical accepted `RecoveryRecommendation` preserved as dataset output.
- Existing recovery prompt/schema/parser/bounds/legality semantics unchanged.
- `RecoveryRecommendationValidation` remains a deterministic runtime legality result, not the dataset target.

## Non-goals

- Automatic capture of recovery calls.
- Automatic curation from recovery execution or workflow outcomes.
- Normal recommendation changes.
- Planning/intake/Plan review/Plan revision/memory-judgment adapters.
- Generic curation framework across capabilities.
- Dataset export or trainer formats.
- Dataset deduplication/ranking/sampling/balancing/splitting.
- Fine-tuning/evaluation runner changes.
- Runtime memory changes.

## Acceptance criteria

1. One explicit application API persists one verified recovery reasoning interaction as one M08-001 example.
2. Capability identity is fixed and not caller-controlled.
3. Dataset input is the exact validated typed `RecoveryInferenceInput` projection.
4. Dataset accepted output is the exact canonical typed `RecoveryRecommendation` projection.
5. Observed and accepted recommendations use the same production recovery validation contract.
6. Optional provenance task identity cannot contradict the input recovery task identity.
7. Equal outputs produce a non-correction example; differing outputs require explicit corrected outcome and exact observed-output correction metadata.
8. Invalid/mismatched/unbounded data creates zero rows.
9. Successful curation creates exactly one row through M08-001 only.
10. No recovery inference/legality/workflow behavior changes and no automatic harvesting/verification is introduced.
