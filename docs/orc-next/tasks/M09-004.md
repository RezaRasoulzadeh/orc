# M09-004 — Define deterministic Controller candidate promotion gate

**Status:** Planned
**Milestone:** M09 — Controller specialization

## Objective

Define one deterministic, model-independent candidate-vs-baseline comparison gate over M09-003 baseline reports so Controller specialization acceptance criteria are fixed before any candidate training result is observed.

This task defines comparison semantics only. It does not choose a trainer, train a model, transform the M09-001 dataset, run a candidate model, or change the default Controller model.

## Repository-grounded context

M09-001 provides the deterministic trainer-neutral Active Controller experience snapshot.

M09-002 provides one explicit semantic evaluation suite covering all nine current inference-backed Controller capabilities.

M09-003 provides a typed versioned baseline-report boundary over that exact suite, preserving model/runtime identity, scenario order, expected/observed semantics, distinct parse/validation/runtime evidence, and exact global/per-capability aggregates.

D-006 requires controlled learning and evaluation rather than blind weight mutation. Defining candidate acceptance after seeing candidate results would make promotion policy vulnerable to post-hoc benchmark fitting. The comparison rule therefore belongs before backend selection and controlled training.

## Scope

Add a versioned typed comparison/promotion decision boundary that consumes two validated M09-003-compatible reports:

- baseline report;
- candidate report.

The comparison must first prove the reports are comparable, then produce deterministic per-scenario, per-capability, and global deltas plus an explicit promotion decision and machine-readable reasons.

No inference is required for deterministic acceptance tests. Synthetic validated baseline/candidate reports must be sufficient to exercise the complete gate.

## Comparability contract

Fail closed unless baseline and candidate reports share the same evaluation authority and semantically relevant runtime contract.

At minimum require equality of:

- M09-003 baseline-report schema compatibility required by the comparator;
- M09-002 suite schema version;
- scenario count;
- exact ordered scenario IDs;
- exact ordered capability identifiers;
- exact expected semantic results and acceptable alternatives;
- production request parameters for every scenario;
- semantically relevant runtime configuration required for fair comparison.

The candidate model identity must be distinct from the baseline identity or the result must be explicitly classified as a non-candidate/self-comparison rather than silently treated as promotion evidence.

Do not compare reports from different suites by aligning on partial IDs or intersecting scenarios.

## Gate semantics

The promotion gate must be explicit and conservative.

A candidate is promotable only when all of the following hold:

1. Reports are fully comparable under the contract above.
2. Candidate global passed count is strictly greater than baseline global passed count.
3. Candidate global execution/error count does not increase.
4. No capability has fewer passing scenarios than baseline.
5. No scenario that passed in the baseline becomes non-passing in the candidate.
6. Candidate introduces no new Parse, Validation, or Runtime failure on a scenario that did not have that same failure class in the baseline.
7. Aggregate accounting in both inputs and the produced comparison remains exact.

These are deterministic safety criteria, not statistical claims. Do not invent confidence intervals, weighted scores, or significance thresholds for the current bounded canonical suite.

A candidate that improves some scenarios but violates any regression rule must be rejected with explicit reasons.

## Comparison evidence

Add typed structures sufficient to record:

- comparison schema version;
- baseline model identity;
- candidate model identity;
- shared suite identity;
- per-scenario baseline status;
- per-scenario candidate status;
- per-scenario transition classification;
- per-capability baseline/candidate aggregates and exact deltas;
- global baseline/candidate aggregates and exact deltas;
- comparability status;
- final decision such as `Promote`, `Reject`, or explicit non-comparable/self-comparison outcome;
- deterministic ordered machine-readable rejection reasons.

Prefer enums and typed values over free-form strings for authoritative reason classes. Human-readable detail may accompany typed reason codes but must not determine the decision.

## Determinism and validation

- Input reports must validate before comparison.
- Scenario comparison follows canonical scenario order.
- Capability comparison follows fixed deterministic capability order.
- Reason ordering is deterministic and duplicate-free.
- Repeated comparison of identical inputs serializes identically.
- Impossible deltas/accounting fail closed.
- Unknown scenario/capability data is never ignored.
- Comparison must not mutate either input report.

## Production-boundary constraints

Do not:

- run inference as part of the core comparator;
- change M09-002 expectations;
- change production prompts, parsers, schemas, runtime request settings, or capability semantics;
- tune the gate against observed candidate results;
- derive weights from M09-001 examples;
- choose a trainer/backend;
- perform dataset export/transformation/splitting/sampling/balancing/deduplication/ranking/weighting;
- train or modify model weights;
- change the default Controller model;
- execute Controller intents;
- mutate task, Plan, workflow, memory, experience, registry, or project state;
- add benchmark persistence tables;
- add embeddings, Python runtime dependencies, provider fallback, or provider token hard caps.

## Non-goals

- Real-model execution.
- Training backend investigation or selection.
- Fine-tuning/LoRA/adapters.
- Statistical significance analysis.
- Latency, throughput, memory, energy, or token-efficiency benchmarking.
- Human preference scoring.
- Automatic production deployment or model-default mutation.
- Persisting promotion decisions.

## Acceptance criteria

1. A versioned typed comparator consumes validated baseline and candidate M09-003 reports without inference or mutation.
2. Non-comparable suite/scenario/expectation/request/runtime evidence fails closed.
3. Exact per-scenario transitions, per-capability deltas, and global deltas are deterministic and validated.
4. Promotion requires strict global improvement and zero baseline-pass regressions.
5. Promotion rejects any per-capability pass-count regression.
6. Promotion rejects newly introduced Parse, Validation, or Runtime failures under the defined failure-class rule.
7. Authoritative decision/reason semantics are typed and deterministic rather than prose-parsed.
8. Synthetic deterministic tests cover promote, reject, non-comparable, and self-comparison outcomes without a model file.
9. No training, production inference, storage, workflow, memory, dataset, or model-default behavior changes.
