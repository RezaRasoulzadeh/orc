# M07-004 — Route one Controller workflow task edge through a continuation grant

**Status:** Done
**Milestone:** M07 — Supervised autonomy

## Objective

Integrate the M07-003 supervised one-step continuation boundary into exactly one `WorkflowEngine::continue_one`-style task edge for Controller workflows, so the workflow’s trusted current stage supplies the expected routine action and one finite continuation-grant unit can authorize at most that one edge.

This is the smallest workflow integration seam. It must reuse the existing restart-safe workflow transition engine rather than adding a new continuation loop.

## Repository-grounded context

`WorkflowEngine` already owns the authoritative persisted lifecycle. `continue_one_inner()` commits at most one legal transition, and `advance()` deterministically maps task stages:

- `WorkflowStage::Dispatch` → dispatch current task;
- `WorkflowStage::Review` → semantic review current task;
- `WorkflowStage::Revision` → revise current task;
- `WorkflowStage::Acceptance` remains a separate deterministic acceptance gate.

`route_tasks()` already chooses the exact task and stage from canonical task state. M07 must not add Controller-driven task enumeration or another scheduler.

M07-003 refined `OrcApp::continue_controller_action_once(task_id, expected_action, grant, runtime, context)` so a trusted caller can require exactly `Dispatch`, `SemanticReview`, or `Revise` before grant inspection. Wrong recommendations consume zero grant budget. Matching recommendations still pass through M07-001 and exact M03 execution with fresh legality.

The current workflow task-stage implementation directly invokes `WorkflowActions::dispatch`, `review`, or `revise_task`. Controller workflows already carry a local runtime through `continue_one_inner`/`advance`, but no continuation grant is currently available at those task stages.

## Scope

Add one explicit opt-in single-edge workflow continuation path that accepts a local Controller runtime plus one existing M07-001 continuation grant and reuses the current workflow stage as the trusted expected action.

Required behavior:

- expose the smallest `WorkflowEngine` API needed to continue **at most one persisted workflow edge** with both a Controller runtime and an existing continuation grant;
- do not change existing `continue_one`, `continue_run`, or `continue_run_with_controller_runtime` semantics;
- require a Controller workflow (`WorkflowPlanPath::Controller`) before using grant-aware task continuation;
- only `Dispatch`, `Review`, and `Revision` task stages may consume the continuation grant;
- derive the expected existing `ControllerActionKind` deterministically from the current persisted workflow stage:
  - `Dispatch` → `ControllerActionKind::Dispatch`;
  - `Review` → `ControllerActionKind::SemanticReview`;
  - `Revision` → `ControllerActionKind::Revise`;
- use the exact persisted `current_task_id`; the Controller cannot choose or replace the task;
- route the selected task through the existing M07-003 `OrcApp::continue_controller_action_once()` boundary;
- trusted application code constructs the action-specific `ControllerActionExecutionContext`; model output never supplies provider/agent/runtime/backend/validation handles or overrides;
- on an M07-003 executed result, map persisted canonical evidence back into the **existing** workflow `ProviderOutcome` or `ReviewOutcome` expected by the current stage transition logic;
- preserve existing workflow transition mapping, edge names, revision counters, review verdict handling, acceptance policy, task-status checks, provider-run provenance, and transition persistence;
- a non-executed M07-003 result must not be silently converted into success; it must stop/fail the attempted workflow edge through the existing workflow error/stop semantics without a second Controller inference or fallback provider call;
- grant rejection, expected-action mismatch, no-action recommendation, fresh-legality rejection, context failure, or canonical execution failure must not trigger the legacy direct `dispatch`/`review`/`revise_task` path as fallback;
- exactly one workflow edge, at most one Controller inference, at most one successful grant-budget consumption, and at most one routine task action per API call.

## Integration guidance

Prefer extending the existing internal `continue_one_inner` / `advance` dependency flow with an optional trusted grant alongside the already optional Controller runtime, or an equivalently small capability-local seam.

If the generic `WorkflowActions` boundary needs an opt-in Controller task-action adapter, keep it source-compatible for existing test/custom implementations with a default non-participating method. The production `AppWorkflowActions` implementation should be the only adapter that constructs trusted execution contexts and invokes `OrcApp::continue_controller_action_once()`.

Do not create a second workflow state machine or duplicate the existing Dispatch/Review/Revision transition logic. The new path should produce the existing stage outcomes and then let the current `advance()` logic perform canonical task-state/verdict/counter/transition decisions.

For `SemanticReview`, derive the existing review verdict and revision feedback from canonical persisted review/run evidence after successful M03 execution; do not trust arbitrary Controller text and do not invent a second review result schema.

For Dispatch/Revision, preserve existing canonical run identity where available. If the existing M03 revision path legitimately yields no direct run ID in a configured path, use the same canonical persisted post-action evidence already used elsewhere rather than fabricating provider provenance.

## Invariants / requirements

- `WorkflowEngine` remains the sole restart-safe workflow continuation engine.
- Existing workflow persisted stage/status/task identity is authoritative.
- No model-generated workflow stage, task selection, transition edge, revision count, acceptance decision, execution context, or grant scope.
- Reuse M07-003 expected-action enforcement; do not duplicate it with another action schema.
- Reuse M07-001 grant semantics and M03 authorization/fresh legality/canonical mutation.
- Grant budget is consumed only when M07-001 successfully mints exact M03 authorization.
- Wrong expected/proposed action and other pre-mint rejection preserve zero-consumption semantics.
- Post-mint failure does not refund grant budget.
- Existing `WorkflowPolicy.max_task_revisions` and `max_transitions` remain authoritative and unchanged.
- Acceptance is never grant-driven in this task. `WorkflowStage::Acceptance` keeps existing policy/user gate behavior and cannot consume a continuation grant.
- Planner/PlanReview/Lead/Discovery/ApplyPlan/ApplyDirect are unchanged.
- Existing legacy/provider workflow path remains unchanged.
- No automatic repeated continuation while grant budget remains.
- No grant persistence/recovery across restart.
- No retry, fallback provider execution, automatic recovery, task enumeration, or memory automation.
- No provider token hard cap, model-specific behavior, or Python.

## Non-goals

- Passing a continuation grant through `continue_run_with_controller_runtime` for repeated multi-edge execution.
- Automatically spending all remaining grant budget.
- Persisting or reconstructing grants after restart.
- Automatically accepting tasks or resolving user/Plan gates.
- Changing scheduler behavior or task-selection ordering.
- Changing Controller recommendation prompt/schema/bounds/semantics.
- New CLI/TUI/GUI controls.
- Automatic memory capture/maintenance.

## Acceptance criteria

1. One explicit workflow API can continue at most one edge using a supplied Controller runtime and continuation grant.
2. The workflow current persisted stage deterministically supplies the expected routine action; the Controller cannot choose another action or task.
3. Controller Dispatch stage executes only through M07-003/M07-001/M03 and then uses existing workflow Dispatch transition logic.
4. Controller Review stage executes only through the same supervised chain, then reconstructs the existing `ReviewOutcome` from canonical persisted evidence and uses unchanged PASS/REVISE/REJECT routing.
5. Controller Revision stage executes only through the supervised chain and uses unchanged revision count/task-status transition logic.
6. Any non-executed supervised result stops/fails that edge without fallback provider execution, second inference, or second action.
7. Acceptance and all non-task stages cannot consume the grant through this API.
8. Existing legacy workflow behavior and existing controller Plan/intake/review/revision workflow behavior remain unchanged.
9. Existing transition persistence, provider provenance, workflow limits, and restart semantics remain authoritative.
