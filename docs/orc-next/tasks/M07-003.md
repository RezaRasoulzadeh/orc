# M07-003 — Constrain supervised continuation to one expected routine action

**Status:** Done
**Milestone:** M07 — Supervised autonomy

## Objective

Add the smallest trusted expected-action constraint to the M07-002 one-step continuation seam so a deterministic caller such as `WorkflowEngine` can require exactly one routine action kind before any continuation-grant budget is consumed.

This prepares the existing one-step Controller continuation path for safe composition with deterministic workflow stages. It does **not** integrate continuation grants into the workflow loop yet.

## Repository-grounded context

M07-002 added `OrcApp::continue_controller_action_once()`, which performs one `propose_controller_action` inference, checks exact task identity, inspects the M07-001 grant, then executes the exact authorized intent through M03.

`WorkflowEngine` already owns deterministic task stages `Dispatch`, `Review`, and `Revision`. Each stage already implies one canonical routine action, so a future workflow integration must be able to reject a Controller recommendation for a different action **before** grant authorization. Otherwise an action/context mismatch can consume a grant unit even though the deterministic workflow stage never permitted that action.

`ControllerActionExecutionContext` is trusted application-owned state and action-specific, while `ControllerActionIntent` / `ControllerActionKind` remain the canonical action schema. No new action or policy schema is needed.

## Scope

Extend the existing M07-002 one-step continuation seam with an explicit trusted expected routine action constraint.

Required behavior:

- trusted application/operator code supplies exactly one expected existing `ControllerActionKind` together with the explicit task, grant, runtime, and execution context;
- only `Dispatch`, `SemanticReview`, and `Revise` are valid expected actions for this continuation seam;
- `Accept` is rejected deterministically as an invalid expected continuation action;
- perform the existing Controller recommendation exactly once;
- after exact task-identity validation and before M07-001 grant inspection, compare the proposed intent action to the trusted expected action;
- if the proposal is for another action, return a bounded typed non-executed result without inspecting the grant, consuming budget, or mutating state;
- if the proposed action matches, preserve the existing M07-002 sequence unchanged: grant inspection → exact M03 authorization → fresh-legality execution;
- the expected-action value is trusted caller input only and is never inferred, widened, persisted by the model, or supplied through Controller structured output;
- preserve existing execution-context mismatch behavior as a final trusted M03 defense, while allowing deterministic callers to construct a context matching the expected action.

## Invariants / requirements

- Reuse `ControllerActionKind`, `ControllerActionIntent`, `ControllerContinuationGrant`, `ControllerContinuationStepResult`, M03 authorization, and existing execution paths.
- Do not introduce a second action enum, policy object, grant type, authorization token, or mutation path.
- The expected-action check occurs before grant inspection and therefore before budget consumption.
- A mismatched recommendation consumes zero grant units and executes nothing.
- `Accept` cannot be an expected routine action and cannot reach grant inspection.
- Exact caller-supplied task identity remains authoritative.
- The model cannot change expected action, execution context, grant scope, project binding, budget, workflow stage, agent/provider selection, validation runner, or acceptance policy.
- Existing M03 fresh legality remains authoritative after successful grant authorization.
- Scheduler/agent permissions, availability, quota/economy facts, lifecycle, validation/review evidence, revision feedback, and workflow limits remain authoritative.
- At most one inference, one successful grant consumption, and one action execution per call.
- No retry, second recommendation, automatic task selection, workflow continuation, automatic acceptance, recovery loop, or automatic memory invocation.
- No provider token hard cap, model-specific behavior, or Python.

## API guidance

Prefer the smallest additive or signature-level refinement of `OrcApp::continue_controller_action_once()` that makes the trusted expected action explicit. Avoid creating a parallel continuation function unless compatibility requires it.

The bounded result should expose an explicit expected-action mismatch/rejection outcome using existing action kinds. Do not encode arbitrary model text or duplicate lifecycle state.

## Non-goals

- Integrating grants into `WorkflowEngine`.
- Repeated continuation while budget remains.
- Automatic workflow/task enumeration.
- Automatic `Accept`, Plan approval, or user-decision resolution.
- Persisting continuation grants or expected-action constraints.
- New Controller prompts or schemas.
- Automatic memory capture/maintenance.
- CLI/UI design.

## Acceptance criteria

1. The one-step continuation API accepts one explicit trusted expected routine `ControllerActionKind`.
2. Only `Dispatch`, `SemanticReview`, and `Revise` are valid expected actions; `Accept` is rejected before grant inspection.
3. A Controller proposal whose action differs from the expected action returns a bounded non-executed result with zero grant consumption and zero mutation.
4. Exact task-identity validation remains in force independently of the expected-action check.
5. A matching proposal follows the unchanged M07-002 grant-inspection and exact M03 execution chain.
6. Successful authorization still consumes exactly one unit; post-mint execution failure still does not refund it.
7. Trusted execution context and fresh M03 legality remain independent final enforcement boundaries.
8. No workflow integration, loop, retry, task enumeration, automatic acceptance, or second action/supervision system is added.
