# M07-009 — Compose one supervised Controller memory maintenance step

**Status:** Planned
**Milestone:** M07 — Supervised autonomy

## Objective

Compose the existing M06-011 maintenance judgment, M06-009 mutation proposal/execution boundary, and M07-008 finite maintenance grant into one explicit application-level operation that processes exactly one caller-supplied maintenance request and may perform at most one eligible project-bound maintenance mutation.

This task proves the complete supervised maintenance chain without yet deciding when Orc should select maintenance targets or invoke maintenance automatically.

## Repository-grounded context

The required pieces already exist:

- `OrcApp::judge_controller_memory_maintenance(...)` resolves one explicit active target, constructs bounded canonical maintenance input, performs at most one M06-011 inference, and returns only `Keep` or one exact-target `Correct`/`Supersede`/`Remove` intent.
- `OrcApp::propose_controller_memory_mutation(...)` converts one intent into the canonical M06-009 proposal after deterministic current-project/target legality checks.
- `OrcApp::inspect_controller_memory_maintenance_grant(...)` checks one existing M06-009 proposal against a finite M07-008 grant and mints the existing exact one-shot M06-009 authorization only for exact-current-project Project/Episodic maintenance.
- `OrcApp::execute_authorized_controller_memory_mutation(...)` performs fresh M06-009 validation and canonical `MemoryService` mutation.

No new inference schema, permission model, mutation schema, persistence path, retry loop, or workflow engine is required. The missing seam is one-step composition analogous to M07-007 capture composition, but capability-specific to maintenance.

## Scope

Add the smallest `OrcApp` API needed to process exactly one explicit `ControllerMemoryMaintenanceRequest` with one supplied local Controller runtime and one existing M07-008 maintenance grant.

Required behavior:

- accept exactly one existing `ControllerMemoryMaintenanceRequest`, one `LocalInferenceRuntime`, and one existing `ControllerMemoryMaintenanceGrant`;
- resolve/validate the explicit target through the existing M06-011 application path;
- perform at most one maintenance inference;
- if M06-011 returns `Keep`, stop successfully with an explicit non-mutating outcome; consume zero maintenance-grant units and perform no proposal/authorization/execution;
- if M06-011 returns `ProposeMutation`, preserve the exact returned maintenance intent and pass it through `OrcApp::propose_controller_memory_mutation(...)`;
- pass the resulting exact canonical proposal through `OrcApp::inspect_controller_memory_maintenance_grant(...)`;
- execute only via `OrcApp::execute_authorized_controller_memory_mutation(...)` using the exact authorization minted for that proposal;
- at most one durable maintenance mutation may occur per call;
- successful authorization mint consumes exactly one M07-008 grant unit;
- any failure/rejection before grant authorization consumes zero grant units;
- a failure after grant authorization is minted receives no refund;
- no retry, second inference, alternate proposal, fallback authorization, fallback direct mutation, or grant replenishment;
- returned result must clearly distinguish at minimum: kept/no mutation, mutated successfully, and failure/rejection after a proposed maintenance path;
- do not expose raw mutation/storage/authorization handles to the model;
- do not let the model select or modify grant scope, budget, project identity, execution path, or persistence metadata.

## Exact composition order

The canonical path must remain:

1. caller supplies one explicit `ControllerMemoryMaintenanceRequest`;
2. existing M06-011 `judge_controller_memory_maintenance(...)`;
3. if `Keep`: stop, zero grant consumption;
4. if `ProposeMutation`: existing M06-009 `propose_controller_memory_mutation(...)`;
5. existing M07-008 `inspect_controller_memory_maintenance_grant(...)`;
6. existing M06-009 `execute_authorized_controller_memory_mutation(...)`;
7. return one bounded typed outcome.

Do not collapse or bypass these boundaries merely to reduce code.

## Result semantics

Introduce the smallest state-safe typed result needed for the composed operation. Exact naming may follow repository conventions.

The public result must make the following observable without exposing authorization internals:

- maintenance judgment returned Keep and no mutation occurred;
- an eligible maintenance proposal mutated successfully, including the canonical mutation result/record identity needed by trusted callers;
- the composed step stopped because judgment/proposal/grant/execution failed or was rejected.

Do not repeat the M07-007 impossible-state mistake. The public type must not allow:

- a successful step to wrap a non-success `ControllerMemoryMutationExecutionResult`;
- an execution rejection to wrap a successful `Mutated` result;
- a stage/error mismatch constructed independently by callers.

Use state-safe wrappers/variants or equivalent repository conventions so impossible combinations cannot be constructed through the public API. Reuse existing underlying M06-009/M06-011/M07-008 result/error types where practical.

Inference/runtime errors and malformed M06-011 output must remain distinguishable from proposal rejection, grant rejection, and mutation execution failure.

## Invariants / requirements

- Exactly one explicit maintenance target/request per call.
- At most one Controller maintenance inference per call.
- At most one M06-009 proposal per call.
- At most one M07-008 authorization mint per call.
- At most one M06-009 execution attempt per call.
- `Keep` consumes zero grant units.
- M06-011 request/target/input/output/inference failure before proposal consumes zero.
- M06-009 proposal rejection before authorization consumes zero.
- M07-008 grant rejection consumes zero.
- Successful M07-008 authorization consumes exactly one.
- Post-mint M06-009 execution/fresh-validation/storage failure is not refunded.
- Only Project/Episodic Correct/Supersede/Remove remains eligible through M07-008; this task must not weaken those checks.
- Create and User/Experience remain outside this composed path.
- M06-009 remains the sole canonical durable mutation path.
- M06-011 remains the sole maintenance judgment schema.
- M07-008 remains the sole automatic-capable maintenance permission boundary.
- No grant persistence or restart reconstruction.
- No second loop or retry policy.
- No provider fallback.
- No provider token hard cap.
- No Python or model-specific behavior.

## Non-goals

- Selecting or enumerating maintenance targets automatically.
- Invoking maintenance automatically after task/workflow/Plan/review/validation/recovery/lifecycle events.
- Scanning all active memories for maintenance candidates.
- Batch maintenance or consolidation.
- Automatic User/Experience maintenance.
- Capture/Create behavior.
- Background cleanup/consolidation.
- Semantic/vector retrieval or embeddings.
- Changing M06-011 prompt/schema/bounds.
- Changing M06-009 mutation legality or execution semantics.
- Changing M07-008 grant eligibility or budget semantics.
- CLI/TUI/GUI integration.

## Acceptance criteria

1. One explicit `OrcApp` API composes one caller-supplied maintenance request through M06-011 → M06-009 proposal → M07-008 grant → M06-009 execution.
2. One call performs at most one inference and at most one durable maintenance mutation attempt.
3. `Keep` returns a clear non-mutating outcome, leaves memory/history unchanged, and consumes zero grant units.
4. A valid Project or Episodic Correct/Supersede/Remove proposal can persist exactly one canonical mutation through existing M06-009 execution and consumes exactly one grant unit.
5. Create/global/User/Experience/ineligible proposals cannot bypass M07-008 and consume zero before authorization.
6. Exhausted/revoked/wrong-project grants stop with no mutation and zero additional consumption.
7. Judgment/proposal failure before authorization consumes zero.
8. Post-authorization fresh-validation/execution/storage failure consumes one and is not refunded.
9. Public result types cannot represent impossible success/rejection or mismatched stage/error states.
10. No retry, fallback, second inference, second proposal, direct mutation, automatic target selection, or background maintenance is introduced.
11. Existing M06-009, M06-011, M07-008, M07-006/M07-007 capture, routine-continuation, and workflow behavior remain unchanged.
