# M07-005 — Continue Controller workflows across routine task edges within one finite grant

**Status:** Done
**Milestone:** M07 — Supervised autonomy

## Objective

Extend the proven M07-004 single-edge workflow integration into the existing bounded `WorkflowEngine::continue_run_inner()` loop so one explicitly supplied in-process continuation grant can authorize multiple routine Controller task edges until a deterministic stopping boundary is reached.

This must reuse the existing workflow loop, transition budget, task routing, M07-004 task-edge adapter, M07-003 expected-action constraint, M07-001 grant semantics, and M03 execution boundary. It must not create a second autonomy loop.

## Repository-grounded context

M07-004 added `WorkflowEngine::continue_one_with_controller_grant(...)`. It is intentionally valid only when the persisted Controller workflow is currently at `Dispatch`, `Review`, or `Revision`; it executes at most one edge through the existing `continue_one_inner()` / `advance()` path.

The existing `continue_run_inner()` is already Orc's authoritative bounded repeated-continuation loop. It:

- persists every edge through `continue_one_inner()`;
- stops when workflow status is no longer `Running`;
- is bounded by the existing `WorkflowPolicy.max_transitions` budget;
- already carries an optional local Controller runtime for Controller intake/Plan judgment;
- already routes tasks deterministically through `route_tasks()`;
- already owns revision limits, external-wait reconciliation, user gates, and acceptance policy.

The M07-001 grant is also already finite, shared across clones, project-bound, revocable, and observable through `remaining_actions()` / `state()`. Therefore the next autonomy seam is composition, not a new permission or loop model.

## Scope

Add one explicit opt-in workflow API that continues an existing Controller workflow across multiple persisted edges while using one supplied continuation grant only for routine task actions.

Required behavior:

- add the smallest `WorkflowEngine` API needed to continue a Controller workflow with both a local Controller runtime and one existing M07-001 continuation grant;
- reuse the existing `continue_run_inner()` loop or an equivalently minimal parameterization of it;
- do not change existing `continue_run`, `continue_run_with_controller_runtime`, `continue_one`, or `continue_one_with_controller_grant` behavior;
- require `WorkflowPlanPath::Controller` for the new grant-aware multi-edge API;
- deterministic/non-routine workflow edges continue through the existing workflow engine and consume **zero** continuation-grant units;
- when the persisted stage is `Dispatch`, `Review`, or `Revision`, route exactly that edge through the existing M07-004 grant-aware task-action path;
- preserve exact stage → expected-action mapping and exact persisted `current_task_id` from M07-004;
- after a successful routine edge, continue through subsequent persisted workflow transitions while both the workflow and grant permit further progress;
- never infer task selection, workflow stage, grant scope, budget, acceptance, or transition metadata from the model;
- if the grant becomes exhausted before another routine task edge, stop before Controller inference or action execution for that next routine edge and persist/return an existing bounded workflow stop state rather than falling back to the direct provider path;
- if the grant is revoked, wrong-project, or otherwise unusable before the next routine edge, stop without executing or falling back;
- a non-executed M07-004/M07-003 routine action result still stops through the existing workflow failure semantics with no retry or fallback;
- existing `WorkflowPolicy.max_transitions` and `max_task_revisions` remain independent hard kernel limits and must never be widened by the grant;
- no single run may authorize more routine actions than the grant's remaining finite budget;
- the grant remains in-process only and is never serialized into workflow state or reconstructed after restart.

## Stopping boundaries

The new multi-edge path must stop rather than silently cross operator-controlled boundaries:

- `WorkflowStatus::WaitingUser`;
- `WorkflowStatus::AcceptanceReady`;
- `WorkflowStatus::WaitingExternal`;
- terminal/blocked/non-convergent/cancelled states;
- continuation-grant exhaustion/revocation/invalidity before a routine task edge;
- any M07-004 non-executed routine result.

`WorkflowStage::Acceptance` must remain outside the continuation grant. The grant-aware multi-edge path must not automatically execute `Accept`, even when the existing workflow policy is `AcceptancePolicy::Automatic`; reaching Acceptance is a stopping boundary for this supervised continuation API. Existing non-grant workflow APIs keep their current acceptance behavior unchanged.

Plan approval and explicit user-decision gates likewise retain their existing workflow semantics; the grant does not authorize them.

## Integration guidance

Prefer parameterizing `continue_run_inner()` with an optional trusted continuation grant and deciding at each persisted stage whether that grant is applicable.

The key distinction is:

- deterministic/routing/Controller planning edges: existing workflow behavior, zero continuation budget;
- `Dispatch` / `Review` / `Revision`: existing M07-004 grant-aware task edge;
- Acceptance/user/external/operator gates: stop.

Do not pass a non-`None` grant into `continue_one_inner()` for non-task stages if that would violate the M07-004 guard. The repeated loop should choose the existing ordinary edge path for non-task stages and the M07-004 path only for routine task stages.

Use existing `WorkflowStatus` values where possible. If continuation-grant exhaustion needs explicit workflow reporting, prefer the already existing `BudgetExhausted` status with a precise continuation-action-budget reason rather than adding a new status. This is an action-permission budget, not a provider token budget.

## Invariants / requirements

- `WorkflowEngine` remains the only repeated continuation engine.
- No second loop, scheduler, task selector, action enum, grant type, authorization type, or lifecycle model.
- Existing persisted workflow stage/status/current task remain authoritative before every edge.
- Every routine action still passes through M07-004 → M07-003 → M07-001 → M03 fresh legality → canonical mutation.
- Deterministic edges consume no grant units.
- One successful routine authorization consumes exactly one grant unit.
- Pre-mint rejection consumes zero.
- Post-mint failure is not refunded.
- Exhaustion is checked before attempting the next routine Controller inference where practical.
- No provider fallback after grant rejection/exhaustion or Controller refusal/mismatch.
- Existing transition budget remains independent of grant budget.
- Existing task revision limit remains independent of grant budget.
- Acceptance is never grant-authorized or automatically crossed by this API.
- No automatic user/Plan gate resolution.
- No grant persistence or restart reconstruction.
- No provider token hard cap, model-specific behavior, memory automation, or Python.

## Non-goals

- Persisting continuation grants across restart.
- Automatically creating grants.
- Automatically replenishing or extending grant budget.
- Automatic acceptance.
- Automatic user/Plan decision resolution.
- Recovery-policy redesign.
- Memory capture/maintenance automation.
- CLI/TUI/GUI controls.
- Changing Controller recommendation prompts/schemas/bounds.

## Acceptance criteria

1. One explicit API can continue a Controller workflow across multiple persisted edges with one supplied runtime and one existing finite continuation grant.
2. The implementation reuses the existing workflow loop rather than creating another repeated-continuation engine.
3. Deterministic/routing edges consume zero grant budget.
4. Each Dispatch/Review/Revision edge reuses the exact M07-004 supervised task-edge path and consumes at most one grant unit.
5. A two-or-more-routine-edge sequence can progress with a sufficient grant while preserving existing workflow transition persistence and counters.
6. Grant exhaustion before the next routine edge stops without another routine Controller inference, provider fallback, or action execution.
7. Revoked/wrong-project/invalid grants likewise stop before unauthorized routine execution.
8. `max_transitions` and `max_task_revisions` remain independently authoritative.
9. Acceptance/user/external gates stop the grant-aware multi-edge path; `Accept` is never executed by the continuation grant.
10. Existing non-grant workflow APIs and existing Controller Plan/intake/review/revision semantics remain unchanged.
