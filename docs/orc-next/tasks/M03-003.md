# M03-003 — Connect Controller recommendations to supervised typed actions

**Status:** Done
**Milestone:** M03 — Typed Controller tools

## Objective

Connect the read-only Controller recommendation path from M02 to the typed,
trusted action boundary completed in M03-001/M03-002, so Orc can turn a valid
Controller recommendation into a proposed `ControllerActionIntent` and a
trusted operator/application caller can explicitly authorize exactly one
execution.

This is the first end-to-end supervised Controller tool path. It is not an
autonomy loop: inference may propose one action, but trusted Orc code retains
authorization and the deterministic kernel retains legality and execution
authority.

## Why

The pieces now exist independently:

```text
bounded Controller state
        ↓
LocalInferenceRuntime
        ↓
ControllerRecommendation
```

and:

```text
ControllerActionIntent
        ↓
trusted one-shot authorization
        ↓
fresh deterministic legality check
        ↓
canonical Orc mutation
```

M03-003 should connect those boundaries without collapsing them. Model output
must remain a proposal. Recommendation parsing must not become authorization,
and the tool bridge must not create a hidden lifecycle loop.

## Required design

Establish a supervised path equivalent in responsibility to:

```text
ControllerStatePacket
        ↓
ControllerRecommendation
        ↓
typed recommendation → intent mapping
        ↓
proposed ControllerActionIntent
        ↓
trusted caller chooses whether to authorize
        ↓
M03-002 execution boundary
```

### Recommendation-to-intent mapping

- Map only recommendations that correspond exactly to the four supported M03
  actions: dispatch, semantic review, revise, accept.
- The mapping must be typed and deterministic. Do not parse arbitrary command
  strings or free-form rationale into executable behavior.
- The target task must come from bounded canonical Controller state / typed
  recommendation data, not from model-supplied paths, SQL, shell text, provider
  payloads, or native runtime data.
- Unsupported recommendations such as blocker resolution, dependency
  satisfaction, operator decision, planning, or future recovery actions must
  remain non-executable and return a bounded typed outcome.
- A mapped intent is still only a proposal. It does not carry authorization.

### Supervised execution

- Reuse M03-002 `ControllerActionAuthorization` and
  `execute_authorized_controller_action`; do not create a second execution
  path.
- Trusted Orc/application code must explicitly decide to authorize the proposed
  intent.
- Do not infer authorization from recommendation confidence, rationale, action
  kind, successful parsing, or current legality.
- Preserve the M03-002 fresh legality re-check at execution time.
- Execute at most one Controller-proposed action per explicit authorization.

### Read-only inference boundary

- Reuse the existing `ControllerStateBuilder`, recommendation schema/parser, and
  `LocalInferenceRuntime` boundary.
- Do not grant the local model access to `OrcApp`, `Database`, filesystem
  mutation, shell execution, Git mutation, workers, credentials, or network
  tools.
- Keep model/runtime details independent of Controller action/domain types.

## Scope

- Add a typed deterministic adapter from supported `ControllerRecommendation`
  values to proposed `ControllerActionIntent` values.
- Add a small supervised application seam that can obtain a recommendation and
  expose the resulting proposed intent without mutation.
- Allow a trusted caller to pass that exact proposed intent through the existing
  M03-002 authorization/execution boundary.
- Return bounded typed outcomes for:
  - supported actionable proposal;
  - unsupported/non-executable recommendation;
  - malformed/incompatible recommendation if applicable;
  - inference/runtime failure;
  - authorized execution result via the existing M03-002 result type.
- Add deterministic tests using fake local runtimes/backends; real model weights
  are not required for normal tests.

## Integration constraints

- Do not add authorization fields to `ControllerRecommendation` or
  `ControllerActionIntent`.
- Do not automatically authorize or execute a recommendation merely because it
  is legal.
- Do not loop inference → action → inference.
- Do not add retry/recovery/escalation behavior.
- Do not add new lifecycle actions beyond dispatch/review/revise/accept.
- Do not duplicate M03-001 legality or M03-002 execution logic.
- Do not change CLI/TUI/desktop behavior in this task.
- Do not expose arbitrary commands, SQL, paths, database handles, worker
  handles, provider payloads, or native inference objects through model-owned
  types.

## Non-goals

- Autonomous continuation.
- Recovery/blocker resolution tools.
- Dependency mutation tools.
- Agent/economy selection by Controller.
- Planning/Lead migration.
- Memory or experience persistence.
- Scheduler redesign.
- Interface confirmation UX.
- Training/fine-tuning.
- Model replacement, GPU work, or Python.

## Dependencies

- M02-003 complete: reliable structured Controller output.
- M03-001 complete: typed intents and deterministic legality inspection.
- M03-002 complete and source-reviewed `PASS`: trusted one-shot authorization,
  fresh legality re-check, and canonical execution.

## Acceptance criteria

1. Supported Controller recommendations map deterministically to exactly one of
   the existing dispatch/semantic-review/revise/accept
   `ControllerActionIntent` variants without parsing arbitrary executable text.
2. Unsupported recommendation actions remain explicitly non-executable and
   cannot fall through to a default mutation.
3. Producing a recommendation or proposed intent performs no project/task/run/
   review/worktree/persistence mutation and cannot mint
   `ControllerActionAuthorization`.
4. A trusted caller can explicitly authorize a proposed intent and execute it
   only through the existing M03-002 boundary; no second mutation path is
   introduced.
5. The end-to-end supervised test proves:
   bounded state → fake runtime structured recommendation → typed intent →
   explicit trusted authorization → fresh legality check → canonical mutation,
   with the expected lifecycle/evidence result.
6. Tests prove that the same supported recommendation left unauthorized causes
   zero mutation, and that an unsupported recommendation cannot be executed.
7. Existing read-only Controller evaluation behavior remains unchanged. If the
   production recommendation prompt/schema must change, the real seven-scenario
   Qwen evaluation must be rerun before acceptance; otherwise it must not be run
   merely for this task.
8. Existing CLI/TUI/desktop behavior remains unchanged. No autonomy, recovery,
   planning, memory, scheduler, model, Python, or GPU work is introduced.

## Result

Implemented the supervised recommendation bridge without changing the M02
recommendation schema, parser or prompt. `propose_controller_action` maps the
typed `ControllerRecommendation.suggested_next_step` values `Dispatch`,
`RunSemanticReview`, `Revise`, and `Accept` to the corresponding
`ControllerActionIntent` variants, copying only the bounded typed task ID.
Rationale, response text, confidence and structured-output payloads are not
parsed for actions. `WaitForExecution`, `ResolveBlocker`,
`SatisfyDependencies`, `ConfigureEligibleAgent`, `None`, and an absent next
step return `ControllerActionProposal::Unsupported`; an oversized supported
task ID returns the bounded `Invalid` outcome.

`OrcApp::propose_controller_action` is a read-only application seam that
reuses `ControllerStateBuilder::recommend` and the pure adapter. It exposes no
authorization. A trusted caller must pass the exact proposed intent through
`OrcApp::authorize_controller_action`, then consume the resulting opaque
one-shot authorization with the unchanged
`OrcApp::execute_authorized_controller_action` M03-002 boundary. That boundary
performs the fresh `ProjectOperations::inspect_action` check and delegates
mutation to the existing canonical dispatch/review/revise/accept APIs.

Deterministic tests cover all four mappings, every unsupported next-step
variant, malformed supported task IDs, free-form text being ignored, no
mutation before authorization, and the complete fake-runtime supervised
dispatch path. The end-to-end path ends in canonical `Review` with one
persisted execution run; the existing M03-002 tests continue to verify the
fresh legality rejection and canonical lifecycle/evidence state for all four
authorized actions. No M02 production recommendation behavior or CLI/TUI/
desktop behavior changed, so Qwen reevaluation was not required. No M04
architectural blocker was identified.
