# M03-002 — Execute explicitly authorized Controller intents

**Status:** Done
**Milestone:** M03 — Typed Controller tools

## Objective

Add the first mutation-capable Controller boundary by executing an existing
`ControllerActionIntent` only when a trusted Orc caller explicitly authorizes
that execution and the deterministic kernel re-checks the intent's legality
immediately before invoking the existing canonical mutation path.

The Controller still proposes intent only. It must not be able to authorize
itself, bypass legality, provide arbitrary execution commands, or call storage
or worker backends directly.

## Why

M03-001 established a typed, read-only boundary:

```text
ControllerActionIntent
        ↓
ProjectOperations::inspect_action
        ↓
Allowed | Rejected
```

That inspection is intentionally advisory and cannot be treated as a durable
grant: project state may change between inspection and execution. M03-002 must
therefore introduce an explicit trusted authorization boundary and perform a
fresh canonical legality check at the mutation boundary before delegating to
Orc's existing dispatch/review/revise/accept implementation.

The goal is not to create a second lifecycle executor. The goal is to make the
existing Orc mutation surface safely callable from future Controller tools.

## Required design

Establish a boundary equivalent in responsibility to:

```text
ControllerActionIntent
        ↓
trusted Orc authorization / confirmation
        ↓
fresh deterministic legality inspection
        ↓
Rejected ───────────────→ no mutation
        │
      Allowed
        ↓
existing OrcApp / canonical action implementation
        ↓
bounded execution result
```

Names may follow repository conventions, but these responsibilities must remain
separate and inspectable.

### Authorization

- Authorization must be supplied by trusted Orc/application code, not inferred
  from Controller rationale or recommendation confidence.
- The model-produced intent must not contain an `approved`, `authorized`,
  `confirmed`, permission, or equivalent self-authorization field.
- Prefer an opaque/non-model-deserializable authorization value or equivalent
  trusted-call boundary so model JSON cannot manufacture authorization.
- Authorization is for one requested execution only. Do not persist it as a
  durable capability that allows later execution without another legality
  check.
- This task does not require adding a CLI/TUI/desktop confirmation UI. It adds
  the application boundary that those interfaces can later call explicitly.

### Legality re-check

- Reuse `ProjectOperations::inspect_action` from M03-001 immediately before
  mutation.
- An earlier `Allowed` observation is never sufficient by itself.
- If state changed and the fresh inspection is rejected, return the canonical
  rejection and perform no mutation.
- Do not duplicate dispatch/review/revise/accept legality rules in Controller
  execution code.

### Execution

Support only the four M03-001 intents:

- dispatch;
- semantic review;
- revise;
- accept.

After authorization and a fresh `Allowed` result, delegate to existing
`OrcApp` / canonical action APIs and preserve their validation, worker,
review/revision-lineage, persistence, worktree, and transaction behavior.

Execution-specific trusted configuration such as agent selection, reasoning
effort, backend/test doubles, or existing action overrides must come from
existing Orc/operator/application configuration or a trusted execution context.
Do not add these fields to the model-owned `ControllerActionIntent`, and do not
allow arbitrary shell commands, file paths, SQL, provider payloads, or native
runtime handles through the Controller boundary.

## Scope

- Add a small trusted authorization/execution boundary for
  `ControllerActionIntent`.
- Re-check M03-001 legality immediately before every mutation.
- Execute the four existing action kinds through canonical Orc application
  APIs, without reimplementing their lifecycle behavior.
- Return a typed/bounded result that distinguishes at least:
  - authorization rejected/missing;
  - fresh legality rejection;
  - canonical execution success;
  - canonical execution failure.
- Preserve enough factual information for later Controller/operator
  observability without exposing raw storage handles or unrestricted backend
  data.
- Add deterministic tests using existing testable worker/backend seams where
  external execution would otherwise be required.

## Integration constraints

- `ControllerActionIntent` remains model-independent and intent-only.
- The Controller cannot grant its own permission.
- `ProjectOperations::inspect_action` remains the canonical pre-execution
  legality check.
- Existing `OrcApp`/agent/automated action implementations remain authoritative
  for mutation and transaction semantics.
- Do not map intents to CLI parsing or shell execution.
- Do not call SQLite/`Database` directly from Controller execution code when an
  application/canonical mutation API exists.
- Do not introduce a parallel dispatch, review, revise, or accept implementation.
- Do not weaken explicit operator acceptance/cancellation gates already enforced
  by Orc.
- Do not allow a previously inspected `Allowed` result to bypass the fresh
  mutation-boundary check.

## Non-goals

- Autonomous continuation or repeated action loops.
- Controller recovery/blocker-resolution actions.
- Controller-selected agent/economy policy.
- Planning/Lead migration.
- Memory or experience persistence.
- Training/fine-tuning work.
- New CLI/TUI/desktop confirmation UX.
- Scheduler redesign.
- New worker/provider/runtime abstractions.
- Qwen/llama.cpp changes, GPU work, or Python.
- Persisted authorization tokens/capabilities.

## Dependencies

- M03-001 complete and source-reviewed `PASS`.
- Existing canonical dispatch, semantic-review, revise, and accept mutation
  paths remain authoritative.

## Acceptance criteria

1. A trusted execution API accepts a typed `ControllerActionIntent` plus
   explicit non-model authorization; Controller/model JSON cannot self-authorize
   an execution.
2. Every execution performs a fresh `ProjectOperations::inspect_action` check
   immediately before mutation and returns the canonical typed rejection without
   mutation when no longer legal.
3. Authorized legal dispatch, semantic review, revise, and accept delegate to
   existing canonical Orc mutation paths rather than reimplementing lifecycle,
   validation, review/revision, worker, worktree, or persistence logic.
4. Trusted execution configuration needed by worker-backed actions remains
   outside the model-owned intent and reuses existing Orc configuration/
   override/backend seams.
5. Deterministic tests prove unauthorized execution performs no mutation for at
   least one mutating action and prove a stale previously-allowed intent is
   rejected after canonical state changes before execution.
6. Deterministic tests exercise each of the four authorized legal execution
   paths using existing fake/testable backends where necessary and verify the
   resulting canonical lifecycle/evidence state, not merely that a wrapper
   returned success.
7. Execution results/rejections are typed and bounded; no arbitrary provider
   output, command, SQL, filesystem path, database handle, or native runtime
   object becomes part of the Controller action contract.
8. Existing CLI/TUI/desktop behavior and normal operator-invoked lifecycle
   commands remain unchanged. No autonomy, recovery, planning, memory, model,
   scheduler, Python, or GPU work is introduced.

## Result

Implemented the trusted one-shot Controller execution boundary in
`src/controller_actions.rs`.

- `ControllerActionAuthorization` is an opaque, non-serializable,
  non-cloneable intent fingerprint minted only by
  `OrcApp::authorize_controller_action`; execution consumes it and rejects
  missing or mismatched authorization before any read or mutation.
- `ControllerActionExecutionContext` keeps agent selection, model/effort
  overrides, validation runners, workers, and review backends outside the
  serializable `ControllerActionIntent`. Native worker/backend references
  cannot enter Controller JSON.
- `OrcApp::execute_authorized_controller_action` performs the fresh
  `ControllerActionIntent::inspect` / `ProjectOperations::inspect_action`
  check immediately before canonical execution. A fresh rejection returns
  `FreshLegalityRejected` and performs no mutation; earlier `Allowed`
  observations are not accepted as authorization.
- Dispatch delegates to `agent::dispatch_with_worker_on_db` for injected
  trusted workers or `agent::dispatch_selected_with_db_and_repo` for the
  configured path. Semantic review delegates to
  `OrcApp::automated_review_with_backend`. Revise delegates to
  `agent::revise_with_worker_on_db_with_overrides`, `OrcApp::revise`, or
  `OrcApp::revise_with_previous_agent`. Accept delegates to
  `OrcApp::accept` / `agent::accept_task`.
- `ControllerActionExecutionResult` is bounded and typed: it distinguishes
  authorization rejection, fresh legality rejection, canonical execution
  failure stage, and success with lifecycle/run/review/validation facts. It
  carries no provider output, command, SQL, path, storage handle, or runtime
  object.
- Focused tests now cover 10 Controller action tests, including unauthorized
  no-mutation, stale previously-allowed no-mutation, intent-contract bounds,
  and canonical lifecycle/evidence assertions for all four authorized
  actions.

Validation passed: `cargo test --lib` (303),
`cargo test --features llama-cpp --lib` (309), normal and feature-enabled
clippy with `-D warnings`, `cargo fmt --check`, and `git diff --check`.
The read-only Controller recommendation path did not change, so the real
Qwen evaluation was not rerun. No M03-003 blocker was discovered; its future
tool host must preserve this trusted token-minting/context boundary and must
not expose model JSON as an authorization source.
