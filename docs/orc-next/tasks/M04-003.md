# M04-003 — Execute explicitly authorized recovery recommendations

**Status:** Planned
**Milestone:** M04 — Recovery intelligence

## Objective

Complete the supervised recovery path by allowing a trusted Orc/application caller to explicitly authorize exactly one actionable M04-002 recovery recommendation, followed by a fresh deterministic recovery-legality inspection immediately before delegating to the existing canonical recovery mutation.

The Controller recommends; trusted Orc code authorizes; the kernel re-checks legality and executes.

## Required path

```text
RecoveryRecommendationResult
          ↓
Actionable recovery operation
          ↓
trusted Orc/application authorization
          ↓
fresh inspect_recovery / exact legality check
          ↓
Rejected ───────────────→ no mutation
          │
        Allowed
          ↓
existing canonical recovery mutation
```

## Scope

- Add a typed recovery execution intent/proposal derived only from an M04-002 `Actionable` validation result plus its bounded task identity.
- Add a recovery-specific opaque one-shot trusted authorization that cannot be deserialized or manufactured by the model.
- Bind authorization to the exact task and exact recovery operation.
- At the execution boundary, freshly call the canonical M04-001 recovery inspection and require the exact requested operation to still be `Allowed`.
- Never treat the earlier M04-002 `Actionable` result as a durable legality grant.
- Delegate successful execution to the current canonical Orc mutation for each operation:
  - `Requeue` → existing `OrcApp::requeue` / canonical database requeue path;
  - `ResumeRevision` → existing canonical revision execution path, with trusted execution dependencies/configuration kept outside model-owned types;
  - `AcknowledgeNonConvergence` → existing `OrcApp::unblock_non_convergence` / canonical acknowledgement path.
- Return a bounded typed execution result distinguishing authorization rejection, fresh-legality rejection, canonical execution failure, and successful execution evidence.
- Add deterministic tests for all three recovery operations, stale legality, mismatched/missing authorization, and zero mutation on rejection.

## Authorization rules

- The Controller cannot authorize itself.
- `RecoveryRecommendation`, `RecoveryInferenceRequest`, rationale, confidence, model output, and serialized recovery types must contain no authorization field/capability.
- Authorization must be native trusted Orc/application state, non-serializable, with no public model-facing constructor.
- One authorization permits at most one exact operation on one exact task and is consumed by execution.
- Do not reuse a prior M03 authorization token if doing so weakens type separation or allows normal-action/recovery confusion. Reuse the M03 authorization pattern/implementation concepts where appropriate, not model authority.

## Fresh legality requirement

Immediately before mutation:

1. validate the bounded execution request;
2. consume and match authorization to task + recovery operation;
3. freshly inspect canonical M04-001 recovery legality;
4. require the exact operation to be `Allowed`;
5. only then call the canonical mutation.

Any stale recommendation, changed lifecycle, changed dependency/revision/execution condition, or otherwise newly illegal operation must return a typed rejection with zero mutation.

## ResumeRevision boundary

`ResumeRevision` may require worker/agent/validation execution dependencies. These must remain trusted application-owned execution context, equivalent in principle to M03 `ControllerActionExecutionContext`; they must not be added to Controller recommendation/intent JSON.

Reuse the existing canonical revision implementation rather than implementing revision lifecycle logic inside recovery code.

## Constraints

- Reuse M04-001 `RecoveryOperation` and canonical legality inspection.
- Reuse M04-002 recommendation validation; do not create a second model recommendation path.
- Reuse existing `OrcApp` canonical recovery/revision mutations.
- No direct database/SQLite mutation from Controller recovery code.
- No arbitrary command, shell, path, SQL, provider payload, worker handle, credentials, or runtime object in model-owned types.
- Do not execute `OperatorDecision`; it must remain non-executable.
- Do not authorize a recommendation whose M04-002 validation is rejected or `OperatorDecision`.
- Do not add automatic inference→recovery→inference loops.
- Do not add new recovery operations.
- Do not weaken deterministic validation, dependency legality, review/revision lineage, acceptance, or cancellation gates.
- Keep M03 normal-action behavior unchanged.

## Non-goals

- Autonomous recovery loops.
- Retry/repair policy migration.
- Adding infrastructure repair, dependency repair, or economy escalation operations.
- Broad removal of existing hardcoded recovery/economy policy.
- Planning/Lead migration.
- Memory.
- CLI/TUI/desktop UX.
- Model/prompt/schema changes.
- Qwen evaluation changes.
- Model replacement, GPU work, or Python.

## Dependencies

- M04-001 complete and source-reviewed `PASS`.
- M04-002 complete, real Qwen recovery evaluation 7/7 strict + 7/7 semantic, and source-reviewed `PASS`.
- M03-002 authorization/execution boundary is the reference pattern for trusted one-shot authorization and fresh legality checks.

## Acceptance criteria

1. An actionable M04-002 recommendation can be converted to a bounded typed recovery execution intent without consulting rationale/free-form text.
2. `OperatorDecision` and rejected/illegal recommendations cannot become executable recovery intents.
3. Trusted Orc/application code can mint a non-serializable one-shot authorization bound to one exact task + recovery operation; the Controller/model cannot mint it.
4. Execution freshly re-inspects M04-001 recovery legality immediately before mutation and rejects stale/newly-illegal operations with zero mutation.
5. Allowed `Requeue`, `ResumeRevision`, and `AcknowledgeNonConvergence` delegate to their existing canonical Orc mutation paths rather than duplicating lifecycle logic.
6. Missing/mismatched authorization cannot reach mutation.
7. Execution returns bounded typed success/rejection/failure evidence without provider output, paths, SQL, credentials, handles, or unbounded logs.
8. No inference/action loop, new recovery operation, prompt/schema change, or M03 behavior change is introduced.
