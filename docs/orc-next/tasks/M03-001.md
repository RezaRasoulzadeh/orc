# M03-001 — Define typed Controller action intents and legality boundary

**Status:** Planned
**Milestone:** M03 — Typed Controller tools

## Objective

Introduce the first model-independent action contract between the read-only Controller and Orc's deterministic kernel. The task must define typed Controller intents and a deterministic legality inspection boundary, but must not execute or persist any Controller-requested mutation yet.

## Why

M02 proves that a bounded local Controller can observe canonical project/task state and return strict structured recommendations. Before granting mutation permission, Orc needs an explicit contract that separates model judgment from kernel authority. The Controller may propose an intent; Orc must independently determine whether that intent is currently legal and explain the result without changing state.

This task is intentionally a contract/legality slice, not an execution slice. It prevents M03 from coupling model output directly to `OrcApp` mutations or treating `OperationalNextStep` as an executable command API.

## Scope

- Add a small model-independent typed representation for Controller action intents.
- Define a deterministic legality result for an intent against current canonical Orc state.
- Build legality inspection through existing `ProjectOperations` / selected `OrcApp` application APIs; do not expose `Database`, SQLite, storage transactions or raw persistence to Controller code.
- Cover the normal task lifecycle actions needed for the first tool surface: dispatch, semantic review, revise and accept.
- Preserve room for later recovery/operator-decision tools without implementing them in this task.
- Keep Controller recommendation and local-runtime types independent of llama.cpp, Qwen, GGUF and provider details.
- Add deterministic tests proving legal and illegal intents are classified from canonical state without mutation.

## Required design

The implementation should establish a boundary equivalent in responsibility to:

```text
Controller recommendation / future tool call
                ↓
       ControllerActionIntent
                ↓
 deterministic legality inspection
                ↓
   Allowed | Rejected(reason/facts)
```

Names may differ if repository conventions justify it, but the semantic boundary must remain explicit.

The legality layer must not infer semantic policy that belongs to the Controller. It should answer factual/kernel questions such as whether the requested task exists, whether dependencies permit dispatch, whether the lifecycle phase permits review/revise/accept, and whether required current review/revision evidence exists. It must not decide whether an otherwise legal action is strategically wise.

## Integration constraints

- Reuse canonical lifecycle/application/read logic rather than reproducing transition rules inside `src/controller.rs`.
- Do not map an intent directly to CLI parsing or shell execution.
- Do not let the model provide arbitrary command names, SQL, file paths or free-form mutation arguments.
- Do not execute dispatch, review, revise, accept, recovery, validation, agent selection or any other mutation.
- Do not change existing CLI/TUI/desktop behavior.
- Do not introduce memory, planning/Lead migration, scheduler redesign, recovery intelligence, autonomy loops, model changes, Python or GPU work.
- Do not weaken existing explicit operator acceptance or cancellation gates.

## Non-goals

- Executing Controller intents.
- Adding autonomous continuation.
- Recovery/blocker resolution actions.
- Worker/model selection or economy decisions.
- Planning or Lead unification.
- Memory or training data collection.
- Replacing `OperationalNextStep` in existing read-model/UI surfaces unless a minimal adapter is required to avoid duplication.

## Dependencies

- M02-003 must be accepted before M03-001 implementation is accepted.
- Existing canonical `OrcApp`, `ProjectOperations`, lifecycle and review/revision legality surfaces remain authoritative.

## Acceptance criteria

1. A small serializable model-independent `ControllerActionIntent`-equivalent type exists for dispatch, semantic review, revise and accept, with no backend/provider/native-runtime types or arbitrary command payloads.
2. A deterministic legality inspection API returns a typed allowed/rejected result with a bounded, inspectable rejection reason and does not mutate project, task, run, review, worktree or persistence state.
3. Legality is derived by reusing canonical Orc application/read/lifecycle rules rather than duplicating a parallel Controller state machine; any missing reusable seam is added narrowly at the canonical layer and documented.
4. Tests cover each supported intent in at least one legal and one illegal canonical state, including dependency-blocked dispatch and stale/missing review or revision evidence where applicable.
5. Tests demonstrate legality inspection is side-effect free by comparing relevant task/run/review state before and after inspection.
6. Existing Controller recommendation behavior, lifecycle commands and interfaces remain unchanged; no Controller action is executed and no recovery/planning/memory/autonomy capability is introduced.

## Required validation

- Focused tests for Controller action intent serialization and legality inspection.
- Focused regression tests for canonical lifecycle legality reused by the new boundary.
- `cargo test --lib`.
- `cargo test --features llama-cpp --lib` if the feature remains buildable in the current environment; no model weights are required.
- `cargo fmt --check`.
- `cargo clippy --all-targets -- -D warnings`.
- Feature-enabled clippy if already part of the established local-runtime validation path.
- `git diff --check`.

## Completion evidence

Report:

- the exact action-intent and legality-result types introduced;
- which existing canonical Orc APIs/rules determine legality;
- any narrow canonical seam added and why it was necessary;
- tests proving supported legal/illegal cases and non-mutation;
- all validation results;
- any discovered architectural blocker that should change M03-002 before implementation.

Do not expand scope to solve a discovered M03-002 problem inside this task; report it instead.
