# M05-005 — Persist Controller Plan review decisions through explicit authorization

**Status:** Planned
**Milestone:** M05 — Planning and Lead unification

## Objective

Connect a validated M05-004 Controller Plan review result to canonical durable Plan review/status state through explicit trusted one-shot authorization, without fabricating legacy Lead runs or Lead decisions.

This task migrates review persistence only. Controller Plan revision generation, Plan application, general Lead removal, and workflow rewrites remain later work.

## Required path

```text
validated ControllerPlanReviewResult
              ↓
 typed review-persistence proposal
              ↓
 trusted one-shot authorization
              ↓
 fresh deterministic Plan/review legality check
              ↓
 canonical Controller-origin PlanReview persistence
              ↓
 existing Plan status semantics
```

## Scope

- Inspect M05-004 Controller review types/API, `PlanReview`, `Database::record_plan_review`, Plan review schema/migrations, current-valid-plan checks, Plan status transitions, plan-history/read-model consumers, and M03/M04/M05-003 authorization patterns before editing.
- Determine the smallest truthful durable provenance change required for a Plan review to originate from either legacy Lead review or Controller review. Do not fabricate `lead_run_id` or `lead_decision_id` for Controller reviews.
- Introduce typed Plan-review origin/provenance if the current durable schema cannot represent Controller reviews truthfully. Preserve strict legacy provenance requirements.
- Add or adapt one canonical Database persistence seam for Controller-origin Plan reviews. It must own the same deterministic Plan status transition semantics currently applied by canonical review persistence.
- Add a narrow typed persistence proposal derived only from a validated `ControllerPlanReviewResult` plus trusted canonical Plan identity/context needed for persistence.
- Add an opaque trusted one-shot authorization token following M03/M04/M05-003 patterns. It must be private-field, non-serializable, non-cloneable, consumed by execution, and bound to the exact project/Plan/review proposal or deterministic content identity.
- Add `OrcApp` authorization and authorized execution entry points.
- Immediately before mutation, re-load the Plan, verify project identity, verify it is still the current valid reviewable Plan, verify authorization/proposal matching, and validate that the requested review decision is one of the canonical three outcomes.
- Persist exactly one Controller-origin Plan review through the canonical Database seam and apply only the existing deterministic status effect associated with that decision.
- Return a bounded typed execution result containing persisted review identity, Plan identity, review origin, decision, and resulting Plan status as appropriate.
- Add migration/backward-compatibility tests if schema changes are required.
- Add deterministic tests for all three Controller decisions, authorization mismatch/substitution, stale/superseded Plan rejection, authorization consumption, persistence failure behavior, truthful provenance, exact status transitions, and absence of unrelated side effects.

## Preserve

- M05-004 inference prompt/schema/parser semantics.
- Legacy Lead Plan review behavior and truthful legacy run/decision lineage.
- Existing canonical Plan status semantics for approve/revise/user-decision review outcomes.
- Existing current-valid-plan rules.
- Existing Controller Plan proposal/persistence behavior.
- Existing approved-plan application/task creation behavior.
- Existing Plan history/read-model compatibility unless the minimum provenance extension requires representation updates.

## Constraints

- Controller/model output is never authorization.
- Do not fabricate Lead runs, Lead decision IDs, Planner runs, or other legacy provenance.
- Do not map Controller provenance to fake legacy provenance.
- Do not invoke the legacy Lead backend from the Controller persistence path.
- Do not generate a revised Plan in this task.
- Do not apply an approved Plan or create tasks.
- Do not automatically continue workflow stages.
- Do not remove legacy Lead/Planner machinery.
- Do not broaden review outcomes beyond approve/revise/operator-user-decision.
- Do not duplicate Plan status-transition logic if a canonical shared seam can be extracted narrowly.
- If truthful Controller review provenance requires a durable schema change, make the smallest migration and preserve existing data exactly.
- If `Database::record_plan_review` is too tightly coupled to legacy Lead lineage to extend safely without a broader semantic change, stop and report the exact constraint before weakening provenance or invariants.
- No autonomous review loop.
- No Qwen-specific core/domain behavior.
- No Python.

- Removing Planner/Lead roles or workflow stages.
- General user-decision routing migration.
- DIRECT_TASKS migration.

## Acceptance criteria

1. A validated `ControllerPlanReviewResult` can produce a typed persistence proposal without mutation.
2. Controller review persistence requires explicit trusted opaque one-shot authorization bound to the exact proposal/Plan/project identity.
3. Execution freshly verifies authorization matching and that the Plan remains the current valid reviewable Plan immediately before mutation.
4. Controller-origin Plan reviews are persisted with truthful Controller provenance and no fabricated Lead/Planner lineage.
5. Legacy Lead-origin Plan reviews retain strict truthful legacy provenance and existing behavior.
6. Approve, revise, and operator/user-decision outcomes produce exactly the existing canonical Plan status semantics and no additional lifecycle action.
7. Authorization mismatch/reuse, invalid proposal, stale/superseded Plan, or persistence failure produces no partial review/status mutation.
8. Successful execution creates exactly one durable Controller-origin Plan review and no Lead decision/run, Planner run, task, workflow continuation, revision generation, or Plan application.
