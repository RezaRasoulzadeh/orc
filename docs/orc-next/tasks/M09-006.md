# M09-006 — Provision and measure the canonical specialization source

**Status:** Planned
**Milestone:** M09 — Controller specialization

## Objective

Establish the actual canonical Controller specialization source before any trainer-specific transformation or training. Verify the configured global registry through the normal operator path, then capture deterministic M08-011 inventory and M09-001 Active snapshot evidence without mutating canonical examples or inventing readiness.

## Context

M09-005 completed the native/offline specialization investigation and deferred backend selection. The investigated host had a configured global registry at `/home/reza/.local/share/orc/agents.db`, but that on-disk registry did not contain `controller_experience_examples`; therefore the canonical dataset count was not measurable and must not be treated as zero.

M08-011 already provides deterministic complete-dataset inventory. M09-001 already provides the trainer-neutral canonical Active experience snapshot. This task should use those existing application/read boundaries rather than introduce a second dataset authority or inspect fixtures as production data.

## Scope

Use the normal operator-supported Orc path to initialize/open the configured global registry if that is the intended registry, then read the canonical experience inventory and Active snapshot through existing APIs or the narrowest existing operator-facing path.

Record:

- resolved global registry path and how it was resolved;
- whether schema provisioning/migration was required and what existing Orc mechanism performed it;
- complete canonical example count and lifecycle counts available from M08-011;
- Active snapshot schema version and count from M09-001;
- deterministic example IDs/order and capability coverage derived from canonical records;
- verification-basis and outcome/lifecycle distributions already represented by canonical typed fields where available;
- any missing capability coverage or other factual prerequisites relevant to later transformation work;
- exact repository revision and registry evidence used for the measurement.

Keep measurement separate from training-readiness judgment. If the configured registry is not the intended operator data store, stop at that factual mismatch and document it rather than copying, seeding, fabricating, or migrating data by assumption.

## Required deliverable

Produce a repository-grounded measurement report under `docs/orc-next/` containing the resolved registry authority, provisioning evidence, M08-011 inventory, M09-001 snapshot summary, exact nine-capability coverage, factual distributions available from canonical records, and unresolved blockers.

If a tiny operator-facing read-only command or test-only seam is genuinely required to obtain existing M08-011/M09-001 evidence, identify that separately before implementation. Prefer existing APIs; do not add tooling merely for convenience.

## Non-goals

No trainer-specific export, message transformation, split, sampling, balancing, deduplication, ranking, weighting, readiness threshold, synthetic examples, automatic harvesting, canonical example mutation, model download, GGUF acquisition, training, adapter creation, dependency/toolchain installation, backend selection, promotion, default-model change, storage redesign, embeddings, provider fallback, provider token hard cap, or Python runtime dependency.

Do not use tests/fixtures as production dataset inventory evidence. Do not treat a missing table as an empty canonical dataset.

## Acceptance criteria

1. The authoritative configured global registry is resolved through existing Orc authority rules and explicitly recorded.
2. Registry provisioning state is verified through the normal operator-supported path; missing schema is not silently interpreted as zero data.
3. M08-011 complete inventory is captured from canonical storage with exact factual counts.
4. M09-001 Active snapshot is captured with schema version, exact count, deterministic IDs/order, and validated canonical records.
5. Coverage across all nine inference-backed Controller capabilities is measured from canonical records; missing coverage remains an explicit fact.
6. Any reported distributions or quality/provenance facts come only from existing canonical typed fields, with no inferred readiness score or training threshold.
7. No canonical records, dataset semantics, runtime behavior, model artifacts, defaults, or training state are mutated.
8. The result provides sufficient factual input for a later independently reviewable snapshot-to-trainer transform task without selecting the transform or trainer here.

## Required review

Independently verify the resolved registry authority, provisioning mechanism, exact inventory/snapshot evidence, capability coverage, and absence of canonical data mutation or readiness inference. Documentation-only execution requires no full code validation unless code changes unexpectedly.

## Completion evidence

Report the repository revision, registry path/authority evidence, provisioning state, M08-011 inventory, M09-001 snapshot schema/count/IDs, capability coverage, canonical distributions actually measured, unresolved blockers, changed files, and validation performed. Do not commit or push before independent review.
